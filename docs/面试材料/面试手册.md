## 一、项目一页纸

**项目名称**：EventGuard · 电商订单事件溯源与智能异常治理平台（个人全栈项目）

**背景**：面向电商订单全生命周期的追溯与异常治理场景，区别于仅保存最终状态的传统订单平台，将每次状态变更沉淀为可回放、可审计的事件，并结合实时异常检测、告警分析、人工补偿和运营查询，实现从订单追溯到异常处置的闭环。

**一句话速览（30 秒）**：EventGuard 是一个电商订单的事件溯源管理台。订单每次状态变更都存成不可变事件，可以回放任意历史时刻的状态；事件流经 Debezium CDC 进 Kafka，Python 服务在上面做分层异常检测，告警通过 WebSocket 实时推到前端；另外支持用中文直接问订单和统计，不用写 SQL。技术栈是 Spring Boot 3.3 + Vue3 + FastAPI，全套 Docker Compose 一条命令起。

30 秒里必须留在面试官脑子里的三个词：**事件溯源、CDC 解耦、分层检测**。

**核心技术**：Java 17、Spring Boot 3.3、事件溯源、CQRS、PostgreSQL、Kafka、Debezium、FastAPI、Vue 3、Docker Compose。

**六条核心职责（对应简历，可直接讲）**：

1. **重构订单写入为事件溯源**：不可变事件为唯一事实来源，唯一约束 + 版本前置校验 + 3 次重试；`commandId` + `command_log` 幂等（事务内 advisory lock + 参数指纹，并发重复命令安全闭合），每 100 个事件快照，重建仅回放增量。
2. **完善读写分离异步读模型**：`idempotent_consumers` 去重 + 版本守卫 + 读己写（投影提交通知即时唤醒 + 50ms 兜底轮询、2s 超时，等待不占 Web 线程）；30 写并发验收 110/157 携带版本断言的抽样窗口内追平，未追平如实 409。
3. **搭建 CDC 链路**：PostgreSQL WAL → Debezium → Kafka，消息由库提交派生；消费端手动提交、重试后 DLT（专用字符串编码 + 管理端重放接口），混沌验证含恢复后投影追平断言。
4. **规则与模型分层检测**：5 业务规则 + 3 流程规则 + IsolationForest 事件级 + HMM 序列级（已接线线上）；做了 Baseline 对照并如实汇报负结果（F1 0.887 → 0.753，召回零增益）。
5. **安全可降级的智能查询与处置闭环**：意图分类 + 正则抽参 + 模板接口，不拼 SQL；8s 超时降级摘要；Saga 编排 + 高风险人工审批。
6. **自动化评测与可观测**：三端 338 项测试 + 一键评测 + 混沌注入；Prometheus/Grafana/Loki，含消费积压（lag）指标与告警规则。

**回答边界（任何问题都适用）**：已部署并完成单机全链路验证的个人项目，没有真实生产用户和业务流量。可以说「已部署可访问」（Cloudflare Tunnel 是真的），不能说「生产运行」「服务 N 个用户」。

## 二、讲解话术

### 1 分钟版

> 这个项目叫 EventGuard，做的是电商订单的事件溯源和异常检测。
>
> 起因是我发现传统写法有个问题：订单状态直接 UPDATE 覆写数据库，出了数据不一致只能看到最终状态，没法回答「它是怎么走到这一步的」。所以我把订单的每一次变更都存成一条不可变事件，状态是靠事件 replay 算出来的，任意历史时刻都能回放，天然有完整审计链路。
>
> 在这之上我做了两件事。一是异常检测——事件通过 Debezium CDC 流进 Kafka，Python 服务消费后做分层检测，业务规则判金额偏离、重复支付、状态跳跃，HMM 给序列级第二意见，告警持久化后经 WebSocket 实时推到前端看板。二是中文自然语言查询，运营可以直接问「最近 7 天有多少订单」，不用写 SQL。
>
> 技术栈是 Spring Boot 加 Vue3，AI 服务用 FastAPI 单独拆出来，整套 Docker Compose 一条命令起。测试写了三百多项，一致性相关的用 Testcontainers 真起 PostgreSQL 跑端到端验证。

### 3 分钟版（为什么 → 写侧 → 读侧/CDC → AI 与坑 → 收尾）

**第一段 · 为什么（20 秒）**：传统 CRUD 直接覆写状态，数据不一致时只能看到结果看不到过程。所以我选了 Event Sourcing：状态变更本身成为唯一事实来源。

**第二段 · 写侧（50 秒，硬功夫，讲慢）**：

> 并发两层：数据库上 `UNIQUE(aggregate_id, event_version)` 唯一约束，加写前 `MAX(version)` 前置校验。前置校验给出明确错误，唯一约束兜住校验与插入之间的竞态窗口。冲突由重试模板线性退避重试 3 次。
>
> 幂等另一条线：客户端生成 `commandId`，与事件写入同事务落 `command_log`；重复提交返回首次结果。并发相同 `commandId` 用事务内 advisory lock 串行化，并保存参数指纹——同编号不同参数会被拒绝。
>
> 事件多了重建慢，每 100 个事件落一次快照，重建只回放增量。

**第三段 · 读侧与 CDC（40 秒）**：

> 读侧 CQRS 异步投影。消息不是应用发的，是 Debezium 读 PostgreSQL WAL 推到 Kafka——「事件落库」和「发消息」应用内做不原子，CDC 让消息成为库变更的必然结果。
>
> 异步带来两个问题：重复投递用消费去重表 + 版本守卫挡住；用户写完立刻查不到，做读己写——投影事务提交后主动通知等待中的请求，50 毫秒兜底轮询、2 秒超时返回 409 提示「数据同步中」，等待全程不占 Web 线程（DeferredResult）。

**第四段 · AI 与诚实的坑（40 秒，加分点）**：

> 检测分层：规则在 Java 侧（要读事件库算用户历史基线），模型在 Python，反向调规则接口合并结论。金额基线的标准差用数据库 stddev_pop 真实统计，90 天窗口。
>
> 我踩了个坑，也是最有价值的部分：做完 Baseline 对照发现加 Isolation Forest 后 F1 从 0.887 掉到 0.753，两个版本召回完全相同（0.896），误报从 176 涨到 691——模型只增噪不增召回。根因是 `contamination=0.05` 强制按固定比例判异常。我把这个负结果如实写进了评测报告。

**第五段 · 收尾（10 秒）**：最大的收获是分布式里「保证一致性」不是一句话，是落到具体约束、去重表、版本守卫和超时降级上，每层都要能说清挡的是哪种失败。

## 三、架构详解

### 链路全景

```
Vue3 管理台
  │  写命令 ──▶ CommandHandler ──▶ 事务{ EventStore.append + command_log }
  │                                     │  乐观锁(唯一约束 + MAX(version)前置校验)
  │                                     │  每100事件 → aggregate_snapshots
  │                                     ▼
  │                              PostgreSQL domain_events (WAL)
  │                                     │
  │                              Debezium CDC
  │                                     ▼
  │                                Kafka domain-events
  │                        ┌────────────┼────────────┬──────────────┐
  │                        ▼            ▼            ▼              ▼
  │              OrderViewProjection  SagaTrigger  Python检测   (重试后→DLT,可重放)
  │              (原子去重+版本守卫)  (补偿编排)   (规则+IF+HMM)
  │                        │ afterCommit 通知                │ 告警
  │  读查询 ◀── DeferredResult ◀─ ProjectionProgressNotifier  ▼
  │              (兜底轮询 50ms/2s)              anomaly_alerts 表 + Kafka anomaly-alerts
  └─ WebSocket ◀── AnomalyWebSocketHandler ◀── AnomalyAlertConsumer(先落库再广播)
```

### 关键决策一：Event Sourcing + CQRS，而不是 CRUD + 审计表

审计表是事后记录，状态仍靠 UPDATE 覆写，审计漏写无法自动发现（状态和审计是两份可能漂移的数据）。事件溯源里事件**就是**状态来源。binlog 也不行：它记行变更丢业务意图——同一次状态变化可能来自用户支付、运营手改或补偿回滚，事件类型能区分，binlog 不能，而异常检测需要的正是这层语义。

代价（要主动说）：读侧最终一致、事件 schema 演进要兼容旧事件、存储只增长（90 天归档缓解）。

### 关键决策二：Debezium CDC，而不是应用内双写

`eventStore.append(); kafka.send();` 不原子：库成功消息失败投影永远落后；消息成功库回滚下游收到不存在的事件。Outbox 表能解决但要自建轮询发送器——而本项目事件表**本身就是 Outbox**，Debezium 读 WAL 等于零应用代码拿到 Outbox 保证。代价：多一个中间件、CDC 有延迟、connector 挂了链路停（有健康检查）。

### 关键决策三：NL 查询走「意图分类 + 模板执行」，不做 Text2SQL

按重要性：① 安全——生成的 SQL 要么敢直接执行（注入面全开），要么写个比模板复杂十倍的校验器；② 可靠——生成正确率不稳定，出错时用户看到数据库报错；③ 可降级——模型挂了 Text2SQL 完全不可用，模板有关键词兜底。代价是只能答三类问题，这是主动选的边界：**可控的窄能力 > 不可控的宽能力**。

### 一致性的五层防线

1. **写侧**：唯一约束 + 前置版本校验 + 重试 3 次 → 并发写不产生版本空洞
2. **命令侧**：`command_log` 主键幂等 + advisory lock + 参数指纹 → 重复/并发提交不产生重复事件
3. **消费侧**：`idempotent_consumers` 原子占位去重 + 版本单调守卫 → at-least-once 下投影不重复不倒退
4. **读侧**：读己写（投影通知 + 兜底轮询，2s 超时 409）→ 宁可提示「同步中」，不返回过期数据
5. **隔离故障**：消费失败重试后进 DLT（字符串编码无损 + 管理端重放），毒消息不阻塞分区

## 五、事实边界与代码地图

### 简历表述 vs 代码支持（2026-08-16 更新）

| 简历表述 | 代码真正支持的结论 | 剩余限定 |
|---|---|---|
| 重复提交不新增事件 | 顺序重复读 `command_log` 返回首次结果；并发重复经 advisory lock 串行化 + 参数指纹校验 | 默认不强制客户端传 `commandId`（生产由 `EG_REQUIRE_COMMAND_ID=true` 开启） |
| 每 100 个事件生成快照，重建仅回放增量 | 版本达 100 倍数写快照；快照边界差一 bug 已修复（`event_version > snapshotVersion`，含边界测试） | 阈值是经验值未压测标定 |
| 读己写 50ms 轮询 2s 超时 | 投影提交通知即时唤醒 + 共享线程兜底轮询，DeferredResult 不占 Web 线程 | 通知为进程内单实例；多副本需 Redis |
| 110/157 读己写窗口内追平 | s09 抽样携带 expectedVersion 并断言版本/状态/金额 | 未追平返回 409 是明确降级语义 |
| 数据库/Kafka 故障 2s 恢复、事件零丢失 | PG 场景 `pg_isready` 约 2s、重启前后行数一致；Kafka 场景暂停期间可写，恢复后**新增投影按 expectedVersion 追平断言** | 新断言需在服务器重跑混沌回填数字；恢复时间两场景口径不同 |
| 8s 超时降级摘要 | 意图分类 2s（超时走关键词）+ 润色共享 8s 总预算，分层 wait_for 保证上界 | httpx 单次 30s 超时依赖外层取消兜底 |

## 六、Q&A 题库（Q1–Q200 精炼版）

> 口径标注：**已实现**=代码存在可解释路径；**已验证**=测试/评测断言过；**有限验证**=单机/固定用例/Mock；**尚未覆盖**=代码缺口或仅设计目标。标 ✅ 的为 2026-08-16 已修复/升级项。

### 一、项目整体与架构（Q1–Q12）

**Q1 一分钟介绍？** 订单追溯+异常治理个人全栈项目；变更存为不可变事件、状态由回放得出；写侧 Java 单事务（事件+命令日志），Debezium→Kafka，多消费组分头投影/检测/补偿。最想让面试官关注：写侧并发与幂等、CDC 与至少一次下的投影一致性、大模型被限制在表达层。边界：已部署无真实流量。

**Q2 为什么不用审计表？** 审计表是事后附属记录，状态与审计是两份可能漂移的数据；事件溯源里事件就是事实源。且异常检测需要「为什么变成这个状态」的业务语义，行变更日志区分不了用户支付/运营手改/补偿回滚。审计表适合只留痕不需重建状态的场景。

**Q3 事件溯源和 CQRS 是一回事吗？** 不是。前者解决状态如何持久化，后者解决读写模型分离。事件表适合按聚合追加回放，不适合列表筛选统计，所以异步投影出 `order_view`。两者可独立存在。

**Q4 创建订单完整链路？** 前端带 JWT + `X-Command-Id` → 控制器构造命令 → 处理器查 `command_log` 未命中 → 新事务内加载聚合、校验、追加事件、写命令日志 → 提交后 WAL → Debezium → Kafka → 投影消费组同事务更新 `order_view` + 去重记录 → afterCommit 通知读己写等待者。

**Q5 谁是唯一事实来源？** `domain_events`。Kafka 是传播通道（可重复可重建），`order_view` 是可丢弃投影，快照是回放加速点。投影与回放不一致时信事件、重建投影。

**Q6 强一致与最终一致的边界？** 单命令内事件+命令日志同事务原子；单聚合版本唯一约束强保证。库→Kafka→读模型→检测都是最终一致；外部支付库存靠幂等键+状态机+补偿，无跨系统强一致。

**Q7 为什么不用分布式事务？** Kafka/PG/第三方无统一低成本 2PC；全局事务扩大锁与故障范围，管不住已发生的支付副作用。本地事务 + CDC 异步传播 + Saga 补偿更符合实际。参与方可控、事务短可评估 2PC；资源可预留可用 TCC。

**Q8 最难的问题？** 明确每个故障窗口由谁兜底：前置校验挡不住竞态要唯一约束兜底；投影提交与 offset 不原子要 DB 更新与去重同事务；LLM 不稳定就不能让它生成查询或直接执行动作。曾有快照边界、Saga 失败处理等已识别并修复的工程问题。

**Q9 如何证明不是只画架构图？** 三类证据：可运行代码路径；三端 338 项测试（不等于覆盖率）；一键评测（功能套件+负载+混沌）。同时主动承认评测脚本本身也需审计口径。

**Q10 为什么 Java 管领域、Python 管智能？** 事务/权限/一致性适合 Spring；模型推理与 LLM 生态在 Python 更便宜。经 Kafka + 受限 HTTP 协作，Python 不能直连订单库。代价是多一条网络边界。

**Q11 为什么不全放一个单体？** 只做订单管理的话模块化单体够用；拆 Python 是因为技术栈与资源隔离确有价值。Java 内部读写权限补偿保持单服务——只在确有价值处拆分。

**Q12 重做最先改哪三件事？** ①正确性：快照边界（✅已修）、无状态事件推进版本（✅已实现）、并发命令幂等（✅已修）、投影重建流程；②补偿可靠性：Saga 实例持久化、稳定外部幂等键；③评测口径：错误率分母、版本断言（✅s09 已校验）、故障后追平核对（✅混沌已补断言）。

### 二、事件溯源、聚合与写侧一致性（Q13–Q34）

**Q13 领域事件 vs 操作日志？** 事件是已发生的业务事实（含聚合/版本/载荷/元数据），参与聚合重建与下游处理；日志用于排障，删除不改业务状态。可靠性要求不同。

**Q14 「不可变」由什么保证？** 应用层只追加 + 主键 + 版本唯一约束；数据库账号仍可 UPDATE/DELETE，无哈希链。生产化：应用账号只授 INSERT/SELECT、归档账号分离、可选哈希链。

**Q15 聚合根是什么？** 一致性边界。`OrderAggregate` 封装状态机（待支付才能支付、已确认才能发货），命令必须先恢复聚合再执行，控制器与投影无法绕过不变量。代价是每次写要加载历史 → 快照。

**Q16 raise 与 applyEvent 区别？** 回放历史只 `applyEvent` 更新状态不进待写列表；新命令 `raise` 先进 `pendingEvents` 再 apply，保存时 flush。区分开否则每次加载会把旧事件重写一遍。

**Q17 版本如何连续不重复？** 前置 `MAX(version)` 校验 + `UNIQUE(aggregate_id, event_version)` 兜底；多事件命令在外层事务内整体提交/回滚。边界：`append()` 自身无事务注解，脱离命令事务调用需自带事务。

**Q18 查最大版本后插入为何仍有竞态？** READ COMMITTED 下两个事务可同时读到相同已提交版本；检查与插入非原子。唯一约束让后者失败转乐观并发异常，新事务重加载重试。前置校验的价值是早失败和明确报错。

**Q19 为什么乐观锁？** 同一订单并发写概率低，乐观锁无冲突不占锁，冲突时 3 次重试成本低于全程持锁。热点聚合持续冲突时再分析是否按聚合串行队列。

**Q20 重试几次？** `MAX_RETRIES=3` = 初次失败后再重试 3 次，共 4 次尝试，退避 10/20/30ms。每次必须新事务新聚合（旧事务可能已标记回滚）。只重试乐观并发异常——确定性错误重试无意义。

**Q21 事件与 command_log 为什么同事务？** 事件提交而日志未记 → 重试会重复执行；日志先记而事件回滚 → 重复请求拿到未发生的成功。同事务要么都成功要么都回滚；Debezium 只见已提交事件。

**Q22 commandId 幂等实现与验证程度？** 重复编号先查 `command_log` 命中即返回首次结果；顺序重复已有单测+功能评测验证（两请求成功、事件一条、日志一行）。

**Q23 并发相同 commandId？** ✅已修复：事务内 `pg_advisory_xact_lock(commandId)` 串行化，第二个请求等锁后读到首次结果返回；数据库主键仍是底线。

**Q24 不传 commandId 会怎样？** demo 默认服务端生成随机 UUID（开箱可用但识别不了重试意图）；生产 `EG_REQUIRE_COMMAND_ID=true` 强制，ProductionSecurityGuard 拒绝无号启动。可靠做法是调用方生成并持久化幂等键。

**Q25 同编号不同参数？** ✅已修复：`command_log` 存 SHA-256 请求指纹，命中时校验订单/类型/参数，不一致抛「commandId 已用于不同的订单、命令类型或参数」。

**Q26 库存预留为何在事务前？** 外部副作用无法进本地事务。先按 `commandId` 调网关（网关按编号幂等）再写事件。风险：网关扣减成功而本地事务失败——生产要持久化外部请求状态+对账释放。

**Q27 支付链路可靠性风险？** 意图事件→协调器调网关→写 `gateway_request`→异步回调（稳定命令编号+可选 HMAC 签名）→完成事件。窗口一：网关成功而 `gateway_request` 插入失败成孤儿支付；窗口二：回调先置终态再派发命令，命令失败后重放被「已终态」挡住。生产需 pending 先落库+状态机重试。

**Q28 为什么快照？阈值为何 100？** 回放量随事件数增长，快照以空间换加载时间。100 是经验值未压测标定——科学定法是测单事件回放耗时按目标延迟反推（主动承认该补测）。

**Q29 快照增量回放曾有实际错误？** ✅已修复：曾有 `snapshotVersion+1` + `event_version >` 的差一错误会跳过快照后第一条事件；现改为传快照版本严格大于，并有 `loadFrom(orderId, 2)` 边界测试（修复于 351fcff）。

**Q30 快照与事件同事务？** 是，命令事务内事件+快照+命令日志整体提交/回滚。快照只是缓存，也可异步生成，但加载必须校验快照版本结构、异常回退全量回放。

**Q31 事件结构升级怎么办？** 当前 JSONB 按 `event_type` 硬映射，无 `schemaVersion`/upcaster——加可选字段可兼容，删改字段破坏回放。生产：事件加版本号+向上转换器+契约测试。**尚未覆盖**。

**Q32 90 天归档脚本安全吗？** 默认 dry-run，同事务「复制到归档表+删除」；但按 created_at 全局删而非按聚合快照水位，且加载不查归档表——真执行可能切断无快照聚合的重建链。**尚未覆盖**（按聚合快照水位归档为升级路径）。

**Q33 upToVersion 是状态时间旅行吗？** 不是完整版：✅已优化为 SQL 层 `event_version <= ?` 截断（不再全量拉取内存过滤），返回的是截至版本 N 的事件列表，未重放出结构化状态。

**Q34 历史事件被篡改能发现吗？** 不能。无内容哈希/链式摘要/外部锚定，主键与版本约束只防重复不防改动。高审计场景加哈希链+权限分离+管理审计。**尚未覆盖**。

### 三、CQRS、异步投影与读己写（Q35–Q50）

**Q35 为什么异步投影？** 同步投影把读侧逻辑和故障放进写事务。异步让写侧只提交事实，下游独立扩展重建。代价是短暂旧读——用读己写按需补强而不是全局同步。

**Q36 投影消费事务包含什么？** 反序列化 → 原子 `INSERT ... ON CONFLICT DO NOTHING` 占位去重 → 更新 `order_view`（版本单调条件）→ afterCommit 通知等待者。任一步失败整体回滚；Kafka offset 独立，重投由去重表挡（at-least-once + 幂等）。

**Q37 去重键为什么含消费组？** 同一事件被投影/Saga/检测等多个业务消费者独立处理，`(consumer_group, event_id)` 表示「某消费者是否处理过某事件」。消费者标识不可随意改名。

**Q38 先查后插的竞态？** ✅已统一为原子占位：投影用单条 `tryMarkProcessed`（INSERT ON CONFLICT 判断 rowcount）；SagaTrigger 也改为同款原子占位（2026-08）。对外部副作用的场景仍建议带状态的 Inbox。

**Q39 版本守卫解决什么？** 投影 UPDATE 仅在现有版本小于事件版本时生效：旧事件不覆盖新状态，同版本重复不改。

**Q40 版本守卫解决不了什么？** 乱序缺口：v3 先到 v2 后到，v2 被丢弃但其独有字段（如支付时间）永久缺失；v1 未到时 v3 更新 0 行仍可能被标已处理。生产应检查 `currentVersion+1` 连续性，缺口暂存或重放。

**Q41 无状态事件要推进版本吗？** ✅已实现：`PaymentRequestedEvent`/`InventoryReservedEvent`/`CompensationExecutedEvent` 等经 `advanceVersion` 推进 `order_view.version`，读己写不会因目标版本是这类事件而误超时。

**Q42 读己写如何工作？是强一致吗？** 命令返回版本，查询带 `expectedVersion`；✅现为投影 afterCommit 通知即时唤醒 + 共享单线程 50ms 兜底轮询，2s 超时 409。是为单次写提供的有界等待，不是系统级强一致。

**Q43 为什么超时 409 不返回旧数据？** 调用方给了目标版本，返回旧数据违反语义；一直阻塞占资源且 2s 后大概率是链路故障。409 让前端提示「同步中」可重试。✅通知机制下已不占 Web 线程（DeferredResult）。

**Q44 Thread.sleep 轮询的扩展性？** ✅已解决：投影提交通知（`ProjectionProgressNotifier`，事务提交后唤醒）为主，共享单线程调度器兜底轮询为辅，Controller 返回 DeferredResult 释放 Servlet 线程。通知为进程内单实例，多副本需 Redis Pub/Sub（已标注升级路径）。

**Q45 expectedVersion 从哪来？** 写命令响应的版本，不能客户端猜（并发/回调/补偿会插事件）。接口应校验非负、限制异常大值。

**Q46 「520 次写后查询均读到最新版本」真实吗？** 历史口径：那轮抽样只验证「2s 内查到记录」。✅当前 s09 口径已收紧：读己写线程携带 `expectedVersion` 并断言版本+状态+金额，110/157 追平、其余 409——新版负载报告以此为准（服务器重跑后回填）。

**Q47 一致性套件 13 项证明什么？** 固定生命周期顺序、读己写接口、顺序幂等、事件数量、最终版本、独立状态机回放一致。不覆盖：任意乱序、并发命令（现有单测覆盖 advisory lock 路径）、长时间故障。

**Q48 reset() 为何不能完成重建？** `reset()` ✅已同时清理 `order_view` 与该消费组的去重记录，但 Kafka 消费位点仍需重置（或换新消费组），否则消息不会重投。在线重建的正解是 `order_view_v2` + 新命名空间回放后切换。

**Q49 投影与回放不一致怎么排查？** 事件是事实源：查事件版本连续 → Debezium 位点/日志 → topic 消息与 key → 消费组 lag/DLT → 去重记录 → `order_view.version`。修复靠重放或新投影切换，不手改数据行；`eventguard.projection.lag` 指标可提前发现。

**Q50 列表分页与统计的边界？** `LIMIT/OFFSET` 深分页慢且页边界漂移，生产改 `(updated_at, order_id)` 游标分页；统计按 `updated_at` 过滤，语义是「最近状态更新时间」≠ 创建/支付时间。**尚未覆盖**（当前量级 OFFSET 足够）。

### 四、PostgreSQL WAL、Debezium 与 Kafka（Q51–Q77）

**Q51 双写问题？** 库与队列无共同本地事务，谁先谁后都有一致性窗口。项目不在业务事务里发 Kafka，消息由 Debezium 从已提交 WAL 派生。

**Q52 与 Outbox 的关系？** 思想同 Outbox：`domain_events` 本身既是事实源也是待发布消息，不必复制一张 Outbox 表。代价：事件保留策略、CDC 运维与消息契约耦合。

**Q53 WAL 是什么？** 预写日志，修改数据页前先记日志。`wal_level=logical` 后可解码为行级变更，Debezium 用 `pgoutput` 只订阅 `domain_events`。WAL 不是业务事件，业务语义在 `event_type` 与载荷里。

**Q54 publication / slot / offset？** publication 决定哪些表可发布；replication slot 是 PG 端消费水位（阻止 WAL 过早清理）；Debezium offset 是连接器断点续传位置（挂载于命名卷）。恢复要三者一起考虑。

**Q55 为什么只发布已提交事务？** 逻辑解码识别事务边界，回滚事务的变更不发布——命令事务任一步失败，Kafka 收不到该事件。

**Q56 Debezium 恢复后为何可能重复？** 消息已入 Kafka 而 offset 未持久化就崩溃，恢复后重发。CDC 天然至少一次，事件编号去重是正确性要求而非优化。

**Q57 首次启动/offset 丢失？** 依 `snapshot.mode` 与现有槽决定初始快照。未显式固定快照策略，生产要明确上线/重建/offset 丢失流程，防止全量重发或 WAL 已清无法恢复。**尚未覆盖**。

**Q58 SMT 做了什么？** `ExtractNewRecordState` 去 envelope + `RegexRouter` 统一路由到 `domain-events`；消息键 `aggregate_id` 保证同订单同分区。SMT 只做轻量转换，语义处理在消费者。

**Q59 分区内有序？** 每分区独立追加日志，跨分区无全局顺序。`aggregate_id` 作 key 保订单内顺序；消费侧仍留版本守卫（重放/扩容/并发处理可能乱序）。

**Q60 分区数？** 无显式主题初始化脚本，靠自动创建，单机默认大概率单分区。设计文档的 6 分区规划不能当部署事实。生产要预创建主题并纳入基础设施代码。**尚未覆盖**。

**Q61 消费组解决什么？** 组内分区分担、组间独立全量。投影/Saga/检测三个组各自消费同一事件流。实例数超过分区数不再增吞吐。

**Q62 关闭自动提交=逐条手动提交吗？** Python 是（成功后逐条 `commit()`）；Java 依赖 Spring Kafka 容器提交策略+统一错误处理器，不是业务代码逐条提交。稳妥说法：「消费成功后推进位点，失败有限重试」。

**Q63 至少一次/至多一次/精确一次？** 系统整体至少一次+业务幂等；投影靠去重表做到「重复消息不重复更新」的业务效果，但外部退款等不能扩大成端到端 exactly-once。

**Q64 Java 消费重试几次？** `FixedBackOff(1000, 2)` = 首次失败后再重试 2 次，共处理 3 次，随后进 `<topic>.DLT`。别说成「重试三次」。

**Q65 Python 重试与退避？** 失败 seek 回原 offset，第 1/2 次失败等 0.3/0.9s；第 3 次失败直接发 DLT，成功后提交原位点（1.8s 常量实际用不到）。失败计数在内存，重启重新计数。

**Q66 无参 commit 为何依赖 max_poll_records=1？** 无参提交推进当前已处理分区位置；每批 1 条保证不会跨过失败消息。将来放大批量要改为按分区连续成功提交。

**Q67 为什么需要 DLT？进了 DLT 算成功吗？** 毒消息无限重试会阻塞分区，DLT 隔离保主链路。进 DLT=失败被隔离≠业务完成。✅已补管理端重放接口（`POST /admin/dlt/{topic}/replay`）与 lag 告警规则；按消费组隔离 DLT 通道仍是升级路径。

**Q68 DLT 发布与 offset 提交原子吗？** 不原子。Python 先等 DLT 发布成功再提交原 offset（避免跳过）；DLT 成功而提交前崩溃会重复写一条 DLT——DLT 消费/重放也要按事件编号幂等。✅Java DLT 已改专用 StringSerializer（无 `__TypeId__` 头、无二次编码），重放可无损往返。

**Q69 Kafka 暂停时为何还能写？** 写路径只依赖 PG。但复制槽会持续保留 WAL，长时间停机可能撑满磁盘——解耦是延迟故障传播，不是无限承受。

**Q70 Debezium 长期不可用拖垮 PG？** 槽不推进则 `pg_wal` 增长直至磁盘耗尽。需监控槽保留字节、LSN 差值、磁盘余量。**尚未覆盖**（当前告警不含复制槽指标）。

**Q71 当前 Kafka 是高可用吗？** 不是：单 KRaft Broker、副本因子 1、PLAINTEXT、无消息数据卷。适合单机验证。生产需多 Broker 多副本 `acks=all` + 认证加密。**尚未覆盖（明确排除项）**。

**Q72 Kafka 容器删除重建会怎样？** 无数据卷则主题消息丢，而 Debezium offset 认为已发布不会补发——需人工重置 offset/槽或从事件表回灌。「pause 可恢复」≠「数据灾难可恢复」。

**Q73 「2 秒恢复零丢失」的口径问题？** PG 场景计时到 `pg_isready`，零丢失=重启前后行数一致；Kafka 场景含暂停期间写命令、以 topic 可访问为恢复，`data_loss_events` 曾是脚本直填。✅2026-08-16 起 kafka-pause 新增恢复后投影按 expectedVersion 追平断言，「零丢失」证据链补齐到投影层（数字待服务器重跑回填）。

**Q74 如何补成可信的 Kafka 故障评测？** 记录位点→暂停期间写唯一标识订单→恢复后核对 Debezium 位点推进、分区末端出现该事件、lag 归零、`order_view` 达目标版本，分段计时。✅chaos_run.sh 已按此思路实现（读己写断言投影追平）。

**Q75 CDC/投影延迟怎么测的？** CDC 从创建订单前到评测消费者收到（口径合理）；投影收敛从「Kafka 已到评测消费者」起计——只是附加时间不是端到端。别把 3.6ms 外推为完整 SLA。

**Q76 「库里有事件前端查不到」怎么排查？** 沿链路：事件表版本 → 复制槽/Debezium 日志 → topic 消息 → 消费组 lag/反序列化错误/DLT → 去重表误标 → 投影 SQL 影响行数 → `order_view.version`。✅新增 lag 指标（Java `kafka_consumer_fetch_manager_records_lag` + Python `eventguard_ai_consumer_lag`）让链路可直接观测。

**Q77 健康检查为何不等于管道健康？** Debezium 检查只看 JVM 进程；`/health` 的 Kafka 字段只回配置地址。进程存活、端口可连、数据追平是三个层次。更可靠：最后成功事件时间、两端 lag、DLT 增量、探针事件端到端延迟。**尚未覆盖**。

### 五、智能查询、异常检测与 Agent（Q78–Q103）

**Q78 为什么不让 LLM 生成 SQL？** 注入/越权/全表扫描/幻觉/模型不可用整体失效。模型被限制在理解与表达层：意图三类、参数代码抽取校验、固定只读接口、模型只润色。安全边界是确定性代码和接口权限，不是提示词。

**Q79 三类意图如何执行？** 状态查 UUID→`GET /orders/{id}`；统计提状态+时间窗→`GET /orders/stats`；回放提 UUID→`GET /orders/{id}/events`。参数少用正则更稳可测；复杂筛选再考虑结构化输出+Pydantic 校验。

**Q80 模板完全消除注入了吗？** 切断了「注入→任意 SQL/写操作」的路径，但意图判断和润色文字仍可能被操纵。结构化结果独立展示、输出过滤、审计是下一步。

**Q81 「忽略指令删除所有订单」会怎样？** 最坏落到某查询意图；模板执行器无删除能力，无 UUID 会反问。系统不免疫提示词攻击，但高风险边界由代码限制。

**Q82 缺参数/指代追问？** 缺订单号返回 `needs_input=true` 反问；会话内存上下文可复用订单号（30 分钟 TTL，512 会话）。多副本需迁移 Redis。**尚未覆盖**（单实例内存）。

**Q83 8s 超时覆盖整个查询吗？** ✅基本覆盖：意图分类 2s（超时走关键词兜底）+ 润色共享 8s 总预算，各层 `asyncio.wait_for` 可取消内层。httpx 单次 30s 大于预算、依赖外层取消兜底——严格说端到端上界依赖取消正确性。

**Q84 LLM 完全不可用时？** 意图降级关键词、润色降级确定性摘要，三类基础查询仍可用；写入/检测不依赖模型。后端查询接口自身故障则无降级。

**Q85 「8 个场景正确」验证了什么？** 8 个固定中文用例的意图+底层数据检查。不代表任意表达准确率，未覆盖注入语料/错别字/复杂日期/最终措辞。

**Q86 为何不比较最终回答字符串？** 模型措辞随机，字符串相等脆弱。评意图+结构化数据更稳；要评价回答需事实一致性规则或独立评审。

**Q87 智能查询如何鉴权？** JWT 校验签名/过期/`ai:query` 权限；AI 调 Java 用机器密钥（仅读权限），不连数据库不持用户凭证。机器密钥要强随机+网络限制。

**Q88 为什么规则优先模型补充？** 重复支付/状态跳跃/超卖有明确业务定义，规则可解释应优先；IF 用于规则未覆盖的统计异常并降权。桥接失败记指标继续模型检测（故障期明确规则可能漏报）。

**Q89 有哪些检测规则？** 事件级 5 条（金额偏离/重复支付/状态跳跃/高频下单/库存超卖）+ 流程级 3 条（非法迁移/停滞 24h/死循环 5 次）+ HMM P004（序列似然）。阈值来自演示与合成评测。

**Q90 停滞订单会自动告警吗？** 不会——停滞规则只在消费新事件时检查窗口，之后无事件就无触发。评测用旧时间戳事件触发。生产需定时扫描非终态或延迟消息。**尚未覆盖**。

**Q91 HMM 接入实时链路了吗？** ✅2026-08-16 起已接线：`main.py` 构造 `ProcessLevelHMMDetector` 注入检测管道（此前传 None 仅离线）；模型文件缺失自动降级返回空不阻断。线上效果数字待服务器跑 s03 回填。

**Q92 为什么 IF 离线效果反而差？** F1 0.887→0.753，召回不变（0.896，TP 仅+1），FP 176→691。根因 `contamination=0.05` 强制按 5% 判异常与真实分布不符。结论：当前数据与特征下规则是主检测器，模型只能谨慎辅助。

**Q93 P/R/F1/FPR 各说明什么？** P=告警中真异常占比，R=真异常被发现占比，F1 综合，FPR=正常被误报比例。异常治理不能只追召回（耗尽运营注意力），按风险分级设阈值。负结果的教训：只报 F1 不够，要看混淆矩阵。

**Q94 模型缺失/管道启动失败？** IF 缺失使检测管道启动失败但 FastAPI 主服务仍可用（`detector_running=0`）。功能级降级，生产必须对此告警。

**Q95 告警如何到前端？** 检测→`anomaly-alerts` 主题→Java 消费**先落 `anomaly_alerts` 表（V8，重启可查）再广播** WebSocket；前端断线 3s 重连，`GET /alerts/recent?limit=` 从库里补拉按 `anomaly_id` 去重。✅原内存环形缓冲已删除。

**Q96 断线一分钟告警丢吗？** ✅持久化后不再丢：历史在库里，`/alerts/recent` 支持 limit（默认 100，上限 500）。剩余边界：无按时间游标的增量补拉、多实例广播需 Redis。**尚未覆盖（单实例）**。

**Q97 WS 为什么 JWT 放查询参数？** 浏览器 WS API 不便设 Authorization 头。风险：token 入代理/访问日志。握手只校验签名/权限，未查 `token_version`——改密后旧 token 的 WS 到过期前仍有效。**尚未覆盖**（升级：短时 ticket）。

**Q98 根因报告如何约束输出？** 要求 JSON→解析→Pydantic 字段/风险枚举校验→动作白名单→证据事件名核对（存在于真实序列）；失败反馈模型修正一次，仍失败报错，不自动执行。

**Q99 根因分析的幻觉风险？** 证据检查只认英文事件名，中文/金额不严格校验；事件加载失败降级空列表会跳过检查。生产：区分「无事件」与「加载失败」，金额状态字段建立结构化引用。

**Q100 ReAct Agent 能调什么工具？为何限 5 步？** 三个只读工具（状态/事件序列/统计），过程记录前端轨迹；5 步防循环与时延费用。工具白名单/参数/轮数/超时都由代码限制。

**Q101 Agent 证据进最终报告吗？** 未完整串联——Agent 结束后单独调 `RootCauseAnalyzer`，工具证据没整体传入。改进：报告显式引用工具结果。**尚未覆盖**。

**Q102 Agent 能直接退款吗？** 不能。只读工具+白名单建议，执行权在 Java 权限/白名单/审批。这是有意的安全边界。

**Q103 检测出异常但发布 Kafka 连续失败？** ✅已闭环：发布异常使 handler 抛错→有限重试（0.3/0.9s）→DLT 发布成功才提交原 offset；DLT 不可用则保持未提交，重启续试。告警不静默丢。内存 anomaly_store 可选 JSONL 持久化（默认关）。

### 六、Saga 补偿与人工审批（Q104–Q120）

**Q104 什么是 Saga？为何不用一个事务？** 跨服务长事务拆成本地步骤，失败时补偿恢复。退款/库存/通知涉及外部系统，PG 事务回滚不了它们。补偿是新的业务动作不是物理撤销，每步独立审计。

**Q105 两条补偿触发路径？** ①领域事件自动触发：支付重试超限→REFUND+NOTIFY；库存预留失败→MARK_OUT_OF_STOCK+NOTIFY。②AI 根因建议→用户前端提交 Saga。Agent 不自动执行——区分「事件自动触发」与「AI 建议经用户提交」。

**Q106 退款金额为何读事件表而非 order_view？** Saga 与投影是不同消费组，取消事件到达时读模型可能未追上；`OrderCreatedEvent` 必先落库，事件表是事实源。✅2026-08-16 起：金额读取失败或创建事件缺失直接抛异常走重试/DLT，不再退 0 元（此前 0 元会绕过「>100 元需审批」）。

**Q107 哪些动作需要审批？risk=HIGH 决定吗？** 服务端按真实参数判定：冻结订单始终审批、退款>100 元审批；低额退款/通知/标记缺货不审批。模型 risk 字段只展示不信任——防模型把高风险标低。

**Q108 AI 建议的退款会正确进审批吗？** 仍有缺口：前端把建议映射为空参数提交，`RefundAction` 读不到金额按 0 处理，AI 建议链路的大额退款不会自动进审批（自动 Saga 链路会，因为它从事件表带真实金额）。**尚未覆盖**（AI 建议结构化携带金额为升级路径）。

**Q109 Saga 持久化程度？** 实例与步骤在内存 `ConcurrentHashMap`；需审批的步骤随审批单落库，重启由 `SagaRecoveryRunner` 重建。只能恢复「等待审批」状态，不支持多副本（审批请求路由到无实例节点会 FAILED）。**尚未覆盖（明确排除项）**：Saga 实例表+步骤表+租约。

**Q110 补偿步骤失败怎么办？** ✅已修复：`executeStep` 失败/异常→`fail()` 标记 FAILED 并停止，不再推进步骤索引硬走完。

**Q111 为什么曾有「事件显示成功但真实退款失败」？** 曾先写 `CompensationExecutedEvent` 再调外部动作。✅已修复：动作成功后才写完成事件；`RefundAction` 先调 `paymentGateway.refund`。剩余：外部「结果未知」状态仍需对账。

**Q112 退款幂等？** 不严格：`CompensationService.execute` 随机命令编号 + 网关随机 UUID，重投/重复点击会产生新外部请求。**尚未覆盖**：`sagaId + stepId` 稳定幂等键 + 外部请求持久化。

**Q113–Q117（ Saga 流程与评测口径）** Saga 步骤：REFUND/MARK_OUT_OF_STOCK/NOTIFY_DELAY 白名单动作；审批流 `POST /approvals/{id}/approve|reject`；`EG_SAGA_ENABLED=false` 可关。评测（Mock 网关）验证 150 元订单支付重试超限→审批→补偿闭环、库存失败→标记缺货两流程走通——说「两类 Saga 流程验证通过」，不说「真实支付退款成功率」。

**Q118 等审批时重启 vs 步骤执行中重启？** 前者可恢复（审批单+剩余步骤落库）；后者无完整持久化，可能事件已写动作未完成或反之，重启后无法判断是否重试——这是需要步骤状态+幂等键的原因。

**Q119 真实退款超时如何判成败？** 超时=未知状态。先按稳定请求编号向网关查单；网关幂等则同号重试；长期未知进对账/人工。Saga 应有 `UNKNOWN` 状态。Mock 未覆盖此场景。

**Q120 可生产化最小版本？** 按触发事件编号去重（✅原子占位已做）；持久化 Saga/步骤状态（未做）；`sagaId+stepId` 外部幂等键（未做）；区分请求/成功/失败/未知事件（部分）；审批条件更新+真实主体（部分）。

### 七、Java / Spring / 数据库 / Kafka / 模型八股（Q121–Q156）

**Q121 为何 TransactionTemplate 而非 @Transactional？** 冲突后要结束当前事务、新开事务重加载聚合；重试在外层控制，事务边界清晰，不会在已回滚事务里循环。

**Q122 @Transactional 自调用失效？** AOP 代理只拦截外部调用，`this.method()` 不经代理。命令侧显式 TransactionTemplate 避开；投影监听由容器调 Bean，代理生效。

**Q123 Spring 默认对什么回滚？** RuntimeException 和 Error；受检异常需 `rollbackFor`。捕获异常只打日志正常返回=事务被认为成功——这是 Saga 曾忽略失败的机制性危险。

**Q124 事务能覆盖 Kafka offset 吗？** 不能。JDBC 事务管理器只管 DB；offset 由容器独立提交，重投由去重表挡。即使 Kafka 事务也只覆盖 Kafka 内部，带不动 PG 和第三方。

**Q125 单例 Bean 并发？** 单例≠单线程，成员须无状态或线程安全。`OrderCommandHandler` 请求状态全在局部变量，可并发复用。

**Q126 record 用在哪？** 命令参数等不可变值对象，自动访问器/相等性。Java 不可变≠持久化不可变。

**Q127 ThreadLocal 与事务？** 连接与事务资源绑定线程；Mock 回调的独立调度线程是新命令新事务，符合异步语义。

**Q128 HikariCP 为何不盲目调大？** 连接大增 PG 后端进程/内存/切换，库先垮。当前 10 上限是 800MB 容器保守值，调优看池等待/SQL 耗时/副本数。

**Q129 JdbcTemplate 而非 JPA？** 追加/`ON CONFLICT`/版本条件更新/JSONB 需精确控制 SQL 与影响行数；无复杂对象映射需求。代价是手写 SQL 与行映射。

**Q130 PG 默认隔离级别？** READ COMMITTED：语句级快照，同事务两次查询可见不同结果；两写事务可同读版本——靠唯一约束兜竞态。

**Q131 RR 与 SERIALIZABLE？** RR 事务级稳定快照防不可重复读；SERIALIZABLE 检测串行化冲突强制重试。约束仍要保留——它直接表达业务不变量。

**Q132 MVCC？** 多版本行让读不阻塞写；事件表只追加冲突更少。长事务阻碍旧版本清理、复制槽阻碍 WAL 清理——都要监控增长。

**Q133 唯一约束/主键/普通索引？** 主键非空唯一；唯一约束表达候选键不变量；普通索引只加速不防重。项目：`event_id` 主键、`(aggregate_id,event_version)` 唯一、状态索引供查询。

**Q134 复合索引列序？** 最左前缀：查询固定 `aggregate_id` 等值 + `event_version` 排序，该顺序同时服务定位与顺序扫描。

**Q135 JSONB 优缺点？** 异构事件统一存储+可查；类型与必填约束弱、演进要治理。高频稳定字段应投影成读模型列。

**Q136 参数化为何防注入？** `?` 绑定为数据不改变语句结构。表名/列名/排序方向不能绑定——白名单映射。

**Q137 OFFSET 深分页为何慢？** 扫描并丢弃前面行；页边界随更新漂移。游标分页保存 `(updated_at, order_id)` 上页尾键继续扫描。

**Q138 CAP/BASE 落点？** 写侧单 PG 本地事务重一致；到 Kafka/读模型异步传播允许滞后；读己写为特定请求提供有界一致。别用 CAP 简单说选了 AP/CP。

**Q139 2PC/TCC/Saga 区别？** 2PC 协调器强一致但锁贵；TCC 资源显式预留；Saga 本地事务+补偿，吞吐好但有中间状态。本项目外部退款/库存适合 Saga。

**Q140 acks 取值与单 Broker 局限？** 0 不等/1 等 leader/all 等 ISR。单 Broker 副本 1 时 `acks=all` 也无节点冗余——持久化盘+多副本才是可靠。

**Q141 重平衡？** 成员/分区变化重新分配。处理超时被移出组后，已处理未提交的消息会被新实例重处理——靠事件幂等挡。监控重平衡次数与处理时延。

**Q142 重试主题 vs DLT？** 重试主题延迟分级再处理可恢复错误；DLT 隔离终态失败等人工。当前是原地有限重试+DLT；长期依赖外部服务的消费者更适合非阻塞重试主题。

**Q143 WebSocket vs SSE？** WS 全双工适合双向；SSE 单向推送重连简单。告警是单向，SSE 也够；选 WS 为看板交互留空间，代价是握手鉴权/心跳/多实例广播。

**Q144 HS256 vs RS256？** 对称密钥签验同钥（所有验证方可签发）；RS256 私签公验。Java/Python 共享 HS256 方便，服务增多改非对称+轮换。

**Q145 JWT 吊销？** 无状态难吊销。项目用 `token_version`：每请求比对库中版本，改密/全端登出递增。代价每请求一次查询；AI 与 WS 握手未完整同查——吊销语义不统一。**尚未覆盖**。

**Q146 角色与权限为何分开？** 接口校验具体权限（`order:read` 等）而非角色名，便于调整职责。高风险审批还应职责分离（发起人≠批准人）。

**Q147 限流四算法？** 固定窗口简单边界两倍突发；滑动窗口平滑状态多；漏桶整形；令牌桶受控突发。项目单实例内存固定窗口 60/10s——老实承认，标注升级路径。

**Q148 async def 一定快吗？** IO 等待密集才划算；CPU 密集阻塞事件循环。查询用异步 HTTP；Kafka 检测独立线程；推理要线程/进程池。

**Q149 wait_for 超时语义？** 截止时间到取消内部任务抛超时；底层要正确响应取消释放资源。项目润色 8s 预算+分类 2s 子预算。

**Q150 Pydantic 防 hallucination 吗？** 防结构（类型/枚举/白名单），不防事实。事实正确性要结构化证据约束。

**Q151 IF 原理？** 随机切分隔离树，异常路径短易隔离。无标签适合探索，但对分布/特征/contamination 敏感——本项目负结果证明要与基线对照。

**Q152 HMM 假设？** 一阶马尔可夫+观测独立。订单流程受更长历史影响未必满足；不同长度序列的似然不可直接比。✅已接线为第二意见（P004），效果口径待实测。

**Q153 ReAct 工程限制？** 工具白名单/参数模式/轮数/超时/输出长度/权限/审计，不给模型写权限。项目 5 步+只读。

**Q154 Counter/Gauge/Histogram？** 只增计数；可增减瞬时值；桶分布服务端算分位。✅已补 lag Gauge（两端）与 lag 告警；复制槽积压 Gauge 仍缺。

**Q155 P95？** 95% 样本不超过该值。平均被快请求稀释，长尾由锁/池/GC/外部调用造成——P50/P95/P99/最大值/错误率一起看。

**Q156 背压在哪需要？** Debezium 积压→WAL 增长；检测慢→消费 lag；读己写等待放大 DB 压力。用 lag/队列/时延触发限流或降级，不让每层无限排队。

### 八、性能、测试、可观测、部署与安全（Q157–Q185）

**Q157 92.7 怎么算的？** 50 并发稳态 30.5s 完成 2823 组「下单+支付」迭代÷时长。不是 HTTP QPS（每迭代≥2 请求）、创建失败不进分母。当前口径以 30 并发 52.39 为准，92.7 是历史档位。

**Q158 P95 1102ms 含什么？** 从创建订单到支付接口返回（两次 HTTP+两次命令处理），不含异步回调变 PAID、CDC、投影。是写侧业务延迟非完整闭环。

**Q159 错误率 0% 覆盖所有失败吗？** 分母是进入统计的迭代；创建失败/部分客户端异常不在内。严谨口径：全部分母+分阶段统计。说的时候主动交代。

**Q160 一次压测能证明稳定支持 50 并发吗？** 只证明该环境完成过一次稳态。可信容量结论要分级加压（10/25/50/100/200）×多轮×长时间稳压，记录资源与业务指标对齐。

**Q161 为何压测关限流？** 单 IP 60/10s 会先测到限流阈值而非处理能力。前提是报告声明条件；另补一组开限流+多真实 IP 的验证。

**Q162 更可信的容量测试？** 固定环境→预热→逐级升压×3 轮→吞吐/延迟/资源对齐→找拐点→事后核对事件数量/位点/读模型版本确认没以数据错误换吞吐。

**Q163 338 项测试代表什么？** 后端 172（4 skipped 无 Docker）+AI 127+前端 39 的通过数之和；不是覆盖率；Testcontainers 集成测试在 CI（有 Docker）会真跑。

**Q164 84 断言证明什么？** 固定数据与环境下的指定条件；一条断言可能只是状态码。价值在可重复执行，不在数字大。

**Q165 测试分层分工？** 单元：状态机/规则/抽取；集成：真库约束/事务/并发竞态；端到端：跨服务接线。仍缺：快照边界真库测试（✅已有单测）、投影重建、Saga 外部失败、Kafka 数据恢复。

**Q166 Mock 通过≠真实补偿成功？** Mock 网关退款固定成功；评测证明流程串通不证明渠道退款。真实接入要签名/幂等键/超时未知态/对账。

**Q167 混沌实际验证了什么？** PG：重启达 pg_isready+行数一致+命令可写。Kafka：暂停期间可写、恢复后 topic 可访问、✅新增投影按 expectedVersion 追平。AI：延迟时规则兜底。未覆盖：Broker 数据损坏、副本切换、长时间积压。

**Q168 如何升级故障演练？** ✅已部分落地：唯一标识事件→恢复后核对位点/主题/去重/读模型版本，分段计时。还差：多轮分布、容器重建/数据卷损坏场景。

**Q169 有哪些可观测能力？** Java：命令耗时/结果、投影、Saga、告警、回调、限流拒绝；AI：消费/检测/发布/查询/LLM 调用；✅新增两端消费 lag 指标与 lag>1000 告警规则。仍缺：复制槽/WAL 积压、DLT 增长、端到端事件延迟。

**Q170 哪些告警真正触发？** 服务不可达、5xx>5%、主机内存 20%/10% 双档，✅新增 Kafka/AI 消费积压两条。Alertmanager webhook 经 `ALERT_WEBHOOK_URL` 注入指向飞书中继——生产要验证触发→分组→送达→恢复全链路。

**Q171 Kafka/Debezium 还缺什么监控？** 复制槽保留字节、槽活跃、LSN 差、磁盘余量、Debezium 位点推进、DLT 增长、端到端事件延迟。✅lag 已补；其余**尚未覆盖**。

**Q172 进 DLT 后系统该做什么？** 隔离≠成功。✅已有：`POST /admin/dlt/{topic}/replay` 受控重放（剥头原样字符串、幂等表兜底）+ lag 告警。还差：失败原因检索、限速重放、按消费组隔离通道。

**Q173 有完整链路追踪吗？** 没有。有集中日志+业务指标+局部 trace id；无跨服务 OpenTelemetry。要做需 trace context 跨 HTTP/Kafka 传播。**尚未覆盖**。

**Q174 为何 Compose 不是 K8s？** 个人成本验证完整链路，Compose 足够；无多副本调度/自动扩缩容需求。K8s 也不能自动修幂等/恢复/一致性问题。

**Q175 为何不是高可用？** 单宿主机、单 Broker 副本 1、PG 无主从、服务单副本、Kafka 无数据卷。明确说「单机可运行部署」。

**Q176 健康检查与优雅停机程度？** PG/Kafka 基础检查、Java 优雅停机 30s、Compose stop_grace_period。缺：完整业务健康检查、Debezium 位点推进验证、停机实测。

**Q177 RPO/RTO？** pg_dump 保留 14 天在本机；RPO 理论 24h（无自动调度记录）；RTO 未知（没做过空库恢复演练）。备份还缺异地与加密。**尚未覆盖**。

**Q178 ProductionSecurityGuard 保证什么？** `EG_ENV=prod` 时拒绝默认 JWT secret/machine key/通配 WS Origin/关闭命令 ID 强制。残留：`spring.sql.init.mode` 硬编码 always 与 `EG_SQL_INIT_MODE` 存在接线分叉；AuthDataSeeder 每次启动重置演示账号。**尚未覆盖**（部分危险配置守卫）。

**Q179 吊销后 AI/WS 立即失效吗？** 不一定。Java REST 比对 `token_version`；FastAPI 只验签名权限；WS 握手无版本查询；管理员重置/禁用/改角色未统一递增版本。**尚未覆盖**。

**Q180 限流的安全与扩展缺陷？** 单实例内存固定窗口+边界两倍突发；信任 `X-Real-IP`（绕过代理直连可伪造）；AI 路径不经 Java 限流；多副本不共享。生产：可信代理边界+分布式限流+模型接口独立预算。

**Q181 回调防伪造/重放/并发？** 已有：机器密钥+提供方校验+外部单号关联+可选 HMAC（`EG_GATEWAY_CALLBACK_SIGNATURE_REQUIRED`）+稳定命令编号+找不到 gateway_request 拒绝派发。残留：签名默认关、终态更新无条件抢占。

**Q182 网络暴露与密钥管理？** 多端口映射宿主机（含 5432/9092，注明仅 SSH 隧道）；Kafka 明文；默认密钥靠部署者替换。生产：收敛源站端口、内网划分、Kafka 认证加密、密钥管理轮换。

**Q183 WS token 查询参数风险？** 入代理/访问日志。更安全：一次性短时 ticket + 严格 Origin + TLS + 不记完整查询串。

**Q184 CI 与安全门禁缺什么？** ✅2026-08-16 起有 GitHub Actions（三端测试，CI 有 Docker 时 Testcontainers 真跑）。仍缺：覆盖率趋势、依赖/镜像/密钥扫描、静态分析。

**Q185 只加五个测试加什么？** 快照 99–102 边界（✅已有单测，补真库版）、并发相同 commandId（✅已有 advisory lock 单测，补真库）、投影乱序缺口、Saga 外部失败/重复触发/并发审批、Kafka 暂停全链路追平（✅混沌已覆盖）。

### 九、高压场景与故障排查（Q186–Q200）

**Q186 50→200 并发大量 expectedVersion 先看什么？** ✅已缓解原瓶颈：等待不再占 Web 线程（DeferredResult），DB 轮询收敛到共享单线程兜底。仍要看 Hikari 活跃/等待、DB CPU、投影 lag、读己写超时计数。短期限并发+客户端退避；长期容量测试。别先盲目调大连接池（排队转移到 PG）。

**Q187 响应丢失+并发重试同命令？** 顺序重试命中 `command_log`；✅并发重试经事务内 advisory lock 串行化，第二个请求返回首次结果；参数指纹防编号复用到不同参数。

**Q188 快照 100+事件 101 重启会怎样？** ✅已修复：加载从 `event_version > 100` 起回放 101，无跳事件、无版本错乱（有边界测试）。

**Q189 Kafka 暂停 30 分钟？** 写侧可写；复制槽保留 WAL 增长可能撑满磁盘。恢复要核对 Debezium 位点/槽积压/lag/读模型。✅chaos 已补追平断言；30 分钟长时积压场景未验证。

**Q190 Kafka 容器删除消息丢失能自动恢复吗？** 不能。单 Broker 无数据卷；Debezium offset 认为已发布。需人工重置或从事件表回灌——事件库是重建消息链路的事实源。

**Q191 Debezium 重发会重复更新读模型吗？** 投影侧：去重表（✅原子占位）+版本守卫挡住。Saga：✅原子占位去重；Python 告警去重在内存（重启失效会重发一轮，指纹去重缓解）。

**Q192 毒消息一直反序列化失败？** Java 首次+2 次重试→DLT（✅可经 `/admin/dlt/{topic}/replay` 修复后重放）；Python 3 次后 DLT，发布失败不提交 offset。DLT 发布也失败：继续失败告警+暂停分区/长退避，不提交。

**Q193 v3 先到 v2 后到守卫保证正确吗？** 只保证 v2 不覆盖 v3；v2 独有字段可能永久缺失。严格做法：只接受 `currentVersion+1`，缺口暂存/补齐/重放，更新 0 行不标成功。

**Q194 清空 order_view 重放为什么没数据？** ✅`reset()` 已清理该组去重记录，但消费位点不重置就不会重收消息。在线重建正解：新投影表+新命名空间回放后切换。

**Q195 读模型 2s 没追上前端怎么办？** 409≠写失败。前端保留成功结果、提示同步中、退避重查，绝不因 409 重提命令。服务端返回当前/目标版本，集中超时则沿链路排查。

**Q196 意图分类耗时 15s，8s 降级生效吗？** ✅已修：意图分类 2s 子预算，超时走关键词兜底，不会拖到润色阶段才降级。

**Q197 「删除所有订单」会怎样？** 模板执行器无删除能力；注入最多影响分类与措辞。结构化数据独立展示，权限服务端独立校验。

**Q198 补偿事件已写、真实退款失败？** ✅已修复顺序：先外部动作后写完成事件；动作失败 Saga 标记 FAILED 不再包装成功。残留：外部结果未知态需对账。

**Q199 事件重投+两人同时批准/拒绝？** Saga 触发 ✅原子占位去重；审批并发抢占（`WHERE status='PENDING'` 条件更新）**尚未覆盖**；内存步骤索引并发推进有风险。

**Q200 宿主机磁盘损坏怎么恢复？** 备份在本机可能同失；Kafka 无卷。生产：异地/对象存储+加密+定期空库恢复演练；恢复 PG 后以事件表为源重建主题与读模型，按版本/数量/抽样校验。只有演练过才有可信 RPO/RTO。

## 七、面试官连续追问模拟（八个方向）

回答统一四步：业务问题 → 方案与代码路径 → 验证证据 → 主动交代代价与边界。

**模拟一 · 事件溯源**：审计表漂移 vs 事件事实源 → 不是过度设计（追溯是核心需求）但别全系统套用 → 不可变是领域语义（DB 权限未隔离，主动说）→ 快照边界 bug ✅已修（99–102 边界测试）→ 阈值 100 是经验值。翻车点：说「事件永不能改」却讲不出权限方案。

**模拟二 · 幂等与并发**：`command_log` 同事务 → 并发相同编号 ✅advisory lock + 指纹（能讲清实现）→ 唯一约束与前置校验各司其职 → 重试口径：命令 3 次 4 尝试、消费 2 次 3 处理。翻车点：把乐观锁说成行锁；说并发重复「一定成功返回相同结果」而不讲机制。

**模拟三 · CQRS 与读己写**：异步投影窗口 → 读己写是单次写后有界等待非强一致 → ✅通知+兜底轮询+DeferredResult（能画链路）→ 版本守卫防倒退不补缺口 → 无状态事件推进版本 ✅ → 通知单实例、多副本 Redis 是边界。

**模拟四 · Debezium**：双写不原子 → 事件表即 Outbox → 至少一次+编号去重 → Kafka 停机 WAL 涨 → 数据丢失可从事件表重建（无自动流程）→ 2s 恢复口径：✅新断言补齐到投影追平，如实说明分段计时。

**模拟五 · 智能查询安全**：模型不生成 SQL，意图+模板+只读接口 → 注入被限制在文字层 → 8s 预算 ✅分层覆盖 → 8 用例是固定口径非通用准确率 → 模型挂了关键词+摘要兜底。

**模拟六 · Saga 与审批**：跨系统副作用用 Saga → 步骤失败 ✅停止并 FAILED、先动作后事件 ✅ → 重复触发 ✅原子去重 → 审批并发抢占未做（主动认）→ Mock 成功率口径限定。

**模拟七 · 性能容量**：52.39 是业务迭代吞吐非 QPS → 错误率分母主动交代 → p95 1262 是基线不是成果 → 优化先看指标（池等待/DB CPU/投影 lag）不先调参 → ✅读己写已不再是线程瓶颈。

**模拟八 · 生产运维**：不能直接上线（单点/无演练/告警链路待验证）→ 守卫覆盖部分配置（sql.init 接线分叉主动说）→ 吊销不全链路 → 限流固定窗口+IP 信任边界 → RTO 未知无演练。翻车点：把 restart 策略当高可用、把组件启动当告警送达。

## 八、差异化亮点

### 亮点一：做了 Baseline 对照实验，并如实汇报负结果

绝大多数简历写「引入 AI 提升 X%」，追问「不用 AI 是多少」就答不上来。你有完整对照数据，且结论是 AI 更差。话术要点：

> 我原本想的是「规则打底、模型提升」，做完补了 Baseline 对照，发现加了 Isolation Forest 后 F1 从 0.887 掉到 0.753。我第一反应是想调参把数字调好看，但实验的意义是回答「模型有没有用」不是让数字好看。看混淆矩阵发现更有意思的事：两个版本召回完全一样（0.896），模型只多抓 1 个真异常却多 515 个误报——不是「用误报换召回」，是纯制造噪音。根因是 contamination=0.05。学到的是：做算法前先建 Baseline，不然不知道自己在和什么比。

### 亮点二：一致性是被约束和测试钉住的，不是说出来的

> 我讲一致性按「挡什么」讲：唯一约束挡并发版本空洞；command_log 主键挡网络重试重复；原子占位去重挡 at-least-once 重投；版本守卫挡乱序倒退；读己写超时挡把旧数据当成功。五个机制对应五种失败，少一个就有洞。幂等与一致性这两块用 Testcontainers 真起 PG 跑端到端——mock 掉数据库测出来的绿色是假的。

### 亮点三：失败路径是设计过的，且已知上限都有标注

> 我花了不少时间在「出错怎么办」：消费失败重试后进 DLT 且可管理端重放；告警先落库再广播，重启不丢；Saga 重启从待审批单恢复；LLM 超时分层降级；模型缺失意图降级关键词。另一个习惯是把「我知道但故意没做」的写在代码注释里标明上限和升级路径——WebSocket 无心跳、Saga 内存实例——这些是权衡不是遗漏，我知道它们在什么流量下会变成问题。

## 九、演练建议

**四天计划**

- 第 1 天 · 话术：只练 1 分钟和 3 分钟版，录音回听。听两件事：有没有「然后就……」；30 秒内说出「事件溯源」。第二段（写侧）最容易讲飞，卡表。
