# EventGuard 项目配置参数全景清单

> 用途：面试前说明“系统有哪些可调参数、当前怎么配、改了会影响什么”。
>
> 核对日期：2026-08-25。本文按当前仓库代码、`.env`、Compose、前端和运维配置整理；敏感值只标记“已配置/未配置”，不抄录明文。

---

## 1. 先讲清配置的四种来源

EventGuard 的参数不只在一个配置文件里，面试时先说明配置来源和优先级：

| 来源 | 典型内容 | 生效时机 | 说明 |
|---|---|---|---|
| `.env` / 环境变量 | DB、JWT、Provider、限流、演示账号 | 容器启动或进程启动 | 敏感值不进 Git；Compose 会把它注入服务 |
| Spring `application.yml` / `@Value` | 端口、连接池、读己写、DLT、规则阈值 | Java 启动 | 环境变量通常覆盖 YAML；`@Value` 里有显式默认值 |
| Python `Settings` | AI Kafka、检测阈值、超时、模型目录 | AI 进程启动 | `EG_` 前缀映射字段名；未知环境变量被忽略 |
| 数据库/用户配置 | 用户 LLM、角色权限、审批状态 | 运行时读取 | 不需要重建镜像；权限和个人模型按用户隔离 |
| 代码固定常量/构建参数 | 路由、状态列表、分页默认值、ECharts、Vite proxy | 编译/页面加载 | 当前不是外部配置，改动通常需要改代码并发布 |

### 1.1 当前环境摘要

从当前工作区 `.env` 读取到的非敏感配置：

- 数据库：`POSTGRES_DB=eventguard`、`POSTGRES_USER=eventguard`、`DB_URL=jdbc:postgresql://postgres:5432/eventguard`、`DB_USER=eventguard`。
- Kafka：`KAFKA_BOOTSTRAP=kafka:9092`、`EG_KAFKA_BOOTSTRAP=kafka:9092`。
- AI 遗留环境参数仍填有 `EG_LLM_BASE_URL=http://ollama:11434/v1`、`EG_LLM_MODEL=qwen2.5:7b`，但当前 AI 代码按用户从 Java `/internal/users/{uid}/llm-config` 取模型配置，这两个环境变量不是当前用户 AI 请求的事实来源。
- 环境模式：`EG_ENV=demo`、`EG_REQUIRE_COMMAND_ID=false`、`EG_ALLOW_BODY_USER_ID=true`、`EG_SQL_INIT_MODE=always`、`EG_GATEWAY_CALLBACK_SIGNATURE_REQUIRED=false`、`EG_WS_ALLOWED_ORIGINS=*`。
- Provider：支付、库存、通知均为 `mock`。
- `PIP_INDEX_URL=https://pypi.org/simple`。
- `EG_JWT_SECRET`、`EG_MACHINE_API_KEY`、数据库密码、API key 等敏感变量已配置但本文不展示；`EG_GATEWAY_CALLBACK_SECRET` 与 `TUNNEL_TOKEN` 当前为空。
- `EG_SAGA_ENABLED` 未在当前 `.env` 显式设置，Compose/代码默认启用 Saga。

### 1.2 面试中的“当前值/默认值”标记

- **当前已配置**：当前 `.env` 或 Compose 明确注入，线上/本地启动会读到。
- **默认生效**：没有显式覆盖时由代码或 Compose 使用。
- **可配置但当前未配置**：代码支持，当前为空/未设置，使用降级或 Mock。
- **代码固定**：存在可调意图，但当前没有环境变量入口。
- **遗留/不生效**：文件里还留着，但当前调用链不再读取，不能把它当成有效运行配置。

## 2. 后端参数（Java/Spring Boot）

### 2.1 服务、数据库和连接池

| 参数 | 当前/默认值 | 来源 | 作用与面试解释 |
|---|---:|---|---|
| `server.port` | `8080` | `application.yml` | Java REST、WebSocket 服务端口；Nginx/Compose 反代到此端口 |
| `spring.application.name` | `eventguard-server` | `application.yml` | Spring 应用名，也是 Micrometer 指标标签 |
| `spring.shutdown` | `graceful` | `application.yml` | 优雅停机，先停止新请求，给在途请求时间 |
| `spring.lifecycle.timeout-per-shutdown-phase` | `30s` | `application.yml` | Spring 生命周期阶段最多等待 30 秒；Compose stop grace 为 35 秒 |
| `DB_URL` | 当前 `jdbc:postgresql://postgres:5432/eventguard` | `.env` | 主命令/查询数据源连接 PostgreSQL |
| `DB_USER` | 当前 `eventguard` | `.env` | 数据库用户 |
| `DB_PASSWORD` | 已配置，敏感值不展示 | `.env` | 数据库密码 |
| `spring.datasource.hikari.maximum-pool-size` | `8` | `application.yml` | 命令/查询连接池上限；小机器上避免连接数挤占内存 |
| `spring.datasource.hikari.minimum-idle` | `2` | `application.yml` | 连接池最小空闲连接 |
| `spring.datasource.hikari.connection-timeout` | `30000ms` | `application.yml` | 获取连接最长等待时间 |
| `spring.datasource.hikari.validation-timeout` | `5000ms` | `application.yml` | 连接校验超时 |
| `spring.datasource.hikari.max-lifetime` | `1800000ms` | `application.yml` | 连接最大生命周期，避免长连接失效 |
| `eventguard.projection-datasource.*` | 独立池：上限 `2`、最小空闲 `1` | `application.yml` | Kafka 投影使用独立数据源，避免投影阻塞命令读写 |
| `EG_LOCAL_DB_URL` | 默认 `jdbc:postgresql://localhost:5432/eventguard` | `application-local.yml` | IDEA 本地 profile 的数据库地址 |
| `EG_LOCAL_DB_USER` / `EG_LOCAL_DB_PASSWORD` | `eventguard` / `changeme` | `application-local.yml` | IDEA 本地数据库认证 |

**配置关系**：线上容器使用 `DB_URL/DB_USER/DB_PASSWORD`；IDEA profile 使用 `EG_LOCAL_*`，避免把容器内 `postgres` 主机名误用于宿主机进程。

### 2.2 Kafka 与 CDC 消费

| 参数 | 当前/默认值 | 来源 | 作用 |
|---|---:|---|---|
| `KAFKA_BOOTSTRAP` | `kafka:9092` | `.env`/`application.yml` | Java Kafka bootstrap 地址 |
| `spring.kafka.consumer.group-id` | `debug-consumer` | `application.yml` | 通用默认消费组；业务监听器通常在 `@KafkaListener` 上显式指定组 |
| `spring.kafka.consumer.auto-offset-reset` | `earliest` | `application.yml` | 没有历史位点时从最早消息消费，便于投影重建/演示 |
| `key/value-deserializer` | String/String | `application.yml` | Debezium 输出纯 JSON 字符串，不能误用 JsonDeserializer |
| `EG_PROJECTION_CONCURRENCY` | Compose 默认 `3` | Compose | 投影消费者并发度；提高吞吐也会增加数据库竞争 |
| `KAFKA_NUM_PARTITIONS` | `3` | Compose Kafka | 单节点 Kafka topic 默认分区数 |
| Kafka 副本/ISR | `1/1` | Compose Kafka | 当前单节点演示，不是高可用副本配置 |
| `KAFKA_HEAP_OPTS` | `-Xms256m -Xmx512m` | Compose | Kafka JVM 堆上限 |
| `EG_LOCAL_KAFKA_BOOTSTRAP` | `localhost:9092` | `application-local.yml` | IDEA 运行时的 Kafka 地址 |
| `EG_LOCAL_KAFKA_LISTENER_ENABLED` | `false` | `application-local.yml` | IDEA 默认关闭 Kafka listener，避免容器 hostname 无法解析；要本地跑消费链路需改为 `true` |

**Debezium 固定参数**（`debezium/conf/application.properties`）：

- PostgreSQL connector：`pgoutput`、`public.domain_events`、publication `dbz_publication`。
- topic prefix：`eventguard`；SMT 把 topic 重写为 `domain-events`。
- Kafka sink：`kafka:9092`，Key/Value 都是 StringSerializer。
- `aggregate_id` 提升为 Kafka key，保证同一订单事件进入同一分区并尽量保持顺序。
- offset 文件：`/debezium/data/offsets.dat`，由 `debezium-data` 卷持久化。
- 删除 tombstone、unwrap CDC envelope、保留 `op/ts_ms` source 字段。

这些不是用户业务参数，但决定“PostgreSQL 事实事件如何变成 Kafka 事件”，面试中应与 `KAFKA_BOOTSTRAP` 一起讲。

角色默认权限：`ADMIN=全部`；`OPERATOR=订单读/建/写+异常+AI+补偿`；`VIEWER=订单读+异常查看+AI 查询`。角色与用户关联实际保存在 `auth_user_role`、`auth_role_permission`。

### 3.3 用户级 LLM 配置（数据库运行时配置）

这是当前 AI 功能的实际模型来源，存储表 `user_llm_config`，前端路径 `/profile`：

| 字段 | UI 约束/默认 | 存储/作用 |
|---|---:|---|

| `base_url` | 必须 `http://` 或 `https://` | `/v1/chat/completions` 或 `/v1/messages` 地址 |

### 3.5 AI 固定/降级行为

- 没有用户 LLM 配置：NL 查询仍可走关键词意图和数据摘要；根因、深度分析、周报、订单故事返回 409。
- LLM 单次超时：NL 查询返回规则摘要；分析类端点返回 504。
- Isolation Forest 模型缺失：预测接口返回 `prediction=null`；不会伪造置信度。
- Python AI 启动检测管道失败：API 仍启动，但 `/health` 的 detector running 为 false，事件消费告警链路暂停。
- AI 不直连 PostgreSQL；所有业务读取经 `BackendClient` + Java 机器密钥完成。

## 7. 枚举类与有限值域

### 7.1 先区分四种“枚举”

本项目只有 4 个 Java 语言级 `enum`，但系统中的有限值远不止 4 组。面试时应按约束强度分层说明：

| 类型 | 约束方式 | 本项目示例 | 失配后果 |
|---|---|---|---|
| 语言级枚举 | Java 编译期类型检查 | `OrderStatus`、`SagaStatus` | 非法值无法编译，数据库脏值会在 `valueOf` 时失败 |
| 模型/类型枚举 | Python `Literal`、TypeScript union、模型标签文件 | 风险等级、LLM Provider、预测终局 | Python 部分有 Pydantic 校验；TypeScript 只约束编译期 |
| 协议枚举 | Java/Python/Vue 共同约定字符串 | `event_type`、补偿动作、异常来源 | 拼写不一致会造成反序列化失败、分支不命中或页面显示异常 |
| 配置枚举 | 环境变量或 CLI 的有限候选值 | `EG_ENV`、Gateway Provider、`BENCH_SUITES` | Spring 条件 Bean 可能缺失，或程序回退到默认行为 |

数据库中的 `status/type/source/level` 多数是 `VARCHAR/TEXT`，目前没有 PostgreSQL `ENUM` 或 `CHECK` 约束。因此“合法值”主要由应用层保证，写库脚本、跨服务消息和手工 SQL 都可能绕过约束。本章列的是代码实际识别的有限值，不把 HTTP 状态码、URL、任意用户名、模型名、自由文本等开放值域算作项目枚举。

### 7.2 Java 语言级枚举总表

| 枚举类 | 值 | 用途与持久化位置 |
|---|---|---|
| `OrderStatus` | `PENDING_PAYMENT`、`PAYMENT_FAILED`、`PAID`、`CONFIRMED`、`SHIPPED`、`DELIVERED`、`CLOSED`、`CANCELLED`、`REFUNDED` | 订单聚合状态机；投影为 `order_view.status`，前端列表和 AI 查询也使用同名字符串 |
| `SagaStatus` | `STARTED`、`AWAITING_APPROVAL`、`EXECUTING`、`COMPLETED`、`FAILED` | 补偿 Saga 的内存状态和 API 返回值；当前不单独持久化 Saga 实例 |
| `AnomalyLevel` | `INFO`、`WARN`、`ERROR` | Java 规则引擎响应中的声明严重度；当前 Python 桥接没有原样传到最终告警 |
| `GatewayRequest.Status` | `PENDING`、`SUCCEEDED`、`FAILED` | 网关出站请求状态，持久化到 `gateway_request.status` |

源码位置分别是 `command/aggregate/OrderStatus.java`、`compensation/saga/SagaStatus.java`、`anomaly/model/AnomalyLevel.java` 和 `gateway/model/GatewayRequest.java`。

### 7.3 订单状态 `OrderStatus`

| 值 | 业务含义 | 主要进入方式 | 后续约束 |
|---|---|---|---|
| `PENDING_PAYMENT` | 已创建、待支付；发起异步支付后仍保持该状态 | `OrderCreatedEvent`、`PaymentRetriedEvent` | 可支付、记支付失败或取消 |
| `PAYMENT_FAILED` | 支付失败，允许重试 | `PaymentFailedEvent` | 重试回待支付；累计重试超过 3 次自动取消 |
| `PAID` | 支付已完成 | `PaymentCompletedEvent` | 可预留库存、确认、退款或取消 |
| `CONFIRMED` | 商家/系统已确认订单 | `OrderConfirmedEvent` | 可发货、退款或取消 |
| `SHIPPED` | 已发货 | `ShippedEvent` | 可确认送达；聚合根仍允许取消，因为只禁止关闭/已取消状态取消 |
| `DELIVERED` | 已送达 | `DeliveredEvent` | 可关闭；聚合根仍允许取消 |
| `CLOSED` | 正常履约结束 | `OrderClosedEvent` | 终态，不允许取消 |
| `CANCELLED` | 订单取消或支付重试超限 | `OrderCancelledEvent` | 终态，不允许再次取消 |
| `REFUNDED` | 已退款 | `OrderRefundedEvent` | 业务/预测终局标签；不能关闭，但当前取消命令的 guard 仍允许从该状态取消 |

主链路是 `null -> PENDING_PAYMENT -> PAID -> CONFIRMED -> SHIPPED -> DELIVERED -> CLOSED`。`PaymentRequestedEvent`、库存预留成功/失败、退款请求意图和补偿执行事件只留痕，不改变订单状态。当前 `CancelOrderCommand` 只禁止 `CLOSED/CANCELLED`，因此 `SHIPPED`、`DELIVERED`、`REFUNDED` 也能转为 `CANCELLED`；这是代码真实边界，若业务希望退款成为严格终态，应收紧聚合根 guard。前端 `OrderList.vue` 的筛选值、Python `template_executor.py` 的中文状态提取、预测特征映射都必须与这 9 个值一致。

### 7.4 Saga、审批与网关状态

**Saga 状态**

| 值 | 含义 |
|---|---|
| `STARTED` | Saga 实例刚创建的瞬时初态 |
| `EXECUTING` | 正按顺序执行补偿步骤 |
| `AWAITING_APPROVAL` | 当前高风险步骤已落审批单，Saga 暂停 |
| `COMPLETED` | 所有步骤成功，内存实例随即删除 |
| `FAILED` | 步骤异常、返回失败、审批拒绝或恢复失败 |

**审批状态 `compensation_approval.status`**

| 值 | 含义 | 可迁移到 |
|---|---|---|
| `PENDING` | 等待人工决策 | `APPROVED` 或 `REJECTED` |
| `APPROVED` | 审批通过，Saga 执行当前步骤并继续 | 终态 |
| `REJECTED` | 审批拒绝，Saga 转 `FAILED` | 终态 |

`requested_by` 的建表注释写的是 `agent/human`，但当前自动 Saga 实际写入 `saga`；`decided_by` 是当前登录用户名，不是封闭枚举。这是“设计注释与实现不一致”，面试时应如实说明，不能把 `agent/human` 当成数据库强约束。

**网关请求状态 `GatewayRequest.Status`**

| 值 | 含义 |
|---|---|
| `PENDING` | 请求已落库、等待支付网关异步回调 |
| `SUCCEEDED` | 回调成功；终态，重复回调幂等跳过 |
| `FAILED` | 发起或回调失败；终态，重复回调幂等跳过 |

支付接口自身的 `PayResponse.status` 是另一组协议值：`PAYMENT_REQUESTED` 表示发起成功、等待回调，`PAYMENT_FAILED` 表示命令或网关发起失败。它不要与订单的 `PAYMENT_FAILED`、网关记录的 `FAILED` 混为一谈。

### 7.5 聚合、命令与领域事件类型

当前系统只有一个聚合类型：`aggregate_type=Order`。命令日志的 `command_type` 取 Java 类简单名：

| 命令类型 | 含义 |
|---|---|
| `CreateOrderCommand` | 创建订单 |
| `PayOrderCommand` | 记录支付意图并调用支付网关 |
| `CompletePaymentCommand` | 网关成功回调后确认支付完成 |
| `FailPaymentCommand` | 记录支付失败 |
| `RetryPaymentCommand` | 从支付失败状态重试 |
| `ReserveInventoryCommand` | 预留库存 |
| `ConfirmOrderCommand` | 确认订单 |
| `ShipOrderCommand` | 发货 |
| `DeliverOrderCommand` | 确认送达 |
| `CloseOrderCommand` | 关闭已送达订单 |
| `CancelOrderCommand` | 取消非关闭、非已取消订单 |
| `RefundOrderCommand` | 对已支付/已确认订单退款 |

`domain_events.event_type`、Kafka 消息和 `EventDeserializer` 共同识别以下 15 种事件：

| 事件类型 | 含义 | 是否改变订单状态 |
|---|---|---|
| `OrderCreatedEvent` | 订单创建 | 是，变为 `PENDING_PAYMENT` |
| `PaymentRequestedEvent` | 已发起异步支付 | 否 |
| `PaymentCompletedEvent` | 支付成功 | 是，变为 `PAID` |
| `PaymentFailedEvent` | 支付失败 | 是，变为 `PAYMENT_FAILED` |
| `PaymentRetriedEvent` | 支付重试 | 是，回到 `PENDING_PAYMENT` |
| `InventoryReservedEvent` | 库存预留成功 | 否，保持 `PAID` |
| `InventoryReservationFailedEvent` | 库存预留失败，供 R005/Saga 处理 | 否，保持 `PAID` |
| `OrderConfirmedEvent` | 订单确认 | 是，变为 `CONFIRMED` |
| `ShippedEvent` | 发货并记录运单号 | 是，变为 `SHIPPED` |
| `DeliveredEvent` | 已送达 | 是，变为 `DELIVERED` |
| `OrderClosedEvent` | 正常关闭 | 是，变为 `CLOSED` |
| `OrderCancelledEvent` | 取消订单 | 是，变为 `CANCELLED` |
| `OrderRefundRequestedEvent` | 退款意图已发起 | 否，保持 `PAID` |
| `OrderRefundedEvent` | 退款完成 | 是，变为 `REFUNDED` |
| `CompensationExecutedEvent` | 补偿动作执行留痕 | 否 |

这里的类名字符串就是事件协议。新增事件必须同时修改事件类、聚合 `apply`、`EventDeserializer`、读模型投影、Java/Python 状态迁移、AI 特征词表、测试和文档；只新增 Java 类并不足以让 CDC 消费链路识别它。

### 7.6 异常等级、来源、优先级与规则 ID

异常协议有三个独立维度：

| 字段 | 合法值 | 含义 |
|---|---|---|
| `level` | `INFO`、`WARN`、`ERROR` | 对外告警严重度；前端按它决定标签颜色，当前内置链路实际主要产生 `WARN/ERROR` |
| `source` | `RULE`、`IF`、`PROCESS` | 检测来源：Java 规则、Isolation Forest、流程检测 |
| `priority` | `HIGH`、`LOW` | AI 协同检测的处置优先级；规则命中为高、IF 为低，流程规则按实现指定 |

`AnomalyResult.level` 中的 `HIGH/LOW` 实际表示内部优先级，转成最终 `Anomaly` 时映射为 `HIGH -> ERROR`、`LOW -> WARN`；最终对象的 `level` 才是 `INFO/WARN/ERROR`。这是当前命名上的历史包袱。还有一层实现差异：Java `RuleEngine` 返回了每条规则声明的 `AnomalyLevel`，但 Python `RuleBridge` 当前忽略响应中的 `level`，将任何 Java 规则命中统一构造成 `HIGH`，所以 R001/R004 虽声明 `WARN`，经完整 AI 发布链路后仍会成为 `ERROR/HIGH`。面试时应把“Java 规则元数据”和“最终 Kafka 告警”分开说明。

**Java 事件级规则**

| 规则 ID | Java 声明严重度 | 含义/阈值 |
|---|---|---|
| `R001` | `WARN` | 订单金额偏离用户均值超过 `sigma * std`，默认 `3σ` |
| `R002` | `ERROR` | 同一订单 5 分钟内重复出现支付完成事件 |
| `R003` | `ERROR` | 事件对应的前序订单状态不在合法集合中 |
| `R004` | `WARN` | 同一用户 1 分钟内创建订单达到 20 次阈值 |
| `R005` | `ERROR` | 库存预留量超过实际库存，或直接出现预留失败事件 |

**Python 流程级规则**

| 规则 ID | 严重度/优先级 | 含义 |
|---|---|---|
| `P001_ILLEGAL_TRANSITION` | `ERROR/HIGH` | 滑动事件窗口内出现非法状态迁移 |
| `P002_STUCK` | `WARN/HIGH` | 非终态订单超过配置时长没有后续事件 |
| `P003_DEAD_LOOP` | `ERROR/HIGH` | `PaymentRetriedEvent` 次数超过死循环阈值 |
| `P004_HMM_LOW_LIKELIHOOD` | `WARN/LOW` | HMM 对整个事件序列给出的似然低于训练阈值 |

IF 异常没有固定业务规则 ID，落最终告警时以来源 `IF` 兜底。规则 ID 会进入 Kafka 告警、数据库历史、Prometheus label、WebSocket 和前端聚合键，因此它也是稳定协议标识。

### 7.7 补偿动作与风险等级

`AnalysisReport` 用白名单拒绝 LLM 生成的任意动作；Java `CompensationActionRegistry` 也只注册相同 5 类动作：

| `actionType` | 默认风险 | 审批规则 | 实际动作 |
|---|---|---|---|
| `REFUND` | `MEDIUM` | 金额大于 100 时审批 | 调支付 Provider 发起退款 |
| `NOTIFY_DELAY` | `LOW` | 不审批 | 发送订单延迟通知 |
| `MARK_OUT_OF_STOCK` | `LOW` | 不审批 | 把指定 SKU 标记为缺货 |
| `FREEZE_ORDER` | `HIGH` | 恒需审批 | 冻结订单；当前实现主要返回执行结果，未形成独立订单状态 |
| `BACKOFF_AND_STOP` | `LOW` | 不审批 | 停止重试；当前实现主要返回执行结果 |

风险枚举为 `LOW/MEDIUM/HIGH`，也是前端 `ai.ts` 的 TypeScript union。它既用于补偿建议风险，也用于预测结果风险：不能与异常的二值 `priority=HIGH/LOW` 完全等同。

### 7.8 AI 查询意图与预测标签

**自然语言查询意图**

| 值 | 含义 | 执行路径 |
|---|---|---|
| `event_lookup` | 查询某订单当前状态/详情 | 提取订单 ID，查询订单读模型 |
| `stats_aggregation` | 按状态、时间做数量和金额聚合 | 调订单统计接口 |
| `trace_replay` | 查询事件历史、时间线或状态变更 | 调事件轨迹接口 |

分类先请求用户配置的 LLM，只接受以上标签；非法输出或调用失败时走关键词规则，仍无法判断则默认 `event_lookup`。

**订单终局预测模型标签**

| 标签 | 含义 | 风险映射 |
|---|---|---|
| `CLOSED` | 预测正常履约关闭 | `LOW` |
| `CANCELLED` | 预测最终取消 | `MEDIUM` |
| `REFUNDED` | 预测最终退款 | `MEDIUM` |
| `STUCK` | 预测长期停滞 | `HIGH` |

标签顺序和数字编码来自 `models/predictor_meta.json`，不是 Java 枚举。模型置信度低于 `0.45` 时，代码把风险强制降为 `LOW`；新增/重排标签必须与训练模型 `classes_`、元数据和风险映射一起发布。

### 7.9 RBAC 角色、权限与审计动作

内置角色是启动种子数据，不是 Java enum；管理员可在数据库中创建其他角色，所以它属于“当前预置集合”而不是永远封闭的枚举：

| 角色码 | 默认权限范围 |
|---|---|
| `ADMIN` | 全部 9 项权限 |
| `OPERATOR` | 订单读/建/写、异常查看、AI 查询、补偿执行 |
| `VIEWER` | 订单只读、异常查看、AI 查询 |

权限目录由 `AuthDataSeeder.PERMISSIONS` 定义：`order:read`、`order:create`、`order:write`、`anomaly:view`、`ai:query`、`compensation:execute`、`user:manage`、`role:manage`、`anomaly:evaluate`。其中机器 API 主体固定只有 `order:read`、`anomaly:evaluate`、`compensation:execute`。

审计日志 `action` 当前写入以下动作码：

| 分类 | 动作码 | 含义 |
|---|---|---|
| 登录会话 | `LOGIN_OK`、`LOGIN_FAILED`、`LOGOUT`、`LOGOUT_ALL` | 登录成功/失败、当前设备退出、全部设备退出 |
| 密码 | `PASSWORD_CHANGE` | 用户修改自己的密码 |
| 用户管理 | `USER_CREATE`、`USER_UPDATE`、`USER_RESET_PASSWORD`、`USER_DELETE` | 管理员的用户 CRUD/重置密码操作 |
| 角色管理 | `ROLE_CREATE`、`ROLE_UPDATE`、`ROLE_DELETE` | 管理员的角色 CRUD 操作 |

`auth_audit_log.action` 只是 `VARCHAR(64)`，新增管理操作时应统一定义动作码，否则后台筛选和审计统计会出现同义不同名。

### 7.10 Gateway 与通知协议值

| 字段 | 当前代码实际值 | 设计预留/说明 |
|---|---|---|
| `gateway_type` | `PAYMENT` | 表注释预留 `INVENTORY`、`NOTIFICATION`；当前只有支付协调器创建 `gateway_request` |
| `request_type` | `CREATE_PAYMENT` | 表注释预留 `CAPTURE`、`REFUND`、`RESERVE`、`NOTIFY`；当前网关请求表只落支付创建 |

### 7.12 Kafka 固定协议标识

以下值严格说是部署拓扑标识，不是业务枚举，但改名需要生产者、消费者、监控和重放链路同步，面试时适合与协议枚举一起讲：

| 类型 | 当前值 | 作用 |
|---|---|---|
| 主事件 topic | `domain-events` | Debezium 将 `domain_events` CDC 统一重写到此 topic |
| 告警 topic | `anomaly-alerts` | Python 发布异常，Java 消费后存历史并推 WebSocket |
| Java 投影 group | `order-view-projection` | 独立构建 `order_view` |
| 投影幂等 consumer key | `order-view` | 写入 `idempotent_consumers.consumer_group`，与 Kafka group 名不同 |
| Java Saga group | `saga-trigger` | 独立消费失败事件并启动补偿 |
| Python 检测 group | `ai-event-detector` | 规则 + IF + 流程检测 |
| Java告警推送 group | `anomaly-ws` | 消费告警并广播到前端 |
| 死信/隔离 topic | `<topic>.DLT`、`<topic>.DLT.quarantine` | 有限重试后进 DLT，超过重放上限再隔离毒消息 |

不同职责必须使用不同 consumer group，才能让同一事件分别到达投影、Saga 和 AI；同职责多实例共享同一 group，才能分摊分区而不重复处理。

### 7.13 前端有限显示模式

| 页面/字段 | 值 | 性质 |
|---|---|---|
| 异常看板模式 | `明细模式`、`聚合模式` | 实际由 `aggregateMode: boolean` 控制，不是后端领域枚举 |
| NL 对话消息角色 | `user`、`assistant` | TypeScript union，决定消息左右布局和渲染方式 |
| Element Plus 状态标签类型 | `success`、`info`、`warning`、`danger`、`primary` | 纯 UI 颜色语义，由订单/异常状态映射得到，不写入后端 |

这类值只影响展示，不应写回领域状态。面试时可以借此说明“UI 枚举、协议枚举和业务状态机是三层不同职责”。

### 7.14 新增枚举值的同步检查表

1. 新订单状态：同步 `OrderStatus`、聚合命令校验和 `apply`、读模型投影、列表筛选、NL 状态解析、流程检测迁移表、预测特征和测试。
2. 新领域事件：同步事件类、序列化 payload、`EventDeserializer`、CDC 消费者、投影、AI 事件词表/HMM 词表、监控标签和回放测试。
3. 新补偿动作：同步 Java Action Bean/Registry、Python `ALLOWED_ACTIONS` 与提示词、审批风险规则、前端选项和 Saga 测试。
4. 新异常来源/等级/规则：同步 Java/Python DTO、`anomaly-alerts` 契约、数据库查询、Prometheus label、WebSocket、前端颜色/聚合和评测预期。
5. 新 Provider：必须同时提供条件 Bean、配置校验、凭证参数、健康检查和部署配置；仅在注释或 `.env` 中增加候选值不会自动获得实现。
6. 对长期稳定字段可考虑增加数据库 `CHECK` 或共享契约测试；在此之前，至少保证 API 入参白名单校验，避免非法字符串落库后在消费者侧才失败。

## 10. 面试中最值得主动讲的配置取舍

1. **配置分层**：环境变量放部署差异和密钥，Spring/Python 放服务默认，数据库放用户运行时配置，代码常量只保留真正稳定的 UI/协议约束。
2. **安全默认**：当前 demo 为了体验保留 `EG_ENV=demo`、Mock Provider、宽松 WS origin、可选 command id；生产保护器会要求收紧这些开关。
3. **用户级 LLM**：从进程级单模型升级为 `user_llm_config`，API key AES 加密、接口掩码、AI 机器主体按 uid 取配置。
4. **可演示故障**：支付失败率、支付延迟、库存种子是受控注入参数，可以复现 `PAYMENT_FAILED`、异步回调、库存不足和 Saga 补偿。
5. **资源上限**：Compose 同时限制 JVM heap、容器内存和日志轮转，适配当前单机演示；多副本生产还需要 Redis、共享 Saga、共享 WS 广播和更高 Kafka 副本数。
6. **遗留配置识别**：`.env` 里还存在 `EG_LLM_*`，但当前 AI `Settings` 已不读取；配置盘点不能只 grep 文件，必须沿调用链确认是否生效。

## 11. 一分钟配置总结话术

> EventGuard 的配置分四层：Java 后端负责数据库、Kafka、连接池、JWT/RBAC、限流、读己写、DLT、网关 Provider 和 Saga；Python AI 负责事件消费组、规则阈值、模型目录、LLM 并发/重试/超时和降级；前端 Vite 负责 API base URL、开发代理、路由和页面默认参数；Compose/运维负责 PostgreSQL logical replication、Kafka 单节点资源、Debezium、Prometheus、Alertmanager、Grafana、Loki 和 Tunnel。当前演示环境使用 Mock Provider、demo 安全模式、单节点 Kafka、用户级 LLM 配置和挂载模型目录。面试时我会特别区分“环境变量里写了什么”和“调用链真正读取什么”，例如旧的 `EG_LLM_*` 仍在 `.env`，但当前 AI 实际按用户从 Java 数据库取 LLM 配置；这比单纯罗列配置文件更能说明系统设计和排障能力。
