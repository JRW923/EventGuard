# EventGuard 数据库表全景

> 用途：面试前快速掌握全部 16 张表的结构、含义和设计动机；被问"数据库有几张表/表怎么设计的"时直接使用。
>
> 核对日期：2026-08-29。唯一可信来源为 Flyway 迁移脚本 `eventguard-server/src/main/resources/db/migration/V1-V9`（新装库从零执行）与 `postgres-init/00-schema.sql`（Docker 初始化，内容与 V1/V2 一致，供 `01-logical.sql` 建 publication）。本文所有字段与索引均逐行核对过 SQL 原文。
>
> 各表「一行示例」为按代码真实写入路径构造的演示数据（非生产导出）：字段名、取值格式与代码写入一致，关联表共享同一条订单链路（订单 `3f2c1a4b-…`），便于对照看数据怎么流转。各表「取值受限字段」与《项目配置参数全景清单.md》第 7 章（枚举类与有限值域）同源核对。

## 1. 一图速览

```text
事件溯源与一致性（命令侧/消费者共用）
  domain_events（唯一事实源，CDC 源） aggregate_snapshots command_log idempotent_consumers
查询读模型（CQRS 查询端）
  order_view
认证与授权（RBAC）
  auth_user auth_role auth_permission auth_user_role auth_role_permission auth_audit_log
网关与 Saga 补偿
  gateway_request notification_log compensation_approval
AI 异常与用户配置
  anomaly_alerts user_llm_config
```

两张关键关系图：

- **CDC 范围**：`CREATE PUBLICATION dbz_publication FOR TABLE domain_events` —— 只有 `domain_events` 进 Debezium；其余 15 张表都是普通表，各自由所属服务直接读写（V3/V4/V9 注释中明确"无需 CDC"）。
- **谁写谁读**：

  | 表 | 谁写 | 谁读 |
  |---|---|---|
  | domain_events | 命令侧 Java | 命令回放、前端时间线、风控规则；Debezium 搬进 Kafka |
  | aggregate_snapshots | 命令侧 | 命令侧（回放的起点） |
  | command_log | 命令侧 | 命令侧（防止重复执行） |
  | order_view | 投影消费者 | 前端订单页、AI 查询 |
  | idempotent_consumers | 消费者 | 消费者自己（防止重复消费） |
  | gateway_request | 发支付时写，回调时改 | 回调靠它找回订单 |
  | notification_log | 通知网关 | 目前没人读（纯留痕） |
  | compensation_approval | Saga 写，审批接口改 | 前端审批页 |
  | anomaly_alerts | Java 告警消费者 | 前端异常看板 |
  | auth 五张表 | 启动种子 + 管理页操作 | 登录和鉴权 |
  | auth_audit_log | 登录等安全操作 | 管理员审计页 |
  | user_llm_config | 用户在个人中心保存 | AI（经 Java 转交） |

  记住三句话：① domain_events 有两条读路——直接查库（查历史）和 Kafka 消费（实时流）；② Python AI 不碰数据库，读走 Java 接口、写只发 Kafka；③ notification_log 目前只写不读（原描述"AI 根因分析能查它"是设计意图，当前实现尚未接）。

## 2. 事件溯源与一致性

### 2.1 domain_events —— 事件表（唯一事实源，append-only）

来源：V1。这是全系统最重要的一张表，Debezium 只 CDC 它。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| event_id | UUID PK | 事件全局唯一 ID，也是下游幂等键 |
| aggregate_id | UUID | 聚合根 ID（当前系统即订单 ID） |
| aggregate_type | VARCHAR(64) | 聚合类型（当前唯一值为 Order，EventStoreJdbcImpl 硬编码常量） |
| event_type | VARCHAR(128) | 事件类型（如 OrderCreated） |
| event_version | INT | 聚合内版本号，单调递增 |
| payload | JSONB NOT NULL | 事件业务数据 |
| metadata | JSONB | 附加信息（trace、操作者等） |
| created_at | TIMESTAMPTZ | 事件发生时间 |

取值受限字段：

- `aggregate_type`：唯一值 `Order`（当前系统只有订单一个聚合根）。
- `event_type`：15 种事件类名，是消费链路的协议值——OrderCreatedEvent / PaymentRequestedEvent / PaymentCompletedEvent / PaymentFailedEvent / PaymentRetriedEvent / InventoryReservedEvent / InventoryReservationFailedEvent / OrderConfirmedEvent / ShippedEvent / DeliveredEvent / OrderClosedEvent / OrderCancelledEvent / OrderRefundRequestedEvent / OrderRefundedEvent / CompensationExecutedEvent；其中 PaymentRequested、库存预留成功/失败、退款意图、补偿执行这 5 类只留痕、不改订单状态。

关键约束与索引：`UNIQUE (aggregate_id, event_version)` —— **同一聚合同一版本只能有一个事件**，这是并发写事件的最终防线（乐观锁落库）；另有 `(aggregate_id, event_version)` 复合索引（回放）、payload/metadata 的 GIN 索引（V6，支撑 AI/时间线的 JSON 条件查询）。

面试讲法：append-only，任何人都不 UPDATE/DELETE；读模型坏了可以靠它全量回放重建。

一行示例（订单创建事件）：

```json
{
  "event_id": "5f0c9a2e-8f3b-4c1d-9a7e-2b6d8e4f1a3c",
  "aggregate_id": "3f2c1a4b-9d5e-4f6a-8b7c-1d2e3f4a5b6c",
  "aggregate_type": "Order",
  "event_type": "OrderCreatedEvent",
  "event_version": 1,
  "payload": {"orderId": "3f2c1a4b-9d5e-4f6a-8b7c-1d2e3f4a5b6c", "userId": "u-demo", "totalAmount": 199.00},
  "metadata": {"userId": "u-demo"},
  "created_at": "2026-08-29T10:15:30+08:00"
}
```

payload 由各事件类的 `getPayload()` 生成（本例 OrderCreatedEvent）；metadata 携带订单归属客户 userId——R001 金额偏离/R004 高频下单规则就是按 `metadata->>'userId'` 聚合同一客户的历史订单。注意它是自由字符串、不是 auth_user 外键：demo 模式（EG_ALLOW_BODY_USER_ID=true）下来自请求体自由填写（如 u-demo），生产模式强制取登录主体 auth_user.id。

### 2.2 aggregate_snapshots —— 聚合快照（加速回放）

来源：V2。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| aggregate_id | UUID PK | 聚合根 ID，一聚合最多一份最新快照 |
| aggregate_type | VARCHAR(64) | 聚合类型 |
| version | INT | 快照对应的聚合版本 |
| state | JSONB NOT NULL | 快照时的聚合状态 |
| created_at | TIMESTAMPTZ | 快照时间 |

取值受限字段：

- `aggregate_type`：同 domain_events，唯一值 `Order`。

面试讲法：事件多了以后逐条回放变慢，快照把回放起点从第 0 版推到快照版本，之后只需重放增量事件。

一行示例（每 100 个事件触发一次快照）：

```json
{
  "aggregate_id": "3f2c1a4b-9d5e-4f6a-8b7c-1d2e3f4a5b6c",
  "aggregate_type": "Order",
  "version": 100,
  "state": {"aggregateId": "3f2c1a4b-9d5e-4f6a-8b7c-1d2e3f4a5b6c", "status": "PAID", "totalAmount": "199.00", "version": 100, "retryCount": 0},
  "created_at": "2026-08-29T14:20:00+08:00"
}
```

state 就是 `OrderAggregate.toStateMap()` 的原样 JSON（注意 totalAmount 存的是字符串）；主键冲突即 upsert，一个聚合只留最新一份快照。

### 2.3 command_log —— 命令日志（命令幂等）

来源：V1，V7 补 `request_hash`。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| command_id | UUID PK | 命令全局 ID（客户端重试沿用同一 ID） |
| aggregate_id | UUID NOT NULL | 命令目标聚合 |
| command_type | VARCHAR(128) NOT NULL | 命令类型（类名） |
| result | JSONB | 首次执行结果（成功版本号或错误） |
| executed_at | TIMESTAMPTZ | 执行时间 |
| request_hash | VARCHAR(64) | 请求指纹（V7 增补） |

取值受限字段：

- `command_type`：12 种命令类简单名——CreateOrderCommand / PayOrderCommand / CompletePaymentCommand / FailPaymentCommand / RetryPaymentCommand / ReserveInventoryCommand / ConfirmOrderCommand / ShipOrderCommand / DeliverOrderCommand / CloseOrderCommand / CancelOrderCommand / RefundOrderCommand。
- `result.success`：true / false（成功带 version，失败带 error，如库存不足）。

关键逻辑（`OrderCommandHandler`）：事务内先按 command_id 行锁 + 查记录；已存在则 `assertCompatible` 校验 request_hash——**同 ID 不同内容的重试会被拒绝**，防止幂等键碰撞；不存在才执行并落库。

面试讲法：命令幂等靠它，事件幂等靠 idempotent_consumers，告警幂等靠 anomaly_id——三层幂等各管一段。

一行示例（创建订单命令首次执行成功）：

```json
{
  "command_id": "c1d2e3f4-a5b6-4c7d-8e9f-0a1b2c3d4e5f",
  "aggregate_id": "3f2c1a4b-9d5e-4f6a-8b7c-1d2e3f4a5b6c",
  "command_type": "CreateOrderCommand",
  "result": {"success": true, "version": 1, "error": null, "orderId": null},
  "executed_at": "2026-08-29T10:15:30+08:00",
  "request_hash": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08"
}
```

result 即 `CommandResult` record 的 JSON（成功带版本号，失败带 error）；request_hash 是 64 位十六进制的 SHA-256 请求指纹。

### 2.4 idempotent_consumers —— 消费幂等记录

来源：V2。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| consumer_group | VARCHAR(64) | 消费组标识（代码实际写入 order-view、saga-trigger） |
| event_id | UUID | 已处理的 domain_events.event_id |
| processed_at | TIMESTAMPTZ | 处理时间 |

取值受限字段：

- `consumer_group`：当前两个写入方——`order-view`（订单投影）、`saga-trigger`（Saga 触发器）；告警链路不写这张表（靠 anomaly_id 主键防重）。

主键 `(consumer_group, event_id)`：Kafka 至少一次投递必然产生重复，消费端先 INSERT 这把联合主键，插不进去说明已处理过，直接跳过。每个消费组独立记账，互不干扰；`IdempotentConsumerCleanup` 定期清理过期记录。

一行示例：

```json
{"consumer_group": "order-view", "event_id": "5f0c9a2e-8f3b-4c1d-9a7e-2b6d8e4f1a3c", "processed_at": "2026-08-29T10:15:31+08:00"}
```

投影消费者写 `order-view`（OrderViewProjection 常量），Saga 触发器写 `saga-trigger`；event_id 正是 domain_events 里那条事件的主键。

## 3. 查询读模型（CQRS 查询端）

### 3.1 order_view —— 订单读模型

来源：V2。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| order_id | UUID PK | 订单 ID（= aggregate_id） |
| status | VARCHAR(32) | 当前状态（9 值 OrderStatus 枚举，见下） |
| total_amount | DECIMAL(12,2) | 订单金额 |
| payment_time | TIMESTAMPTZ | 支付时间 |
| shipping_time | TIMESTAMPTZ | 发货时间 |
| version | INT | 已投影到的事件版本（消费位点守卫） |
| updated_at | TIMESTAMPTZ | 最近更新时间 |

取值受限字段：

- `status`（`OrderStatus` 9 值）：PENDING_PAYMENT 待支付（含已发起异步支付）/ PAYMENT_FAILED 支付失败 / PAID 已支付 / CONFIRMED 已确认 / SHIPPED 已发货 / DELIVERED 已送达 / CLOSED 正常关闭（终态）/ CANCELLED 已取消（终态）/ REFUNDED 已退款。主链路 null → PENDING_PAYMENT → PAID → CONFIRMED → SHIPPED → DELIVERED → CLOSED。注意没有 "CREATED" 状态——订单创建后即 PENDING_PAYMENT。

关键点：`version` 是投影的乐观守卫——事件按版本顺序应用，旧版本事件乱序到达时直接丢弃；页面列表查询走 `(status, updated_at DESC)`、`updated_at DESC` 索引（V6）。它**完全派生**自 domain_events，删了可以重建，这是"读模型只是缓存"这句话的证据。

一行示例（已支付、待发货的订单——投影到第 3 个事件）：

```json
{
  "order_id": "3f2c1a4b-9d5e-4f6a-8b7c-1d2e3f4a5b6c",
  "status": "PAID",
  "total_amount": 199.00,
  "payment_time": "2026-08-29T10:18:02+08:00",
  "shipping_time": null,
  "version": 3,
  "updated_at": "2026-08-29T10:18:02+08:00"
}
```

version=3 对应 OrderCreated(1) → PaymentRequested(2，支付意图不改状态) → PaymentCompleted(3) 三个事件；shipping_time 还是 null，因为订单只走到 PAID。

## 4. 认证与授权（RBAC）

来源：V3（V5 给存量库补 token_version）。共 5 张业务表 + 1 张审计表，经典 RBAC 五表结构；种子数据（权限/角色/账号）由 `AuthDataSeeder` 启动时写入。

### 4.1 auth_user —— 用户

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| id | BIGSERIAL PK | 用户 ID |
| username | VARCHAR(64) UNIQUE | 登录名 |
| password_hash | VARCHAR(100) | BCrypt 哈希，无明文 |
| display_name | VARCHAR(64) | 显示名 |
| enabled | BOOLEAN | 是否启用 |
| must_change_password | BOOLEAN | 强制改密标记（演示账号首次登录弹框） |
| token_version | INT | 令牌版本：改密/登出所有设备时递增，AuthFilter 比对 JWT claims 的 tv，旧 token 全部失效 |
| created_at / updated_at | TIMESTAMPTZ | 创建/更新时间 |

一行示例（种子管理员账号）：

```json
{
  "id": 1, "username": "admin",
  "password_hash": "$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy",
  "display_name": "管理员", "enabled": true, "must_change_password": false,
  "token_version": 0,
  "created_at": "2026-08-01T09:00:00+08:00", "updated_at": "2026-08-29T10:00:00+08:00"
}
```

password_hash 是 60 字符 BCrypt 串（AuthDataSeeder 启动时生成，库里无明文）；token_version 每次改密/登出所有设备 +1，旧 JWT 全部失效。

### 4.2 auth_role / auth_permission —— 角色与权限

| 表 | 字段 | 含义 |
| --- | --- | --- |
| auth_role | id PK, code UNIQUE, name, description | 角色字典（admin/operator/viewer） |
| auth_permission | id PK, code UNIQUE, description | 权限点字典（如 order:refund） |

取值受限字段：

- `auth_role.code`：预置 ADMIN / OPERATOR / VIEWER（种子数据；管理员可再创建其他角色，非封闭枚举）。
- `auth_permission.code`：固定 9 个权限点——order:read / order:create / order:write / anomaly:view / ai:query / compensation:execute / user:manage / role:manage / anomaly:evaluate（AuthDataSeeder.PERMISSIONS 是唯一事实来源）。

一行示例：

```text
auth_role:       {"id": 3, "code": "VIEWER", "name": "只读访客", "description": "只读：查看订单、异常看板、自然语言查询"}
auth_permission: {"id": 7, "code": "user:manage", "description": "用户管理"}
```

9 个权限点、ADMIN/OPERATOR/VIEWER 三角色全部由 AuthDataSeeder 启动时种入（代码里的 PERMISSIONS/ROLES 常量就是权限目录的唯一事实来源）。

### 4.3 auth_user_role / auth_role_permission —— 两张关联表

| 表 | 结构 | 含义 |
| --- | --- | --- |
| auth_user_role | (user_id, role_id) PK，外键 ON DELETE CASCADE | 用户-角色多对多 |
| auth_role_permission | (role_id, permission_id) PK，外键 ON DELETE CASCADE | 角色-权限多对多 |

无取值受限字段——纯 (外键, 外键) 关联对，取值范围就是两张主表的 id。

一行示例：

```text
auth_user_role:       (user_id=2, role_id=2)        -- operator 账号拥有 OPERATOR 角色
auth_role_permission: (role_id=3, permission_id=1)  -- VIEWER 角色拥有 order:read 权限
```

纯关联对、无业务字段；删用户或角色时靠 ON DELETE CASCADE 自动清理两侧关联。

### 4.4 auth_audit_log —— 认证审计

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| id | BIGSERIAL PK | 自增 |
| username | VARCHAR(64) | 操作账号 |
| action | VARCHAR(64) NOT NULL | LOGIN_OK / LOGIN_FAILED / 改密等 |
| detail | VARCHAR(512) | 细节 |
| ip | VARCHAR(64) | 来源 IP |
| created_at | TIMESTAMPTZ | 时间 |

取值受限字段：

- `action`：12 个动作码，按四组——登录会话 LOGIN_OK / LOGIN_FAILED / LOGOUT / LOGOUT_ALL；密码 PASSWORD_CHANGE；用户管理 USER_CREATE / USER_UPDATE / USER_RESET_PASSWORD / USER_DELETE；角色管理 ROLE_CREATE / ROLE_UPDATE / ROLE_DELETE。VARCHAR 无数据库约束，新增管理操作时需统一动作码命名。

一行示例（一次登录失败）：

```json
{
  "id": 101, "username": "admin", "action": "LOGIN_FAILED",
  "detail": "用户名或密码错误", "ip": "203.0.113.7",
  "created_at": "2026-08-29T23:41:07+08:00"
}
```

登录/登出/改密类记录来源 IP；管理员操作用户/角色（USER_CREATE 等）只有 detail，ip 为 null——服务层未传。

面试讲法：登录防爆破计数在内存，但每次成败都落审计表；JWT 无状态不代表没有审计轨迹。

## 5. 网关与 Saga 补偿

### 5.1 gateway_request —— 网关请求/回调关联（兼 outbox）

来源：V4。支付是异步回调，这张表是"我发出去的请求"与"回调进来的通知"的关联依据。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| id | UUID PK | 网关请求 ID |
| command_id | UUID NOT NULL | 发起命令（关联 command_log） |
| aggregate_id | UUID NOT NULL | 订单聚合 |
| gateway_type | VARCHAR(32) NOT NULL | 当前仅写 PAYMENT（INVENTORY / NOTIFICATION 为表注释预留） |
| request_type | VARCHAR(32) NOT NULL | 当前仅写 CREATE_PAYMENT（CAPTURE / REFUND / RESERVE / NOTIFY 为预留） |
| provider | VARCHAR(32) NOT NULL | mock / alipay / … |
| external_ref | VARCHAR(128) | 网关侧单号，回调按它反查（有索引） |
| status | VARCHAR(32) NOT NULL | PENDING / SUCCEEDED / FAILED |
| request_payload / response_payload | JSONB | 请求与响应原文 |
| created_at / updated_at | TIMESTAMPTZ | 时间 |

取值受限字段：

- `gateway_type`：当前只写 `PAYMENT`（只有支付协调器创建 gateway_request）。
- `request_type`：当前只写 `CREATE_PAYMENT`。
- `provider`：mock / alipay（随 EG_PAYMENT_PROVIDER 装配适配器，当前 .env 为 mock）。
- `status`：PENDING（已落库、等异步回调）→ SUCCEEDED / FAILED（终态，重复回调幂等跳过）。

面试讲法：回调先进来时查 external_ref 找到对应命令再驱动聚合，避免"回调认不出订单"；同时它兼作 outbox——状态没推进成功就说明外呼未闭环。

一行示例（发起支付，回调已成功）：

```json
{
  "id": "e4a5f6b7-c8d9-4e0f-a1b2-3c4d5e6f7a8b",
  "command_id": "b7c8d9e0-f1a2-4b3c-8d4e-5f6a7b8c9d0e",
  "aggregate_id": "3f2c1a4b-9d5e-4f6a-8b7c-1d2e3f4a5b6c",
  "gateway_type": "PAYMENT",
  "request_type": "CREATE_PAYMENT",
  "provider": "mock",
  "external_ref": "mockpay-f1e2d3c4-b5a6-4789-8a9b-0c1d2e3f4a5b",
  "status": "SUCCEEDED",
  "request_payload": {"amount": "199.00"},
  "response_payload": {"result": "SUCCEEDED", "error": null, "callback_id": "cb-20260829-0001"},
```

request_payload 只存 `{"amount": "字符串"}`（PaymentCoordinator 原样写入）；external_ref 是网关侧支付单号 `"mockpay-"+UUID`，回调按它反查本行拿到 command_id 驱动聚合。

### 5.2 notification_log —— 通知发送审计

来源：V4。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| id | UUID PK | 通知 ID |
| aggregate_id | UUID | 关联订单（有索引） |
| notification_type | VARCHAR(32) | 类型 |
| recipient | VARCHAR(255) | 接收方 |
| channel | VARCHAR(32) | 渠道 |
| status | VARCHAR(32) | 发送结果 |
| payload | JSONB | 内容原文 |
| created_at | TIMESTAMPTZ | 时间 |

取值受限字段：

- `notification_type`：当前实际发出 `DELAY`（WeCom 模板还支持 OUT_OF_STOCK / REFUND / PAYMENT_FAILED 文案，暂无调用方发出）。
- `channel`：mock / wecom（随 EG_NOTIFY_PROVIDER，当前 mock）。
- `status`：SENT / FAILED。

面试讲法：设计上供 AI 根因分析查"用户到底有没有收到通知"，是排障链路的一环；如实说明——当前实现只写不读（全库无 SELECT），读方是下一步工作。

一行示例（Saga 的延迟通知补偿动作）：

```json
{
  "id": "a9b8c7d6-5e4f-4a3b-9c2d-1e0f9a8b7c6d",
  "aggregate_id": "3f2c1a4b-9d5e-4f6a-8b7c-1d2e3f4a5b6c",
  "notification_type": "DELAY",
  "recipient": "order-user",
  "channel": "mock",
  "status": "SENT",
  "payload": {},
  "created_at": "2026-08-29T15:00:00+08:00"
}
```

NotifyDelayAction 未传 recipient 时落默认值 "order-user"，payload 是通知内容原文（本例为空对象）；排障时先查这张表确认用户收没收到，再往前追网关。

### 5.3 compensation_approval —— 补偿审批流

来源：V4（对齐设计文档 7.4.4）。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| approval_id | UUID PK | 审批单 ID |
| saga_id | UUID NOT NULL | 所属 saga 实例 |
| action_type | VARCHAR(64) NOT NULL | 待执行的补偿动作 |
| aggregate_id | UUID NOT NULL | 目标聚合 |
| params | JSONB | 动作参数 |
| status | VARCHAR(32) NOT NULL | PENDING / APPROVED / REJECTED（有索引） |
| requested_by | VARCHAR(64) NOT NULL | 发起方（注释设计 agent/human，实际 Saga 写 `saga`） |
| requested_at | TIMESTAMPTZ NOT NULL | 发起时间 |
| decided_at | TIMESTAMPTZ | 审批时间 |
| decided_by | VARCHAR(64) | 审批人 |

取值受限字段：

- `action_type`：注册的 5 类补偿动作——REFUND / NOTIFY_DELAY / MARK_OUT_OF_STOCK / FREEZE_ORDER / BACKOFF_AND_STOP（CompensationActionRegistry 白名单）。
- `status`：PENDING → APPROVED / REJECTED（后两者终态；拒绝则 Saga 转 FAILED）。
- `requested_by`：建表注释写的 agent/human，当前唯一写入方 Saga 实际落 `saga`——设计注释与实现不一致，面试时如实说明；`decided_by` 是审批人用户名（开放值）。

面试讲法：saga 自动补偿分两级——低风险直接执行，高风险（如大额退款）写一张 PENDING 审批单等人拍板；这就是前端"审批队列"页面的数据源。

一行示例（Saga 发起的大额退款审批，尚未拍板）：

```json
{
  "approval_id": "d0c1b2a3-4e5f-4678-9abc-def012345678",
  "saga_id": "1a2b3c4d-5e6f-4a1b-8c9d-0e1f2a3b4c5d",
  "action_type": "REFUND",
  "aggregate_id": "3f2c1a4b-9d5e-4f6a-8b7c-1d2e3f4a5b6c",
  "params": {"amount": 199.00},
  "status": "PENDING",
  "requested_by": "saga",
  "requested_at": "2026-08-29T15:02:00+08:00",
  "decided_at": null,
  "decided_by": null
}
```

REFUND 的审批规则是金额 > 100 元才挂审批（RefundAction.requiresApproval），低风险动作如 NOTIFY_DELAY 直接执行不进这张表；decided_at/decided_by 由审批接口拍板后回填。

## 6. AI 异常与用户配置

### 6.1 anomaly_alerts —— 异常告警历史

来源：V8（V7 之后，替代进程内环形缓冲）。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| anomaly_id | TEXT PK | 告警幂等键：at-least-once 重复投递不会产生第二行 |
| rule_id | TEXT | 命中的检测规则 |
| aggregate_id | TEXT | 关联订单 |
| level | TEXT | 告警级别 |
| source | TEXT | 来源（哪类检测器） |
| payload | JSONB NOT NULL | 原始告警 JSON，读取时原样反序列化，字段演进零迁移 |
| received_at | TIMESTAMPTZ NOT NULL | 落库时间（有 DESC 索引，看板按时间倒序） |

取值受限字段：

- `level`：INFO / WARN / ERROR（AI 链路把内部 HIGH→ERROR、LOW→WARN；当前主要产生 WARN/ERROR）。
- `source`：RULE（Java 规则）/ IF（Isolation Forest）/ PROCESS（流程检测）。
- `rule_id`：R001–R005（Java 事件级规则）、P001–P004（Python 流程级规则）、IF 兜底。
- payload 内 `priority`：HIGH / LOW——处置优先级，与 `level` 是两个独立维度。

链路归属：AI 服务（Python）检测后发 Kafka `anomaly-alerts` topic；**Java anomaly consumer 消费后写这张表**并推 WebSocket。前端断线重连调 `/alerts/recent` 补拉的就是它——所以重启/断线不丢告警历史。

一行示例（R001 支付金额偏离告警）：

```json
{
  "anomaly_id": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
  "rule_id": "R001",
  "aggregate_id": "3f2c1a4b-9d5e-4f6a-8b7c-1d2e3f4a5b6c",
  "level": "ERROR",
  "source": "RULE",
  "payload": {
    "anomaly_id": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
    "rule_id": "R001",
    "aggregate_id": "3f2c1a4b-9d5e-4f6a-8b7c-1d2e3f4a5b6c",
    "event_type": "PaymentCompletedEvent",
    "level": "ERROR", "source": "RULE", "priority": "HIGH",
    "detected_at": "2026-08-29T10:18:03+08:00",
    "description": "支付金额较用户历史均值显著偏离",
    "details": {"userId": "u-demo", "amount": 199.00}
  },
  "received_at": "2026-08-29T10:18:04+08:00"
}
```

payload 就是 Python 侧 Anomaly 模型（eventguard-ai/app/model/anomaly.py）发到 Kafka 的原始 JSON，Java 消费者原样落库，details 内容因规则而异；anomaly_id 为 uuid4，at-least-once 重复投递靠它防重。

### 6.2 user_llm_config —— 用户级 LLM 配置

来源：V9。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| user_id | BIGINT PK，外键 auth_user ON DELETE CASCADE | 一人一份配置 |
| provider | VARCHAR(32) | LLM 提供商 |
| base_url | VARCHAR(500) | 接口地址 |
| api_key_enc | TEXT | **AES-256-GCM 密文**（base64(iv‖tag‖ciphertext)），密钥由 EG_JWT_SECRET 派生，库里无明文 key |
| model | VARCHAR(200) | 模型名 |
| max_tokens | INT | 默认 2048 |
| temperature | DOUBLE PRECISION | 默认 0.3 |
| updated_at | TIMESTAMPTZ | 时间 |

取值受限字段：

- `provider`：空串（按 base_url 自动探测协议）/ openai / anthropic——集合之外的值在 Java 保存时被拒绝。

面试讲法：NL 查询/AI 功能每个用户自带 key，替代进程级 EG_LLM_* 环境变量；密钥复用 JWT secret 派生而不是再配一个，运维少管一个敏感项。

一行示例：

```json
{
  "user_id": 2,
  "provider": "openai",
  "base_url": "https://api.deepseek.com/v1",
  "api_key_enc": "mZ3kXQ9fR2s…（base64(iv‖tag‖ciphertext)）",

  "max_tokens": 2048,
  "temperature": 0.3,
  "updated_at": "2026-08-28T21:30:00+08:00"
}
```

provider 仅支持 openai / anthropic / 自动探测；openai + 自定义 base_url 即可接任何 OpenAI 兼容端点（如 DeepSeek），一用户一行（user_id 主键）upsert。

## 7. 面试高频追问速答

1. **"几张表？怎么分工？"** —— 16 张。1 张事实源（domain_events）+ 1 张读模型（order_view）+ 3 张一致性辅助（快照/命令幂等/消费幂等）+ 6 张认证授权 + 3 张网关与审批 + 2 张告警与 LLM 配置。只有 domain_events 进 CDC，其余都是普通 CRUD。
2. **"为什么 payload 用 JSONB 而不是平铺列？"** —— 事件类型多样且会演进，JSONB 让 schema 归事件自身管；查询需求（按 metadata/payload 过滤）用 GIN 索引兜住。代价是没有外键和强类型约束，一致性靠写入方保证——一致性本来就只属于命令侧。
3. **"怎么防重复消费/重复下单？"** —— 三层：命令侧 command_log（command_id 主键 + request_hash 防碰撞）、消费侧 idempotent_consumers（consumer_group+event_id 联合主键）、告警侧 anomaly_id 主键。
4. **"乱序事件怎么办？"** —— order_view.version 与事件 event_version 比对，旧版本丢弃；domain_events 的 UNIQUE(aggregate_id, event_version) 保证同一聚合版本序列严格递增。
5. **"order_view 和 domain_events 会不一致吗？"** —— 会（消费延迟），前端读 order_view 时要接受最终一致；补偿审批/异常看板直接读自己的表。排障顺序：先查 order_view.version 卡在哪，再查 domain_events 事实。
6. **"auth 表为什么不用 UUID 主键？"** —— 内部管理数据量小、无对外暴露需求，BIGSERIAL 简单够用；对外暴露的聚合（订单）才用 UUID。
