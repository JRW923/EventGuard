## 一、一句话速览（30 秒版）

> EventGuard 是一个电商订单的事件溯源管理台。订单每次状态变更都存成不可变事件，可以回放任意历史时刻的状态；事件流经 Debezium CDC 进 Kafka，Python 服务在上面做分层异常检测，告警通过 WebSocket 实时推到前端；另外支持用中文直接问订单和统计，不用写 SQL。技术栈是 Spring Boot 3.3 + Vue3 + FastAPI，全套 Docker Compose 一条命令起。

30 秒里必须留在面试官脑子里的三个词：**事件溯源、CDC 解耦、分层检测**。其他都是展开时再说。

## 二、简历素材

### 项目描述（3 行版，可直接用）

> **EventGuard · 电商订单事件溯源与异常检测平台**（个人项目 / 全栈）
> 基于 Event Sourcing + CQRS 实现订单全生命周期可回放、可审计，通过 Debezium CDC 将事件变更实时同步至 Kafka，驱动规则引擎与机器学习模型的分层异常检测，告警经 WebSocket 秒级推送；支持中文自然语言查询订单与统计。
> 技术栈：Spring Boot 3.3 / Java 17 / PostgreSQL / Kafka / Debezium / FastAPI / scikit-learn / Vue3 + TypeScript / Docker Compose / Prometheus + Grafana

### 核心贡献

- 设计事件存储层，以 `UNIQUE(aggregate_id, event_version)` 唯一约束 + `MAX(version)` 前置校验实现**双层乐观锁**，冲突自动重试 3 次；每 100 个事件落一次快照，聚合重建从快照增量 replay
- 以客户端 `commandId` 为幂等键落 `command_log` 表实现**命令级幂等**，重复提交返回首次结果而非产生重复事件，与事件写入同事务
- 读侧异步投影 + `idempotent_consumers` 表消费去重 + `version` 单调守卫防状态倒退，并提供**读己写一致性**接口（50ms 轮询 / 2s 超时降级）
- 搭建 **CDC 管道**：PostgreSQL WAL → Debezium → Kafka → Python 检测服务，消费侧关闭自动提交、失败 3 次退避重试后投递 DLT，实现 at-least-once 不丢消息
- 实现分层异常检测：5 条业务规则 + 3 条流程规则 + Isolation Forest 事件级 + HMM 序列级；**做了 Baseline 对照实验，规则 Baseline F1 达 0.887（P 0.879 / R 0.896 / FPR 0.088），并定位出引入 Isolation Forest 后 Recall 零增益、误报从 176 升至 691 的根因**
- 中文自然语言查询采用「意图分类 + 参数抽取 + 模板执行」而非 LLM 直接生成 SQL，从架构上消除注入风险，LLM 超时 8s 自动降级为数据摘要
- 沉淀自动化测试 **328 项全部通过**（后端 164 项含 Testcontainers 真库一致性测试、AI 服务 125 项、前端 39 项 + 类型检查）

## 三、面试讲解话术

### 1 分钟版

> 这个项目叫 EventGuard，做的是电商订单的事件溯源和异常检测。
>
> 起因是我发现传统写法有个问题：订单状态直接 UPDATE 覆盖数据库，出了数据不一致只能看到最终状态，没法回答「它是怎么走到这一步的」。所以我把订单的每一次变更都存成一条不可变事件，状态是靠事件 replay 算出来的，这样任意历史时刻的状态都能回放，天然就有完整的审计链路。
>
> 在这之上我做了两件事。一是异常检测——事件通过 Debezium CDC 流进 Kafka，Python 服务消费后做分层检测，业务规则判金额偏离、重复支付、状态跳跃这些，机器学习模型兜底判没被规则覆盖的模式，告警走 WebSocket 实时推到前端看板。二是中文自然语言查询，运营可以直接问「最近 7 天有多少订单」，不用写 SQL。
>
> 技术栈是 Spring Boot 加 Vue3，AI 服务用 FastAPI 单独拆出来，整套用 Docker Compose 一条命令起。测试写了三百多个，其中一致性相关的用 Testcontainers 真起 PostgreSQL 跑端到端验证。

### 3 分钟版（为什么做 → 怎么设计 → 踩了什么坑 → 学到什么）

**第一段 · 为什么（20 秒）**

> 先说背景。我想解决的是订单系统的可追溯问题——传统 CRUD 直接覆写状态，一旦数据不一致，只能看到结果看不到过程。所以我选了 Event Sourcing：状态变更本身成为唯一事实来源。

**第二段 · 写侧怎么保证正确（50 秒，这段是硬功夫，讲慢一点）**

> 写侧的核心是并发安全和幂等。
>
> 并发我做了两层。第一层是在数据库上给「聚合 ID + 事件版本」加唯一约束，第二层是写之前先查当前最大版本做前置校验。前置校验能给出更清楚的错误，唯一约束是最后的兜底——因为前置校验和插入之间有竞态窗口，光靠它挡不住。冲突了会抛并发异常，上层有个重试模板做线性退避，重试 3 次。
>
> 幂等是另一个问题：网络重试会让同一个命令提交两次。我的做法是客户端生成一个 `commandId`，写事件的同时把命令结果记到 `command_log` 表，主键就是这个 ID。同一个命令再来，直接返回上次的结果，不会产生第二条事件。这两个动作在同一个事务里，要么都成功要么都回滚。
>
> 事件多了聚合重建会慢，所以加了快照，每 100 个事件存一次当前状态，重建时先读快照再 replay 后面的增量。

**第三段 · 读侧和 CDC（40 秒）**

> 读侧是 CQRS，异步投影。事件不是应用直接发 Kafka 的，而是用 Debezium 读 PostgreSQL 的 WAL，把变更捕获出来推到 Kafka。这么选是因为「事件落库」和「发消息」如果在应用里做两次写，就不是原子的——可能库写成了消息没发出去。CDC 让消息成为库变更的必然结果。
>
> 异步投影带来两个问题。一个是消息可能重复，我用了一张消费去重表，主键是消费组加事件 ID；另外每条 UPDATE 都带版本单调守卫，只有新版本大于旧版本才更新，防止乱序导致状态倒退。另一个问题是用户下单后立刻查可能查不到，我做了读己写接口，按预期版本轮询投影，50 毫秒一次，2 秒超时就抛异常让前端提示「数据同步中」，而不是假装成功返回旧数据。

**第四段 · AI 部分 + 诚实的坑（40 秒，这段是加分点）**

> 检测是分层的。规则引擎放在 Java 侧，因为它要读事件库算用户历史均值这些；模型放 Python，Python 通过 HTTP 反向调规则接口拿结果，再和自己的模型结果合并。
>
> 这里我踩了个坑，也是我觉得最有价值的部分。我一开始想的是「规则打底、模型提升」，做完之后跑了一组 Baseline 对照实验，结果发现加了 Isolation Forest 之后 F1 反而从 0.887 掉到 0.753。更关键的是我看混淆矩阵才发现，两个版本的召回率一模一样，都是 0.896——模型只多抓到 1 个真异常，但多产生了 515 个误报。也就是说它的召回增益基本是零，纯粹在制造噪音。
>
> 根因是我给的 `contamination` 参数是 0.05，模型被强制按 5% 的比例判异常，而这个比例和真实分布不匹配，它划出去的那批样本里几乎没有真异常。
>
> 结论是这个场景下规则本身就够强，无监督模型没有带来任何增量价值。我没有把这个结果藏起来，而是把对照数据写进了评测报告——因为如果不做 Baseline，我会一直以为加了 AI 就是变好了。

**第五段 · 收尾（10 秒）**

> 整体下来我最大的收获是：分布式里「保证一致性」不是写一句话，是要落到具体的约束、去重表、版本守卫和超时降级上，每一层都得能说清挡的是哪种失败。

| 面试官问 | 坑在哪 | 怎么答 |
|---|---|---|

## 四、技术架构详解

### 链路全景

```
Vue3 管理台
  │  写命令 ──▶ CommandHandler ──▶ 事务{ EventStore.append + command_log }
  │                                     │  乐观锁(唯一约束 + MAX(version)前置校验)
  │                                     │  每100事件 → aggregate_snapshots
  │                                     ▼
  │                              PostgreSQL domain_events (WAL)
  │                                     │
  │                              Debezium CDC
  │                                     ▼
  │                                Kafka domain-events
  │                        ┌────────────┼────────────┬──────────────┐
  │                        ▼            ▼            ▼              ▼
  │              OrderViewProjection  SagaTrigger  Python检测   (失败3次→DLT)
  │              (去重表+版本守卫)    (补偿编排)   (规则+IF+HMM)
  │                        │                            │
  │  读查询 ◀──── order_view (读己写轮询 50ms/2s)        │ 告警
  │                                                     ▼
  └─ WebSocket ◀── AnomalyWebSocketHandler ◀── Kafka anomaly-alerts
                          │
                    RecentAlertsBuffer (环形100) ──▶ GET /alerts/recent (断线补拉)
```

### 关键决策一：Event Sourcing + CQRS，而不是 CRUD + 审计表

**为什么不选审计表**：审计表是「事后记录」，状态还是靠 UPDATE 覆盖的。一旦审计写失败或漏写，你没法发现，因为状态和审计是两份独立数据。事件溯源里事件**就是**状态的来源，不存在「状态对但历史丢了」这种情况。

**为什么不选 CRUD + binlog**：binlog 记的是行变更（`status: PENDING → PAID`），丢的是业务意图。同样一次状态变化，可能是用户支付、可能是运营手动改、可能是补偿回滚——事件类型能区分，binlog 不能。异常检测恰好需要这个语义。

**代价（要主动说）**：读侧最终一致、事件 schema 演进要兼容旧事件、存储只增长。前两个用读己写接口和 payload 存 jsonb 缓解，第三个做了 90 天归档脚本。

### 关键决策二：Debezium CDC，而不是应用内双写 Kafka

**为什么不双写**：`eventStore.append(); kafka.send();` 这两行没法做成原子的。库成功消息失败 → 投影永远落后；消息成功库回滚 → 下游收到不存在的事件。要在应用内解决就得上事务消息或 Outbox 表 + 轮询。

**为什么不用 Outbox**：Outbox 确实能解决原子性（同一事务里写业务表和 outbox 表），但要自己写轮询发送器、处理已发送标记、控制轮询延迟。而我的事件表**本身就是 Outbox**——事件就是要发出去的消息。所以直接让 Debezium 读 WAL，等于用零应用代码拿到 Outbox 的保证。

**代价**：多一个中间件要运维；CDC 有延迟；Debezium connector 挂了整条链路停（加了健康检查）。

### 关键决策三：NL 查询走「意图分类 + 模板执行」，而不是 LLM 直接生成 SQL

**为什么不做 Text2SQL**，按重要性排：

1. **安全**：LLM 生成的 SQL 要么你敢直接执行（注入面全开），要么你写个 SQL 校验器（比模板方案复杂十倍）。
2. **可靠**：LLM 生成 SQL 的正确率不稳定，同一个问题两次生成可能不一样，出错时用户看到的是数据库报错。
3. **可降级**：LLM 挂了 Text2SQL 就完全不可用，模板方案关键词兜底还能跑。

**实际实现**：意图分类只分三类（查订单 / 查统计 / 查轨迹），LLM 优先、关键词表兜底；参数用正则抽（订单号 UUID、状态词、时间窗）；然后调后端已有的 REST 接口，全程不拼 SQL 字符串。LLM 只负责最后把结构化数据润色成中文回答，8 秒超时降级为数据摘要。

**代价**：只能回答预设的三类问题。这是主动选的边界——**可控的窄能力 > 不可控的宽能力**。

### 一致性的四层防线（问最终一致性时用这段）

1. **写侧**：唯一约束 + 前置版本校验 + 重试 3 次 → 并发写不产生版本空洞
2. **命令侧**：`command_log` 主键幂等 → 重复提交不产生重复事件
3. **消费侧**：`idempotent_consumers(消费组, 事件ID)` 主键去重 + `version` 单调守卫 → at-least-once 下投影不重复不倒退
4. **读侧**：读己写按版本轮询，2 秒超时抛异常 → 宁可告诉用户「同步中」，也不返回过期数据

## 五、个人贡献

### 简历版（一句话）

> 独立完成从事件存储层、CDC 管道、分层异常检测到前端管理台的全栈设计与实现，并搭建自动化评测与混沌注入验证体系。

### 1 分钟版

> 这是我一个人从零做的项目，架构设计到编码到部署都是我。
>
> 我自己觉得最有含量的是三块。第一块是事件存储的正确性，乐观锁的两层设计、命令幂等、快照策略都是我推敲过的——比如为什么前置校验之外还要留唯一约束，因为中间有竞态窗口。第二块是最终一致性的处理，消费去重表、版本单调守卫、读己写超时降级，这三个是配套的，少一个就有洞。第三块是我做了 Baseline 对照实验来验证 AI 到底有没有用，最后发现是负收益，我把这个结论如实写进了报告。
>
> 另外三百多个测试是我补的，一致性相关的用 Testcontainers 真起数据库跑，不是 mock。

### 3 分钟版（四块，每块带一个「我当时纠结过什么」）

**① 事件存储层**

> 我实现了事件的追加、聚合重建、快照。这里纠结过一个点：乐观锁到底靠数据库约束还是靠应用校验。最后两个都留了——唯一约束是正确性底线，前置校验是为了给出更明确的错误信息和更早失败。我一开始只写了前置校验，后来意识到查最大版本和插入之间有竞态，两个并发请求可能都通过校验，所以必须有约束兜底。

**② CQRS 与最终一致性**

> 投影是异步的，通过 Kafka 消费事件。纠结的是要不要做同步投影——同步能立即读到，但写请求要等投影完成，而且投影失败会拖垮写侧。最后选异步，然后单独给需要立即读的场景提供读己写接口，按版本轮询。这样代价只落在真正需要强读的路径上。

**③ 分层检测与 AI 效果验证**

> 规则引擎放 Java、模型放 Python，Python 反向调 Java 的规则接口。这么切分是因为规则要读事件库算用户历史基线，放 Python 得再连一次库。
>
> 更重要的是我做了 Baseline 对照。原本只跑 AI 版本，数字看着不错就想收工了，后来觉得不对——不知道「没有 AI 会怎样」就说不清 AI 的价值。补了对照实验才发现 AI 版本 F1 更低，而且召回一点没涨、误报涨了近四倍。这个负结果我留在报告里了。

**④ 故障路径与验证**

> 我专门处理了失败路径：Kafka 消费失败三次退避后进死信队列、告警发布失败退避重试、WebSocket 断线重连后按告警 ID 去重补拉最近告警、Saga 编排器重启后从数据库的待审批单重放在途补偿、LLM 超时降级。另外用 Pumba 做混沌注入，随机杀容器验证能恢复。

## 六、面试题本

给的是**答题框架**，不是背诵稿。每题按框架说出自己的话。

### 基础题（答不上来减分）

**Q1. 什么是 Event Sourcing？和 CRUD 的区别？**

定义（状态变更存为不可变事件序列，状态由 replay 得出）→ 对比（CRUD 存当前状态、事件溯源存变更过程）→ 收益（可回放、可审计、天然有业务因果链）→ 代价（读复杂、schema 演进、存储增长）→ 落到项目（`domain_events` 表 + 快照）

**Q2. CQRS 是什么？读写分离带来什么问题？**

命令侧和查询侧用不同模型 → 好处（读侧可为查询优化，不受写模型约束）→ 问题就是最终一致性 → 你的四层应对（消费去重、版本守卫、读己写、超时降级）

**Q3. 乐观锁和悲观锁的区别？为什么选乐观锁？**

悲观锁先加锁再操作（`SELECT FOR UPDATE`），乐观锁先操作再校验版本 → 选乐观是因为事件追加的冲突概率低（同一订单并发写少），加悲观锁会白付锁开销 → 冲突时重试 3 次的成本远低于全程持锁

**Q4. Kafka 怎么保证不丢消息？at-least-once 和 exactly-once 的区别？**

生产端 acks + 重试，broker 端副本，消费端手动提交 offset → 你的实现：关闭自动提交，处理成功才提交，失败 seek 回原 offset 重试 3 次，超限进 DLT → at-least-once 会重复，所以消费侧必须幂等（你的去重表）→ exactly-once 需要事务/幂等生产者，成本高，业务侧去重更实际

### 深挖题（区分度在这里）

**Q5. 快照阈值为什么是 100？怎么定的？**

诚实说是经验值不是压测出来的 → 但讲清 trade-off：阈值大则重建慢，阈值小则写放大和存储开销大 → 科学定法：测单条事件 replay 耗时，按可接受的重建延迟反推 → **主动加一句「这是我该补测的」**

**Q6. 前置版本校验和唯一约束功能重复，为什么留两个？**

不重复。前置校验在「查最大版本」和「插入」之间有竞态窗口，两个并发请求可能都通过 → 唯一约束是数据库层面的串行化保证，是正确性底线 → 前置校验的价值是快速失败和明确错误信息 → **这题答好很加分，说明你真想过并发**

**Q7. 消费去重表会无限增长吗？怎么清理？**

会 → 现在没做清理（诚实）→ 方案：按时间分区 + 定期 drop 老分区，或只保留一个 offset 水位线（若消费严格有序）→ 现有的事件归档脚本可以顺带处理

**Q8. 读己写 2 秒超时之后前端怎么办？为什么不阻塞更久？**

抛 `ProjectionLagException`，前端提示「数据同步中」并可重试 → 不阻塞更久因为占用连接和线程，而且 2 秒后大概率是投影链路故障不是慢，继续等没意义 → 更好的方案是前端订阅 WebSocket 等投影完成通知，避免轮询

**Q9. 为什么 AI 检测不如规则？给你时间会怎么改？**

先给数据（F1 0.887 → 0.753，**召回完全相同 0.896**，FP 176 → 691）→ 归因：`contamination=0.05` 强制按固定比例判异常，与真实分布不匹配，划出去的样本里几乎没有真异常，所以只增噪不增召回 → 改法三条：① 把规则阈值从 3σ 调到 2.5σ，先榨干规则本身的空间（漏检样本恰好卡在 2.5σ）；② 无监督换有监督，用规则打的标签做弱监督；③ 不做「模型并列」而做「模型只在规则未命中的样本上兜底」，并给更保守的阈值

**Q10. Saga 编排器状态存内存，重启会丢吗？**

在途步骤会丢，但待审批单是落库的 → `SagaRecoveryRunner` 启动时读 PENDING 审批单，把序列化在参数里的剩余步骤反序列化出来重建实例 → 局限是单实例，多实例部署会重复恢复 → 彻底解法是 Saga 实例状态整体落库 + 分布式锁，当时判断个人项目收益不够，留成了已知限制

### 场景题

**Q11. 订单量涨 100 倍，事件表 10 亿行，怎么改？**

分层回答，**强调顺序**：① 读侧先扛（投影表按时间分区、加索引、热数据上缓存）；② 事件表按 `aggregate_id` 哈希分片，因为所有查询都带聚合 ID，分片键天然可选；③ 冷数据归档（已有 90 天归档脚本）；④ 快照阈值下调减少 replay；⑤ 最后才考虑换专用事件存储。**关键是先优化再分片，别一上来就说分库分表**

**Q12. 某订单的投影状态和事件重放结果不一致，怎么排查？**

考的是可观测性思路。① 事件是唯一事实来源，所以先信事件、疑投影；② 查投影消费是否跳过——去重表里有没有这个事件 ID；③ 查版本守卫是否拦掉了合法更新（乱序到达且版本相等）；④ 查投影消费者有没有报错但被吞掉；⑤ 兜底手段：从事件重放重建该聚合的投影 → 顺带说 `eventguard.projection.lag` 指标能提前发现

**Q13. 用户反馈异常告警偶尔收不到，怎么定位？**

沿链路逐段排除。① AI 侧 `eventguard_ai_anomalies_published_total` 有没有涨；② Kafka `anomaly-alerts` 有没有堆积；③ server 消费有没有报错；④ WebSocket 会话是否半开（**已知短板：没有心跳剔除**）；⑤ 前端去重是否误杀 → 现有兜底：断线重连拉 `/alerts/recent` 补拉 → **主动说出短板：环形缓冲只有 100 条，断线久了会丢**

## 七、差异化亮点

### 亮点一：做了 Baseline 对照实验，并且如实汇报了负结果

**为什么差异化**：绝大多数简历项目写「引入 AI/算法，效果提升 X%」，追问「不用 AI 是多少」就答不上来——因为根本没做对照。你有完整的对照数据，而且结论是 AI 更差。

**加分话术**：

> 我原本想的是「规则打底、模型提升」，做完之后补了一组 Baseline 对照，结果发现加了 Isolation Forest 之后 F1 从 0.887 掉到 0.753。
>
> 我当时第一反应是想调参数把数字调好看，但后来觉得这样本末倒置了——实验的意义是回答「模型有没有用」，不是让数字好看。所以我去看了混淆矩阵，发现一件更有意思的事：两个版本的召回率完全一样，都是 0.896，模型只多抓到 1 个真异常，但多产生了 515 个误报。也就是说它不是「用误报换召回」，而是纯粹在制造噪音。
>
> 根因是 `contamination` 设成 0.05，相当于强制模型按 5% 的比例判异常，和真实分布不匹配。
>
> 我从这里学到的是，做算法之前先建 Baseline 是必要的——不然你不知道自己在和什么比。这个项目里更合理的路径其实是先把规则阈值从 3σ 往下调，因为漏检的那批样本刚好在 2.5σ，把规则本身的空间榨干再考虑上模型。

### 亮点二：一致性不是「说」出来的，是被约束和测试钉住的

**为什么差异化**：大部分候选人讲事件溯源停在概念，你能讲到「这条约束挡的是哪种失败」，而且有 Testcontainers 真库测试。

**加分话术**：

> 我讲一致性习惯按「挡什么」来讲，而不是按技术名词讲。
>
> 唯一约束挡的是并发写产生版本空洞；`command_log` 主键挡的是网络重试导致重复事件；消费去重表挡的是 Kafka at-least-once 的重复投递；版本单调守卫挡的是消息乱序导致状态倒退；读己写超时挡的是投影滞后时给用户返回过期数据。五个机制对应五种具体失败，少一个就有对应的洞。
>
> 而且幂等和一致性这两块我没用 mock 测，是用 Testcontainers 真起 PostgreSQL 跑端到端的——因为这两个特性的正确性完全依赖数据库的约束和事务行为，mock 掉数据库测出来的绿色是假的。

### 亮点三：失败路径是设计过的，不只有 happy path

**为什么差异化**：学生项目通常只有正常流程能跑通。你有六条明确的降级/恢复路径，而且代码里对每个已知上限都标了升级路径。

**加分话术**：

> 我觉得这个项目和我之前写的作业级项目最大的区别，是我花了不少时间在「出错怎么办」上。
>
> 具体有六处：Kafka 消费失败退避重试三次后进死信队列而不是丢掉或死循环；告警发布失败退避重试；WebSocket 断线重连后主动拉最近告警，按告警 ID 去重合并；Saga 编排器重启后从数据库的待审批单重放在途补偿；自然语言查询的大模型调用 8 秒超时自动降级成数据摘要；大模型没配置时意图识别降级成关键词匹配，主流程不受影响。
>
> 另外我有个习惯是把「我知道但故意没做」的地方在代码里标出来，写明当前上限和升级路径。比如 WebSocket 没做心跳剔除、规则引擎桥接是同步阻塞调用——这些不是漏掉的，是我判断个人项目阶段收益不够，但我知道它们在什么流量下会变成问题。

## 九、面试演练建议

### 最优先：把 benchmark 跑出来

这是投入产出比最高的一件事。项目现在缺的就是性能量化指标，而评测套件已经写好了，只差执行。找一台有 Docker 的机器（云服务器或同学电脑）：

```bash
docker compose up -d            # 先确认服务能起全
docker compose --profile bench run --rm bench
# 产出 eventguard-benchmark/out/benchmark-report.md
```

把报告里的 P95、吞吐、CDC 延迟、Saga 成功率抄进 [量化口径.md](量化口径.md) 的「可用」区，简历才能写这些数。**跑一次的收益超过再写一千行代码。** 跑之前先在本地确认服务能起来，别在服务器上现调。

### 四天练习计划

**第 1 天 · 话术**
只练 1 分钟版和 3 分钟版，录音回听。重点听两件事：有没有说「然后就……然后就……」，有没有在 30 秒内说出「事件溯源」。3 分钟版超时是常见问题，第二段（写侧）最容易讲飞，卡表练。

**第 2 天 · 高分题**
练 Q6（为什么两层锁）、Q9（AI 为什么更差）、Q11（涨 100 倍怎么办）。这三题是你的高分题，值得逐字打磨。Q9 尤其要练到自然——**说负结果时的语气不能像在道歉，要像在讲一个你想清楚了的结论**。

**第 3 天 · 承认边界**
把「这个我没做」「这个数我没测过」练到能平静说出口。学生最容易输在这里：一被追问就硬撑，撑不住整场信任崩掉。模板是「这块我没做，我的判断是……如果要做我会……」——承认 + 判断 + 方案，三段齐了就不减分。

**第 4 天 · 反向自查**
打开 `EventStoreJdbcImpl`、`OrderCommandHandler`、`OrderViewProjection`、`kafka_consumer.py` 这四个文件，逐个方法问自己「这行为什么这么写」。答不上来的地方，就是面试官现场翻代码时会打到的地方。

### 三个具体提醒

1. **别把 AI 部分放最前面讲。** 硬功夫在事件存储和一致性，AI 那块目前是负收益。开场讲事件溯源建立技术印象，AI 作为「我还做了效果验证」的加分项后置。
2. **主动交代 AI 辅助编码。** 现在面试官都会问。你的护城河是能解释每个决策的替代方案和代价——第四节的「为什么不选别的」就是为此准备的。含糊比承认更致命。
3. **准备一条 3 分钟能演示的路径**：登录 → 下单 → 看订单时间线（体现事件回放）→ 中文提问查统计 → 触发一笔异常看 WebSocket 实时告警。提前跑通并录屏，现场网络出问题时放录屏。逐场景脚本见 [demo-script.md](../使用指南/demo-script.md)。

核心职责与贡献：

1. 负责订单领域核心架构设计，基于 Event Sourcing + CQRS 实现事件追加、快照重建、读模型投影和历史状态回放；通过唯一约束、版本校验、命令幂等和读己写机制处理并发写入、重复请求与投影延迟问题。
2. 搭建 PostgreSQL WAL → Debezium → Kafka → Python 检测服务的事件处理链路，设计消费去重、版本单调守卫、失败重试和 DLT 机制，在 at-least-once 投递语义下保障消息可恢复、状态不倒退。
3. 设计规则、统计、Isolation Forest 与 HMM 组成的分层异常检测体系，并完成 Baseline 对照实验；定位出 Isolation Forest 在当前数据分布下 Recall 基本不变、误报显著增加的原因，形成可解释的模型选型结论。
4. 实现自然语言订单查询与异常根因分析能力，采用意图分类、参数抽取和模板执行约束查询范围，避免 LLM 直接生成 SQL；补充超时、未配置模型和调用失败降级，保证 AI 不可用时主业务仍可运行。
5. 完成 Saga 补偿、审批、WebSocket 告警推送、RBAC 和接口限流等业务治理能力，围绕重试、断线重连、权限拒绝和部分失败场景设计恢复路径，形成从异常发现到人工处置的闭环。
6. 建立覆盖后端、AI 服务和前端的自动化验证体系，累计 328 项测试通过，并使用 Testcontainers 验证真实 PostgreSQL 一致性；同时补齐 Prometheus/Grafana/Loki 观测、Docker Compose 部署和本地 IDE 调试方案，支持面试演示与持续迭代。
