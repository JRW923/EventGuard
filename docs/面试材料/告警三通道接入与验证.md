# EventGuard 监控指标与告警通道说明

> 面试材料：讲清 EventGuard「为什么监控、监控什么、怎么监控、原理是什么、各渠道消息长什么样」。不含接入步骤与运维坑（见其他文档）。

## 1. 为什么要监控

EventGuard 是「事件溯源 + 实时异常检测」系统，它本身就是用来发告警的——所以它自己挂了，用户**完全无感知**。监控的目的，是在用户发现之前主动暴露故障：

- **后端宕机**：`eventguard-server` 不可达 → 订单/异常页面打不开，且本系统产生的告警也发不出去（最危险）。
- **接口错误率过高**：5xx 占比超阈值 → 检测/查询请求在失败，异常漏报。
- **消费链路积压**：Kafka 消费 lag 过大 → 投影/补偿链路落后，异常检测告警延迟甚至丢失。
- **主机内存耗尽**：小机内存曾于 08-15 宕机（可用内存仅 ~10%），需提前预警避免重演。

一句话：**监控是为了让「告警系统」自身的可用性可被观测。**

## 2. 监控什么 / 哪些内容

| 监控对象 | 内容 | 数据来源 |
|---|---|---|
| 后端存活 | `eventguard-server` 是否可达（含其依赖的 DB） | Prometheus `up{job="eventguard-server"}`，来自对 `/actuator/prometheus` 的抓取 |
| 接口健康 | 5xx 错误率（5 分钟内占比） | `http_server_requests_seconds_count` |
| 消费积压 | Java 消费组 lag、Python AI 检测管道 lag | `kafka_consumer_fetch_manager_records_lag`、`eventguard_ai_consumer_lag` |
| 主机资源 | 可用内存占比 | `node_exporter` 的 `node_memory_MemAvailable_bytes` |
| 对外可达 | 公网 `/health` 是否返回 `status:UP`（后端 + DB 探活） | 外部 uptime 工具探 `https://eventguard.jrwdev.site/health` |

对应 **6 条告警规则**（`prometheus/alerts.yml`）：

| 告警名 | 级别 | 触发含义 |
|---|---|---|
| `EventGuardServerDown` | critical | server 连续 1 分钟不可达 |
| `EventGuardHighErrorRate` | warning | 5xx 占比 > 5% 持续 5 分钟 |
| `KafkaConsumerLagHigh` | warning | Java 消费组积压 > 1000 条持续 5 分钟 |
| `AIDetectorLagHigh` | warning | AI 检测管道某分区积压 > 1000 条持续 5 分钟 |
| `HostMemoryLow` | warning | 主机可用内存 < 20% 持续 2 分钟 |
| `HostMemoryCritical` | critical | 主机可用内存 < 10% 持续 1 分钟 |

## 3. 通过哪些方式监控

- **指标采集**：Prometheus 每 15s 抓取 `eventguard-server:8080/actuator/prometheus`、`eventguard-ai:8000/metrics`、`node-exporter:9100`。
- **规则判定**：`alerts.yml` 中的 PromQL 表达式每 15s 求值，持续超阈值（`for` 1~5 分钟）才触发，避免抖动误报。
- **通知分发**：告警推给 Alertmanager，由其扇出到 3 个渠道。
- **对外探活**：公网 `https://eventguard.jrwdev.site/health` 可被第三方 uptime 工具独立监控（SPA 各路由都返回 200 壳，故只探 `/health` 才有意义）。

## 4. 监控原理

端到端流水线：

```
Prometheus 定时 scrape(15s)
   → 指标存入 TSDB
   → 每 15s 用 alerts.yml 规则求值
   → 表达式持续为真超过 for 时长 → 产生 alert(firing)
   → 推送给 Alertmanager
   → Alertmanager 按 route 扇出到两个 receiver：
        • webhook  → 本机飞书中继 172.18.0.1:9102
        • email    → 163 邮箱(直接 SMTP)
   → 中继收到后，把同一条告警文本再转发给：飞书群机器人 + PushPlus(个人微信)
```

关键机制：
- **`for` 持续时间**：避免瞬时抖动误报（如 server 重启的 1 分钟空窗不会立刻告警）。
- **分组与静默窗口**：按 `alertname` 分组，`group_wait: 30s` 等待同组聚合后再发，`repeat_interval: 4h` 控制重复频率。
- **恢复通知**：`send_resolved: true`，告警解除时会再发一条 `resolved` 消息。
- **扇出语义**：父路由 receiver 仅作兜底，多通道必须都列为子路由并 `continue: true`，否则只发其中一个。

## 5. 每种渠道所有可能发送的消息类型及样子

三类渠道的消息**内容**都来自同一份告警数据（alertname / severity / summary / description），区别只在**包装格式**。因此「消息类型」由两维组合决定：
- **状态**：`firing`（触发）/ `resolved`（恢复）
- **级别**：`critical` / `warning`（由告警规则决定）

即：6 条告警 × {firing, resolved} = 每渠道最多 12 种内容（3 个渠道只是同一内容的不同外壳）。

### 5.1 飞书群机器人

- **格式**：文本消息（`msg_type=text`），由中继 `feishu-relay` 拼装。
- **所有可能类型**：`firing-critical` / `firing-warning` / `resolved`（按告警名与状态变化）。
- **长什么样**（中继实际拼接逻辑）：

触发（critical）示例：
```
[EventGuard 告警通知]
- 状态:firing 级别:critical
  摘要: EventGuard server 不可达
  详情: Prometheus 已连续 1 分钟无法抓取 eventguard-server（172.18.0.6:8080）
```

触发（warning）示例：
```
[EventGuard 告警通知]
- 状态:firing 级别:warning
  摘要: 主机可用内存低于 20%
  详情: 可用内存仅剩 18.3%，已低于 20% 预警线。请尽快释放内存或扩容，避免重演 08-15 宕机。
```

恢复（resolved）示例：
```
[EventGuard 告警通知]
- 状态:resolved 级别:critical
  摘要: EventGuard server 不可达
  详情: Prometheus 已连续 1 分钟无法抓取 eventguard-server（172.18.0.6:8080）
```

### 5.2 PushPlus（个人微信）

- **格式**：标题 + 正文。`title` 固定为 `EventGuard 告警`，`content` 为与飞书**完全相同**的那段文本（中继复用同一份 `build_text` 结果）。PushPlus 默认按 HTML 渲染，纯文本里的换行在微信里可能不换行。
- **所有可能类型**：与飞书一致（firing / resolved × critical / warning）。
- **长什么样**：

```
标题：EventGuard 告警
内容：
[EventGuard 告警通知]
- 状态:firing 级别:warning
  摘要: Java 消费组积压超过 1000 条
  详情: 消费者 consumer-0 积压 1320 条持续 5 分钟，投影/补偿链路可能落后，检查 DLT 与消费者日志。
```

### 5.3 163 邮箱

- **格式**：Alertmanager **默认邮件模板**（未自定义），含主题（Subject）与正文（Body）。
- **所有可能类型**：`firing`（主题带 `[FIRING:n]`，n 为同组触发条数）/ `resolved`（主题带 `[RESOLVED]`）。
- **长什么样**：

触发邮件：
```
主题：[FIRING:1] EventGuardServerDown

正文：
Labels:
 - alertname: EventGuardServerDown
 - instance: 172.18.0.6:8080
 - job: eventguard-server
Annotations:
 - description: Prometheus 已连续 1 分钟无法抓取 eventguard-server（172.18.0.6:8080）
 - summary: EventGuard server 不可达
```

恢复邮件：
```
主题：[RESOLVED] EventGuardServerDown

正文：
Labels:
 - alertname: EventGuardServerDown
 - instance: 172.18.0.6:8080
 - job: eventguard-server
Annotations:
 - description: Prometheus 已连续 1 分钟无法抓取 eventguard-server（172.18.0.6:8080）
 - summary: EventGuard server 不可达
```

> 邮件外观由 Alertmanager 默认模板决定，后续若要做成更易读的 HTML 表格，可在 `alertmanager.yml.tmpl` 中加自定义 `email` 模板，不影响其他两渠道。

## 6. 部署要点

- 监控与报警随 `docker compose up -d` 一起起来：Prometheus 抓指标；`alertmanager.yml.tmpl` 经 entrypoint `sed` 注入 SMTP/Webhook 占位符生成运行时配置（密钥只进 `.env` / `feishu.env`，均 gitignore）。
- 中继 `feishu-relay.service`（systemd）常驻，收 Alertmanager 的 webhook 后扇出到飞书 + PushPlus。
- ⚠ 改了 `alertmanager.yml.tmpl` 内容**不会**触发 compose 重建，需手动 `docker compose restart alertmanager` 让配置生效。

## 7. 排查要点

- **路由是否扇出**：`docker compose exec alertmanager amtool config routes test alertname=demo severity=info` 应返回 `webhook,email`。
- **飞书 / PushPlus 是否真发出**：`journalctl -u feishu-relay.service -n 20` 看 `PushPlus 返回` / `飞书返回`。
- **邮件是否发出**：Alertmanager 默认只在出错时打日志，无报错即发送成功；也可用相同凭据直接 `SMTP_SSL` 发一封验证。
- **两个常见坑**：① `.env` 的 `ALERT_WEBHOOK_URL` 必须指向本机中继 `http://172.18.0.1:9102/webhook`（曾误置成无效占位）；② 多通道必须都列为子路由且 `continue: true`，否则只发其中一个。

# 站点可用性监控（uptime-monitor）

> 与上面 EventGuard 内部告警**互补**的另一套监控：独立探测公网站点（`jrwdev.site` 的个人主页 / Synapse / 作品集）可用性，一旦页面不可用即通过**飞书群机器人 / PushPlus（个人微信）/ 163 邮箱**三路同时报警。它与 EventGuard 自身的告警链路完全独立，密钥单独放在 `/opt/uptime-monitor/config.json`（不在任何 git 仓库内）。下面按同样的结构说明。

## 1. 为什么要监控

- `jrwdev.site` 上的页面（个人主页、Synapse 网页版、作品集）是面向外部展示/使用的入口，挂了用户会直接看到白屏或报错，但没有任何内部系统会因此报警。
- 这类站点多由 Cloudflare 边缘托管、源站与 EventGuard 不在同一台机器，EventGuard 内部的 Prometheus 抓不到，需要一套**独立、轻量、对服务器零压力**的外部探活。
- 目标：页面不可用（或恢复）时，运维第一时间三路收到通知。

## 2. 监控什么 / 哪些内容

对 `config.json` 里列出的每个页面做一次 `HTTP GET`：

- 状态码 `>= 400` → 判定不可用（如 `HTTP 503`）。
- 若配置了 `keyword` 且响应体不含该关键字 → 判定不可用（防「200 但白屏」）。
- 连接超时 / 拒绝 / SSL 错误等异常 → 判定不可用，记录异常类型。

当前默认监控页面：`个人主页(https://jrwdev.site/)`、`Synapse Web(https://jrwdev.site/synapse-web.html)` 等（见 `config.json` 的 `pages`）。

## 3. 通过哪些方式监控

- **调度**：systemd timer 每 2 分钟拉起一次 `uptime-monitor.service`。
- **探测**：`monitor.py`（纯 Python 标准库，无第三方依赖）对每页 `HTTP GET`，与前次结果（`state.json`）比对。
- **报警**：仅在「状态翻转」时经三通道发信——飞书 webhook（带签名校验）、pushplus API（个人微信）、163 SMTP（SSL 465）。
- **轻量设计**：启动前随机抖动 15s、页面间留 1s、单页超时 10s 且只读前 200KB、无数据库无常驻进程（脚本跑完即退出）。

## 4. 监控原理

```
systemd timer(每2分钟)
   → uptime-monitor.service → monitor.py
        → 对每页 HTTP GET（带 UA、10s 超时、只读前 200KB）
        → 与 state.json 上次结果比对
        → 仅「状态翻转」时报警：
             • 新增故障（可用→不可用）：立即三路报警
             • 恢复（不可用→可用）：发恢复通知
             • 持续不可用：每 reminder_minutes(默认30) 分钟重报一次
        → 三通道：飞书(签名) / pushplus / 163(SSL465) 同时发送
```

关键机制：

- **只在翻转时报警**：避免同一故障反复刷屏，也避免恢复后静默。
- **持续重报**：持续不可用时按 `reminder_minutes` 周期再提醒，防止「报了一次就没人管」。
- **零压力**：timer 控节奏、随机抖动错峰、超时与体积上限，对目标站点和本机都近乎无感。

## 5. 每种渠道所有可能发送的消息类型及样子

三个通道与上文 EventGuard 告警**完全相同**（飞书 / PushPlus / 163），只是密钥各自独立配置。下面给出 `monitor.py` 实际拼接的消息样例（与 Alertmanager/relay 那套外壳不同）。

> 消息分两类：`站点可用性告警`（故障：含「新增故障」与「持续不可用」两种 bullet）与 `站点恢复通知`（恢复）。

### 5.1 飞书群机器人

- **格式**：文本消息（`msg_type=text`），`content.text` 为下方文本；签名校验同飞书机器人规则（`base64(hmac_sha256(key="timestamp\nsecret"))`）。
- **所有可能类型**：新增故障报警 / 持续不可用重报（同属「站点可用性告警」）/ 恢复通知。
- **样子**：

故障（新增 + 持续）示例：
```
【站点可用性告警】
时间：2026-08-20 13:00:00
以下页面不可用：
• 【新增故障】个人主页 (https://jrwdev.site/) — HTTP 503
• 【持续不可用】Synapse Web (https://jrwdev.site/synapse-web.html) — HTTP 503
请尽快排查。
```

恢复示例：
```
【站点恢复通知】
时间：2026-08-20 13:30:00
以下页面已恢复可用：
• 个人主页 (https://jrwdev.site/) — HTTP 200
```

### 5.2 PushPlus（个人微信）

- **格式**：`title` + `content`，`template: "txt"`（纯文本）。`title` 为 `站点可用性告警` 或 `站点恢复通知`，`content` 为与飞书**完全相同**的文本。
- **所有可能类型**：同飞书（故障 / 恢复）。
- **样子**：
```
标题：站点可用性告警
内容：
【站点可用性告警】
时间：2026-08-20 13:00:00
以下页面不可用：
• 【新增故障】个人主页 (https://jrwdev.site/) — HTTP 503
请尽快排查。
```

### 5.3 163 邮箱

- **格式**：纯文本邮件，`Subject` = `title`，`Body` = `content`（与飞书文本相同）。
- **所有可能类型**：`站点可用性告警`（故障）/ `站点恢复通知`（恢复）。
- **样子**：

故障邮件：
```
主题：站点可用性告警
正文：
【站点可用性告警】
时间：2026-08-20 13:00:00
以下页面不可用：
• 【新增故障】个人主页 (https://jrwdev.site/) — HTTP 503
• 【持续不可用】Synapse Web (https://jrwdev.site/synapse-web.html) — HTTP 503
请尽快排查。
```

恢复邮件：
```
主题：站点恢复通知
正文：
【站点恢复通知】
时间：2026-08-20 13:30:00
以下页面已恢复可用：
• 个人主页 (https://jrwdev.site/) — HTTP 200
```

## 6. 部署要点

- 纯标准库脚本 + systemd timer 每 2 分钟拉起：`systemctl enable --now uptime-monitor.timer`；改配置后 `daemon-reload` 即生效（timer 无需重启）。
- 页面列表与三通道密钥写在 `config.json`（含密钥，不进 git）。通道准备：飞书自定义机器人拿 webhook（+secret 签名）、pushplus 个人中心拿 token、163 开 SMTP 用授权码（**非登录密码**）。

## 7. 排查要点

- 先 `python3 monitor.py --dry-run` 看页面是否被判定 DOWN，不实际发信。
- 看 `monitor.log` 各通道响应（`飞书响应` / `pushplus响应` / `邮件已发送`）。
- 常见坑：飞书 `sign match fail` → secret 不一致（签名 `base64(hmac_sha256("timestamp\nsecret"))`）；163 登录失败 → 用了登录密码而非授权码；pushplus 非 200 → token/配额；SPA 用 keyword 易误报 → 改用健康检查接口或去掉 keyword。
