# EventGuard 告警通道接入与验证说明

> 用途：记录 EventGuard 生产栈「监控地址 + 三个报警通道」的补全过程、改动点与实测结果，作为面试材料中「可独立交付的运维/可观测性工作」的事实依据。

## 背景

EventGuard 页面与报警系统补齐「还差 4 样信息」即可真实启用：
1. 要监控的公网 URL（名称 + 地址）
2. 飞书群机器人报警通道
3. PushPlus（个人微信）报警通道
4. 163 邮箱报警通道

其中 2/3/4 要求「真实启用」——即发生告警时确实能收到通知，而不只是配置存在。

## 1. 监控公网 URL

EventGuard 是 SPA，各路由通常都返回同一个 200 的壳，单纯探路由区分不出「页面挂了」。因此**只监控健康检查接口最准**：

- **`https://eventguard.jrwdev.site/health`**（推荐，已实测存活）
  - 返回 `{"status":"UP","version":"0.1.0-SNAPSHOT","dependencies":{"db":"UP","kafka":"kafka:9092"}}`
  - 能验证后端 + 数据库都在线，比探 SPA 壳有意义
- `https://eventguard.jrwdev.site/`（兜底，仅验证壳）
  - 固定 200，只能证明 nginx/隧道活着，区分不出「后端挂了」

> 在线域名是 `eventguard.jrwdev.site`（经 Cloudflare Tunnel 出网绕过未备案 Host 拦截），不是根域名 `jrwdev.site`/`www.jrwdev.site`。

## 2. 三个报警通道

最终架构：**一条告警经 Alertmanager 扇出到两个 receiver** —— `webhook`（本机飞书中继，再由中继扇出到飞书 + PushPlus）和 `email`（163 邮箱）。

| 通道 | 接入方式 | 状态 |
|---|---|---|
| 飞书群机器人 | `feishu-relay` 中继（监听 docker 网桥网关 `172.18.0.1:9102`）收 Alertmanager webhook，转飞书格式外发 | ✅ 已确认机器人在群内 |
| PushPlus（个人微信） | 复用同一中继，收到告警时一并 POST 到 `https://www.pushplus.plus/send` | ✅ 已实测 `code:200 执行成功` |
| 163 邮箱 | Alertmanager 原生 `email_configs`（SMTP `smtp.163.com:465`） | ✅ 已实测 SMTP_SSL 登录+发送成功 |

> 设计取舍：PushPlus 的 API 格式与 Alertmanager 自带 webhook 格式不兼容，没有另起服务，而是**复用现有 `feishu-relay` 中继**在收到告警时一并转发，Alertmanager 侧零改动。邮箱走 Alertmanager 原生能力，无需中继。

## 3. 改动清单（均无明文密码入库）

| 文件 | 改动 |
|---|---|
| `feishu-relay/relay.py` | 新增 `PUSHPLUS_TOKEN` 支持与 `send_to_pushplus()`；飞书发送结果改为记录返回（此前成功/失败都不打日志，是盲区） |
| `feishu-relay/feishu.env`（gitignore） | 追加 `PUSHPLUS_TOKEN` |
| `prometheus/alertmanager.yml.tmpl` | 新增 `global` SMTP 占位块、`email` receiver、双通道扇出路由 |
| `docker-compose.yml` | alertmanager 的 `environment` 增加 `SMTP_*` 变量、entrypoint `sed` 增加对应占位符替换 |
| `.env`（gitignore） | 增加 `EG_SMTP_PASSWORD`；**修正** `ALERT_WEBHOOK_URL`（曾被误设为无效占位 `http://127.0.0.1:65534/alert`，已改回中继 `http://172.18.0.1:9102/webhook`） |

凭据安全：SMTP 授权码只在 `.env`、飞书/PushPlus token 只在 `feishu.env`，二者均已被 `.gitignore` 忽略，不进仓库。运行时由 compose `environment` 注入、entrypoint `sed` 替换占位符生成带密配置，仓库跟踪的 `alertmanager.yml.tmpl` 只含占位符。

## 4. 两个生产坑（已按 runbook 处理）

1. **bind-mount 配置不自动重建**：改了 `alertmanager.yml.tmpl` 内容不会触发 `docker compose up` 重建（compose 只在配置哈希变化时重建）。需手动 `docker compose restart alertmanager` 让 entrypoint 重新读模板生成配置。
2. **Alertmanager 扇出路由语义**：父路由的 `receiver` 仅在「没有任何子路由命中」时作兜底；只要子路由命中，父路由 receiver 就被丢弃。所以「一条告警发多个通道」必须**把两个 receiver 都列为子路由并加 `continue: true`**，父路由仅作占位。已用 `amtool config routes test` 验证返回 `webhook,email`。

## 5. 实测结果

- **飞书**：直接打 webhook 返回 `code:0`（机器人仍在群内）；webhook 通知链路已真实触发（PushPlus 收到即证明 alertmanager→中继链路通）。
- **PushPlus**：中继日志 `{"code":200,"msg":"执行成功"}`。
- **163 邮箱**：用相同凭据直接 `SMTP_SSL` 登录 + 发信成功，163 已接受。

验证期间向飞书群、PushPlus、163 邮箱各发了 1~2 条标注「自检」的测试告警，已全部 resolve，不会重复发送。

## 6. 复现验证步骤（他人可照做）

```bash
# 1) 确认中继在跑且带 PUSHPLUS_TOKEN
systemctl is-active feishu-relay.service
tr '\0' '\n' < /proc/$(pgrep -f feishu-relay/relay.py | head -1)/environ | grep PUSHPLUS_TOKEN

# 2) 确认 Alertmanager 路由扇出到 webhook+email
docker compose exec -T alertmanager amtool config routes test --config.file=/etc/alertmanager/alertmanager.yml alertname=demo severity=info

# 3) 发一条测试告警，等待 group_wait(30s) 后查三通道
curl -XPOST http://localhost:9093/alerts/api/v2/alerts -H 'Content-Type: application/json' \
  -d '[{"labels":{"alertname":"三通道自检","severity":"info"},"annotations":{"summary":"自检"}}]'
journalctl -u feishu-relay.service -n 20 --no-pager   # 看 PushPlus/飞书返回
# 邮箱：登录 19913823585@163.com 收件箱确认
```
