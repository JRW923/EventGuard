# EventGuard 监控指标与告警通道说明

> 面试材料：讲清 EventGuard「为什么监控、监控什么、怎么监控、原理是什么、各渠道消息长什么样」。不含接入步骤与运维坑（见其他文档）。

## 1. 为什么要监控

EventGuard 是「事件溯源 + 实时异常检测」系统，它本身就是用来发告警的——所以它自己挂了，用户**完全无感知**。监控的目的，是在用户发现之前主动暴露故障：

- **后端宕机**：`eventguard-server` 不可达 → 订单/异常页面打不开，且本系统产生的告警也发不出去（最危险）。
- **接口错误率过高**：5xx 占比超阈值 → 检测/查询请求在失败，异常漏报。
- **消费链路积压**：Kafka 消费 lag 过大 → 投影/补偿链路落后，异常检测告警延迟甚至丢失。
- **主机内存耗尽**：小机内存曾于 08-15 宕机（可用内存仅 ~10%），需提前预警避免重演。

一句话：**监控是为了让「告警系统」自身的可用性可被观测。**

## 2. 监控什么 / 哪些内容

| 监控对象 | 内容 | 数据来源 |
|---|---|---|
| 后端存活 | `eventguard-server` 是否可达（含其依赖的 DB） | Prometheus `up{job="eventguard-server"}`，来自对 `/actuator/prometheus` 的抓取 |
| 接口健康 | 5xx 错误率（5 分钟内占比） | `http_server_requests_seconds_count` |
| 消费积压 | Java 消费组 lag、Python AI 检测管道 lag | `kafka_consumer_fetch_manager_records_lag`、`eventguard_ai_consumer_lag` |
| 主机资源 | 可用内存占比 | `node_exporter` 的 `node_memory_MemAvailable_bytes` |
| 对外可达 | 公网 `/health` 是否返回 `status:UP`（后端 + DB 探活） | 外部 uptime 工具探 `https://eventguard.jrwdev.site/health` |

对应 **6 条告警规则**（`prometheus/alerts.yml`）：

| 告警名 | 级别 | 触发含义 |
|---|---|---|
| `EventGuardServerDown` | critical | server 连续 1 分钟不可达 |
| `EventGuardHighErrorRate` | warning | 5xx 占比 > 5% 持续 5 分钟 |
| `KafkaConsumerLagHigh` | warning | Java 消费组积压 > 1000 条持续 5 分钟 |
| `AIDetectorLagHigh` | warning | AI 检测管道某分区积压 > 1000 条持续 5 分钟 |
| `HostMemoryLow` | warning | 主机可用内存 < 20% 持续 2 分钟 |
| `HostMemoryCritical` | critical | 主机可用内存 < 10% 持续 1 分钟 |

## 3. 通过哪些方式监控

- **指标采集**：Prometheus 每 15s 抓取 `eventguard-server:8080/actuator/prometheus`、`eventguard-ai:8000/metrics`、`node-exporter:9100`。
- **规则判定**：`alerts.yml` 中的 PromQL 表达式每 15s 求值，持续超阈值（`for` 1~5 分钟）才触发，避免抖动误报。
- **通知分发**：告警推给 Alertmanager，由其扇出到 3 个渠道。
- **对外探活**：公网 `https://eventguard.jrwdev.site/health` 可被第三方 uptime 工具独立监控（SPA 各路由都返回 200 壳，故只探 `/health` 才有意义）。

## 4. 监控原理

端到端流水线：

```
Prometheus 定时 scrape(15s)
   → 指标存入 TSDB
   → 每 15s 用 alerts.yml 规则求值
   → 表达式持续为真超过 for 时长 → 产生 alert(firing)
   → 推送给 Alertmanager
   → Alertmanager 按 route 扇出到两个 receiver：
        • webhook  → 本机飞书中继 172.18.0.1:9102
        • email    → 163 邮箱(直接 SMTP)
   → 中继收到后，把同一条告警文本再转发给：飞书群机器人 + PushPlus(个人微信)
```

关键机制：
- **`for` 持续时间**：避免瞬时抖动误报（如 server 重启的 1 分钟空窗不会立刻告警）。
- **分组与静默窗口**：按 `alertname` 分组，`group_wait: 30s` 等待同组聚合后再发，`repeat_interval: 4h` 控制重复频率。
- **恢复通知**：`send_resolved: true`，告警解除时会再发一条 `resolved` 消息。
- **扇出语义**：父路由 receiver 仅作兜底，多通道必须都列为子路由并 `continue: true`，否则只发其中一个。

## 5. 每种渠道所有可能发送的消息类型及样子

三类渠道的消息**内容**都来自同一份告警数据（alertname / severity / summary / description），区别只在**包装格式**。因此「消息类型」由两维组合决定：
- **状态**：`firing`（触发）/ `resolved`（恢复）
- **级别**：`critical` / `warning`（由告警规则决定）

即：6 条告警 × {firing, resolved} = 每渠道最多 12 种内容（3 个渠道只是同一内容的不同外壳）。

### 5.1 飞书群机器人

- **格式**：文本消息（`msg_type=text`），由中继 `feishu-relay` 拼装。
- **所有可能类型**：`firing-critical` / `firing-warning` / `resolved`（按告警名与状态变化）。
- **长什么样**（中继实际拼接逻辑）：

触发（critical）示例：
```
[EventGuard 告警通知]
- 状态:firing 级别:critical
  摘要: EventGuard server 不可达
  详情: Prometheus 已连续 1 分钟无法抓取 eventguard-server（172.18.0.6:8080）
```

触发（warning）示例：
```
[EventGuard 告警通知]
- 状态:firing 级别:warning
  摘要: 主机可用内存低于 20%
  详情: 可用内存仅剩 18.3%，已低于 20% 预警线。请尽快释放内存或扩容，避免重演 08-15 宕机。
```

恢复（resolved）示例：
```
[EventGuard 告警通知]
- 状态:resolved 级别:critical
  摘要: EventGuard server 不可达
  详情: Prometheus 已连续 1 分钟无法抓取 eventguard-server（172.18.0.6:8080）
```

### 5.2 PushPlus（个人微信）

- **格式**：标题 + 正文。`title` 固定为 `EventGuard 告警`，`content` 为与飞书**完全相同**的那段文本（中继复用同一份 `build_text` 结果）。PushPlus 默认按 HTML 渲染，纯文本里的换行在微信里可能不换行。
- **所有可能类型**：与飞书一致（firing / resolved × critical / warning）。
- **长什么样**：

```
标题：EventGuard 告警
内容：
[EventGuard 告警通知]
- 状态:firing 级别:warning
  摘要: Java 消费组积压超过 1000 条
  详情: 消费者 consumer-0 积压 1320 条持续 5 分钟，投影/补偿链路可能落后，检查 DLT 与消费者日志。
```

### 5.3 163 邮箱

- **格式**：Alertmanager **默认邮件模板**（未自定义），含主题（Subject）与正文（Body）。
- **所有可能类型**：`firing`（主题带 `[FIRING:n]`，n 为同组触发条数）/ `resolved`（主题带 `[RESOLVED]`）。
- **长什么样**：

触发邮件：
```
主题：[FIRING:1] EventGuardServerDown

正文：
Labels:
 - alertname: EventGuardServerDown
 - instance: 172.18.0.6:8080
 - job: eventguard-server
Annotations:
 - description: Prometheus 已连续 1 分钟无法抓取 eventguard-server（172.18.0.6:8080）
 - summary: EventGuard server 不可达
```

恢复邮件：
```
主题：[RESOLVED] EventGuardServerDown

正文：
Labels:
 - alertname: EventGuardServerDown
 - instance: 172.18.0.6:8080
 - job: eventguard-server
Annotations:
 - description: Prometheus 已连续 1 分钟无法抓取 eventguard-server（172.18.0.6:8080）
 - summary: EventGuard server 不可达
```

> 邮件外观由 Alertmanager 默认模板决定，后续若要做成更易读的 HTML 表格，可在 `alertmanager.yml.tmpl` 中加自定义 `email` 模板，不影响其他两渠道。
