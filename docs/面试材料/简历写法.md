## 最终简历描述（可直接粘贴）

**项目描述**：面向电商订单全生命周期的追溯与异常治理场景，区别于仅保存最终状态的传统订单平台，将每次状态变更沉淀为可回放、可审计的事件，并结合实时异常检测、告警分析、人工补偿和运营查询，实现从订单追溯到异常处置的闭环

**核心方案**：

**重构订单写入为事件溯源**：针对状态覆盖、并发冲突和重复入账，以不可变事件记录状态，采用唯一约束、版本校验和重试保证安全；通过commandId和command_log去重，每100个事件生成快照。重复提交不新增事件，重建仅回放增量数据

**完善读写分离异步读模型**：针对投影重复、乱序和数据滞后，引入消费去重表、版本守卫、投影通知、50毫秒兜底轮询和2秒超时机制；重复消息不重复更新，乱序不覆盖新状态；资源受限单机30写并发验收中，110/157个带版本校验的读己写请求窗口内追平

**搭建数据库变更捕获链路**：针对数据库与消息发布双写不原子，通过Debezium读取PostgreSQL WAL并写入Kafka，消费端采用手动提交、3次重试和死信队列；数据库宕机或Kafka暂停后均在2秒内恢复，已提交事件零丢失

**设计可降级的智能查询与处置闭环**：针对LLM生成查询语句的注入风险、超时和告警无处置，采用意图分类、参数抽取和模板接口，8秒超时降级摘要；8个查询场景结果均正确，支付重试超限与库存失败两类补偿均成功，高风险操作进入人工审批

## 简历数字口径（不变，面试前必须能解释）

- `52.39 组下单+支付业务迭代/s、95 分位延迟 1262ms、错误率 0%`：关闭接口限流后的 30 写并发资源受限负载验收结果，不与低并发功能评测延迟混用。
- 离线规则基线 F1 `0.887`，叠加 Isolation Forest 后 `0.753`：不能表述为智能模型带来提升。
- `328 项测试`：后端 + 智能服务 + 前端通过数之和（最新一轮：后端 172、AI 127、前端 39），不代表覆盖率。
- `110/157`：30 写并发验收中携带版本断言的读己写抽样在 2 秒窗口内追平的数量，其余如实返回 409。
- 项目无真实生产用户与业务流量，不使用「生产运行」「服务 N 个用户」等表述。

## 本轮代码改动带来的表述升级点（面试可讲）

1. 读己写不再阻塞 Web 线程：投影事务提交后经进程内通知器唤醒等待请求，Controller 以 DeferredResult 返回；50 毫秒轮询降级为共享单线程兜底。
2. 金额基线 R001 的标准差从「均值 10% 估计」改为数据库 `stddev_pop` 真实统计（90 天窗口 + 30 秒 TTL 缓存），「3σ」表述从此字面为真。
3. HMM 序列级检测已接入线上链路（此前仅离线）；Saga 金额缺失直接进重试/DLT，不再退 0 元绕过审批。
4. 告警持久化到 `anomaly_alerts` 表（重启可查），DLT 改纯字符串编码并新增管理端重放接口；Kafka 消费积压指标 + 告警规则已就位（线上数字待服务器实测回填）。
