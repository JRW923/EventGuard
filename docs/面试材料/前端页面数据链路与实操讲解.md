# EventGuard 前端页面数据链路与面试实操讲解

> 用途：面试前熟悉项目、面试中边操作边解释。
>
> 覆盖范围：`eventguard.jrwdev.site` 在线站点与当前仓库 `eventguard-ui`、`eventguard-server`、`eventguard-ai` 的实际实现。
>
> 核对日期：2026-08-25。在线演示环境以管理员账号进入控制台后，订单读模型可看到预置订单；异常看板和审批队列当时为空，但 WebSocket 状态为已连接。指南文案中的“预置 6 条告警”属于演示数据说明，不代表每一时刻数据库都一定有告警。

---

## 1. 先用一句话讲清系统

EventGuard 不是“订单表 + 操作日志”的后台，而是一条事件驱动的运营闭环：

```text
浏览器 Vue 3
  -> Java REST / WebSocket（JWT/RBAC）
  -> 命令侧校验聚合并追加 PostgreSQL domain_events
  -> Debezium 读取 PostgreSQL WAL
  -> Kafka domain-events
      -> order-view-projection -> order_view（查询读模型）
      -> eventguard-ai -> anomaly-alerts
      -> saga-trigger -> 补偿/审批
  -> Java anomaly consumer -> anomaly_alerts（历史表）+ WebSocket
  -> 前端异常看板、时间线、AI 查询、补偿审批
```

### 1.1 整条链路每一跳的真实技术栈

上面图中每个节点背后实际是什么，逐跳展开（均已核对当前仓库）：

**前端 `eventguard-ui`（Vue 3 单页应用）**

- Vue 3 + TypeScript + Vite 构建；UI 组件用 Element Plus，图表用 vue-echarts，路由 vue-router 4。
- 数据获取两条通道：axios 封装（`src/api/http.ts`，统一带 JWT、401/403 拦截）调 REST；原生 `WebSocket` 连 `/ws/anomalies`（`src/composables/useAnomalyWebSocket.ts`）收实时告警，断线重连后调 `/alerts/recent` 补拉、按 `anomaly_id` 去重。
- 登录态是 `reactive` 模块单例（`src/stores/auth.ts`），刻意没用 Pinia——只有一个全局登录态，token/user 持久化 localStorage，权限断言走 `hasPermission()` 供路由守卫和 `v-permission` 指令复用。
- 测试：vitest 组件/API 测试 + vue-tsc 类型检查。

**后端 `eventguard-server`（Java 单体）**

- Java 17 + Spring Boot 3.3.2，单 Maven 模块。REST 用 spring-boot-starter-web，实时推送用 starter-websocket。
- 数据访问是 starter-jdbc + `JdbcTemplate` 直写 SQL——没有 MyBatis/JPA，事件溯源的追加和读模型投影都是显式 SQL。
- 安全：jjwt 签发/校验 JWT（claims 含 roles、permissions、tokenVersion），spring-security-crypto 提供 BCrypt；真正鉴权在 `AuthFilter` 每请求做，并比对数据库 `token_version`。
- 运维面：actuator + micrometer-registry-prometheus 暴露指标；集成测试用 Testcontainers 起 PostgreSQL/Kafka。

**数据与事件层**

- PostgreSQL 16：`domain_events` 事件表是唯一事实源，`order_view` 读模型、`anomaly_alerts` 历史表都是派生数据（建库脚本在 `postgres-init/`）。
- Debezium Server 2.6：独立进程读 PostgreSQL WAL 做 CDC，不是 Kafka Connect 集群方式（配置在 `debezium/`）。
- Kafka（Confluent cp-kafka 7.6.0）：`domain-events` topic，至少一次投递；重复由消费端 `idempotent_consumer` 表、版本守卫兜住。

**AI 服务 `eventguard-ai`（Python）**

- FastAPI + uvicorn 提供 AI REST 接口；kafka-python 消费 `domain-events`，检测结果写回并触发告警。
- 检测用 scikit-learn + hmmlearn（机器学习/隐马尔可夫模型），非规则硬编码；PyJWT 校验 token，prometheus-client 暴露指标，pytest + pytest-asyncio 测试。

**链路之外的支撑组件（docker-compose.yml）**

- 可观测：Prometheus + node-exporter + alertmanager、Grafana + Loki + Promtail（指标、日志、告警全套）。
- 混沌与压测：`eventguard-chaos/` 是 bash 脚本 + pumba 容器注入（杀库、暂停 Kafka、给 AI 注入延迟）；`eventguard-benchmark/` 是 Python 压测。
- 通知与网关：`feishu-relay/`（Python 单文件）把告警转发飞书；Caddy 2 做反向代理/TLS，cloudflared 隧道暴露公网；kafka-ui、Adminer 是调试入口。

面试讲法：不必背全清单，按链路顺序各说一个代表词即可——“Vue 3 + WebSocket、Spring Boot 3 + JdbcTemplate、PostgreSQL 事件表、Debezium CDC、Kafka、FastAPI + 机器学习”，其余在被追问时展开。

核心原则：

1. `domain_events` 是订单事实的唯一来源；`order_view`、快照、告警列表都是派生数据。
2. 前端只负责展示、参数采集和人工确认，不是安全边界；真正权限校验在 Java 和 Python 后端。
3. AI 做检测、分类、解释、预测和只读工具调用，不直接生成 SQL，也不直接执行退款；写动作必须经过 Java 白名单、权限和审批。
4. Kafka 至少一次投递，消费端用 `idempotent_consumer`、版本守卫和状态条件更新处理重复消息。

## 2. 从线上入口开始讲

### 2.1 落地页 `/`

**页面显示与交互**

- 顶部品牌、`核心能力`、`项目技术栈`、`体验账号`锚点导航。
- Hero：EventGuard 事件卫士、事件溯源/异常检测/NL 查询简介、`进入系统/返回控制台`、`查看体验指南`。
- 六张核心能力卡：事件溯源+回放、CDC 实时管道、AI 异常检测、中文 NL 查询、Saga 自动补偿、根因分析+RBAC。
- 技术栈分组：Java 服务端、事件与数据、AI 服务、前端体验、交付与观测。
- 三个体验账号卡：admin、operator、viewer。密码默认模糊显示，点击密码切换显隐，`复制`调用 Clipboard API。
- `Starfield` 是纯前端 Canvas/动画背景，不产生业务数据；卡片 pointermove 只改变 CSS transform。

**代码与数据来源**

- 页面：`eventguard-ui/src/views/Landing.vue`。
- Logo/图片：`eventguard-ui/public/brand/logo-2.png` 等静态资源，Vite/Nginx 直接提供。
- 文案、能力数组、技术栈数组、演示账号数组均是组件内常量，不来自后端。
- `auth.isAuthenticated` 来自 `src/stores/auth.ts`；有 token 时按钮显示“返回控制台”，点击跳 `/orders`，否则跳 `/login`。
- 密码复制优先 `navigator.clipboard.writeText`，失败时使用隐藏 textarea + `document.execCommand('copy')`。

**面试讲法**

> 这个页面是公开的产品入口，刻意不请求业务 API，保证后端不可用时也能介绍产品。账号卡是演示辅助，不是认证数据源；真正登录仍由 `/auth/login` 校验 BCrypt 密码。登录后按钮根据 localStorage 中 token 切换为返回控制台。

### 2.2 体验指南 `/guide`

页面同样是 standalone 页面，不套控制台壳。步骤、数据流图、亮点、角色建议、FAQ 和账号密码均为 `Guide.vue` 内静态配置；按钮只负责锚点滚动、复制密码和跳转登录/订单页。

这里有一个适合面试主动说明的事实：指南描述的是“演示能力和预置数据策略”，线上数据会被重置、归档或被其他体验者操作，因此“指南写有告警”不等于当前告警接口一定返回数据。应以 `/alerts/recent` 和 WebSocket 实时状态为准。

### 2.3 登录 `/login`

**链路**

```text
点击演示账号/输入账号密码
  -> Login.vue 校验非空
  -> auth.login()
  -> POST /auth/login {username,password}
  -> AuthService：限流/锁定检查 -> UserRepository 查用户 -> BCrypt.matches
  -> AuditLogger 写 LOGIN_OK 或 LOGIN_FAILED
  -> JwtService.issue：uid、username、roles、permissions、mustChangePassword、tokenVersion
  -> 返回 {token,user}
  -> 前端写 localStorage: eg_token / eg_user
  -> router.push(redirect || /orders)
```

- 前端 API：`src/api/auth.ts`；状态单例：`src/stores/auth.ts`；令牌存取：`src/api/token.ts`。
- 后端公开端点：`AuthController.login`；认证服务：`auth/service/AuthService.java`。
- 密码是 BCrypt 哈希，不在数据库存明文。登录失败会进入内存防爆破计数和审计日志。
- `mustChangePassword=true` 时弹出强制改密对话框，调用 `POST /auth/password`；成功后刷新 `/auth/me`，再清除本地会话，要求重新登录。
- 路由若带 `?redirect=/orders/...`，登录后回到原目标页；没有则进入订单中心。
- HTTP 401 响应拦截器会清理 token/user，并跳回登录页；403 只提示权限不足。

**面试实操**

1. 点 `operator` 快速填充，说明前端只是填表，不绕过后端。
2. 登录后打开浏览器 Application 只能解释“前端持久化 JWT”，不要把 localStorage 当成可信权限来源。
3. 强调 Java `AuthFilter` 每次请求解析 JWT，并比对数据库 `token_version`；改密或退出所有设备会递增版本，让旧 token 失效。

## 3. 控制台公共壳层与全局数据链路

文件：`eventguard-ui/src/App.vue`、`src/router/index.ts`、`src/api/http.ts`。

### 3.1 路由与页面壳

- Vue Router 使用 `createWebHashHistory()`，线上 URL 形如 `/#/orders`。Hash 不会发送给 Nginx，刷新深链不会被后端当作 `/orders` API，从而避免 SPA 刷新 401/404。
- `meta.standalone=true` 的 `/`、`/guide` 直接渲染页面；其余页面套侧栏、顶栏、主内容和页脚。
- 全局守卫：公开页放行；未登录访问受保护页跳 `/login?redirect=...`；已登录但缺 `meta.permission` 跳 `/403`；刷新时只有 token 没有 user，会调用 `/auth/me`。
- 侧栏菜单按 `auth.hasPermission()` 过滤，按钮级用 `v-permission` 删除 DOM。两者只是用户体验控制，后端仍强制鉴权。

### 3.2 HTTP 客户端

`src/api/http.ts` 创建 Axios：

- `VITE_API_BASE_URL` 非空时使用显式后端地址，否则同源走 Nginx/Vite proxy。
- 请求拦截器从 `eg_token` 加 `Authorization: Bearer <JWT>`。
- 401 清会话并统一跳登录；403 记录权限错误；其他错误由 `friendlyError()` 映射为中文提示。
- 默认超时 10 秒；`/ai/heal` 单独放宽到 30 秒，后端自身还有 45/120 秒业务超时。

### 3.3 顶栏运行状态

`App.vue` 挂载后调用 `GET /health`。返回 `status/version/dependencies`，映射为侧栏“服务运行正常”、顶栏 `Live/Offline`、页脚版本和数据库状态。它不是业务数据，也不等价于 Kafka/AI 全链路健康；它主要反映 Java 服务健康接口。

## 4. 订单中心 `/orders`

### 4.1 页面组件

- 状态筛选：全部、`PENDING_PAYMENT`、`PAYMENT_FAILED`、`PAID`、`CONFIRMED`、`SHIPPED`、`DELIVERED`、`CLOSED`、`CANCELLED`、`REFUNDED`。
- 订单表：订单 ID、状态、金额、事件版本、更新时间、按需 AI 预测、事件时间线。
- `新建订单`按钮只对 `order:create` 可见；分页默认 20 条；`刷新`重新拉取。
- 金额、状态颜色、时间格式都是前端展示转换，原始字段来自 API。

### 4.2 查询链路

```text
OrderList.vue onMounted/loadData
  -> GET /orders?status&page&size
  -> OrderQueryController（order:read）
  -> OrderQueryService
  -> OrderViewRepository 查询 order_view
  -> {orders,total,page,size}
  -> Vue 表格渲染
```

`order_view` 是 Kafka 投影读模型，不是事实表。列表的 `version` 是该订单投影到的事件版本，`updatedAt` 是投影更新时间。

### 4.3 新建订单为什么要轮询

```text
点击新建 -> POST /orders + X-Command-Id: crypto.randomUUID()
  -> OrderCommandController（order:create）
  -> OrderCommandHandler
  -> OrderAggregate 校验状态/金额
  -> EventStoreJdbcImpl 事务追加 OrderCreatedEvent
  -> command_log 保存幂等结果
  -> PostgreSQL commit
  -> 返回 orderId/version
  -> Debezium WAL -> Kafka domain-events
  -> order-view-projection 更新 order_view
```

写成功和读模型可见之间存在 CDC 异步延迟。前端 `waitForOrder()` 每 400ms 调 `GET /orders/{id}`，最多 10 次，确认投影已经出现后再刷新列表；这解决“创建成功但马上刷新看不到”的最终一致性问题。后端对带 `expectedVersion` 的读还提供 2 秒读己写等待和 409“读模型同步中”。

### 4.4 幂等与并发的面试重点

- `X-Command-Id` 是客户端幂等键；相同 commandId + 相同请求指纹复用第一次结果，不重复追加事件。
- PostgreSQL `UNIQUE(aggregate_id,event_version)` 是最终并发底线。
- 应用层版本检查用于更早、更可读地返回冲突；事务 advisory lock 串行化同一命令并发。
- 事件落库和 command_log 在同一事务；Kafka 不由应用双写，而由 Debezium 读取已提交 WAL。

### 4.5 AI 预测按钮

点击某一行的 `预测`：

```text
AiApi.predict(orderId)
  -> GET /ai/predict/{aggregate_id}
  -> Python require_permission('ai:query') 校验 JWT
  -> OrderPredictor 读取该订单事件序列并调用 predictor.pkl/scaler.pkl
  -> 返回 outcome、confidence、risk
  -> 前端按 LOW/MEDIUM/HIGH 显示绿色/黄色/红色标签
```

预测是按需加载，不在列表首屏批量调用；模型缺失时返回 `prediction=null` 和可读消息。watchlist 接口会过滤 `CLOSED/CANCELLED` 终态订单并按风险排序，但当前前端菜单没有独立 watchlist 页面。

## 5. 订单事件时间线 `/orders/:id/timeline`

### 5.1 数据来源

```text
OrderTimeline.vue onMounted
  -> GET /orders/{id}/events?upToVersion=N
  -> OrderQueryController
  -> OrderQueryService.getEvents
  -> EventStoreJdbcImpl 查询 domain_events
  -> EventDto[]（version,eventType,createdAt,payload）
  -> EventTimeline.vue
```

这里故意直接读 `domain_events`，因为时间线是审计/回放功能，不能依赖可能短暂落后的 `order_view`。

### 5.2 图表和回放逻辑

- `EventTimeline.vue` 用 ECharts `LineChart`，x 轴是事件类型，y 轴是事件版本；数据按 `version` 升序排序。
- Tooltip 显示事件类型、版本、时间和 JSON payload；下方表格显示完整 payload。
- `按版本回放` 将 `upToVersion` 传给后端，得到版本截断的事件序列；`重置`清空参数重新读取全部事件。
- 当前实现是“事件范围回放”，不是将任意版本状态完整重建成一个新状态卡片；面试中应明确这是已实现边界，完整状态重建是自然升级项。

### 5.3 为什么这是 Event Sourcing 的证明页面

> 如果只有订单当前表，无法解释“为什么现在是 PAID”。时间线展示的是不可变事件序列，状态是事件折叠的结果；快照只用于优化重建，删除快照仍可以从事件重放。

## 6. 异常看板 `/anomalies`

### 6.1 首屏与实时链路

```text
useAnomalyWebSocket()
  -> wss://当前域名/ws/anomalies?token=<JWT>
  -> JwtHandshakeInterceptor 校验 token + anomaly:view
  -> Java AnomalyWebSocketHandler 保存会话

eventguard-ai Kafka consumer
  -> 消费 domain-events
  -> 事件级规则/Isolation Forest + 流程级规则/HMM
  -> 发布 anomaly-alerts
  -> Java AnomalyAlertConsumer
  -> anomaly_alerts 历史表落库
  -> WebSocket broadcast
  -> AnomalyDashboard.alerts.unshift()
```

浏览器 WebSocket 不能方便地加自定义 Authorization header，所以 token 放在握手 query 参数；HTTPS 页面自动使用 `wss` 防止 mixed content。

### 6.2 断线、重连、去重

- `onopen` 后调用 `GET /alerts/recent` 补拉服务端环形历史，弥补断线期间丢失的消息。
- WS 推送和补拉共用 `seen` anomaly_id 集合；按 `detected_at` 合并排序，前端最多保留 100 条。
- 断线固定 3 秒重连；这是当前单实例演示实现，生产升级可用指数退避和 Redis Pub/Sub 广播。
- 后端先历史落库再广播；落库失败抛异常进入 Kafka 重试/DLT，避免只推到浏览器却没有审计记录。

### 6.3 明细/聚合模式

- 明细表直接展示 `anomaly_id、rule_id、level、description、detected_at`。
- 聚合模式完全由前端计算：按 `rule_id|aggregate_id` 分组，得到命中次数、首次时间、最近时间和代表告警；不是额外后端聚合 API。
- `ERROR/WARN/INFO` 映射为 danger/warning/info。
- `查看根因`打开对话框，先调用 `GET /anomalies/{id}/analysis`。

### 6.4 规则与模型来源

- Java 规则桥接：金额偏差 R001、重复支付 R002、状态跳变 R003、高频 R004、库存溢出 R005，读取事件上下文和历史基线。
- Python 检测消费 `domain-events`，`EventLevelService` 组合规则优先和 Isolation Forest；`ProcessLevelRuleDetector` 检测停滞/死循环等流程异常，HMM 是可选第二意见。
- 规则命中优先保证可解释性；模型结果是补充，不能把模型概率当作业务事实。

### 6.5 根因分析、深度分析和相似案例

**普通根因**

```text
GET /anomalies/{id}/analysis
  -> Python anomaly_store 找告警
  -> 按当前 JWT uid 调 Java /internal/users/{uid}/llm-config
  -> Java 解密该用户 API key
  -> RootCauseAnalyzer 调 OpenAI-compatible/Anthropic-compatible LLM
  -> Pydantic 结构化校验 {root_cause,evidence,suggestions}
```

**深度分析 Agent**：`POST /ai/heal/{id}`，`HealerAgent` 最多 5 步只读工具调用（订单详情、事件、统计、分析等），返回 `report + agent_trace`。前端折叠展示每一步工具输入/输出，便于解释“AI 为什么这么判断”。

**相似案例**：`GET /ai/cases/{id}/similar?top_k=5`，`CaseIndex` 按规则、事件类型、时间邻近等轻量特征打分，并带出历史处置结果；不是向量数据库。

**LLM 未配置**：普通 NL 查询可以降级为关键词意图 + 数据摘要；根因、深度分析、周报和订单故事需要用户自己的 LLM 配置，返回 409，前端应提示去个人中心配置。

### 6.6 从告警到补偿审批

- `发起补偿审批`把 AI suggestions 转成 Saga steps；带退款金额时写入 `params.amount`。
- `CompensationSaga` 按白名单顺序执行；高风险/金额超过阈值的步骤插入 `compensation_approval` 并返回 `AWAITING_APPROVAL`。
- 低风险步骤可直接执行；外部网关成功后才追加 `CompensationExecutedEvent`。
- `执行 xxx`按钮只是带 query 跳 `/compensations?actionType=...&aggregateId=...` 预填，不是绕过审批的快捷后门。

## 7. NL 查询 `/nl-query`

### 7.1 前端交互

- 聊天气泡区保存本地 `messages`；首轮没有 conversation id，后续请求带 `conversation_id`。
- 回车或 `查询`提交；空白问题直接忽略。
- 根据后端 `intent` 渲染不同结构：
  - `event_lookup`：订单/事件描述表；
  - `stats_aggregation`：状态、订单数、总金额表；
  - `trace_replay`：版本、事件类型、时间表；
  - 其他数据：JSON 兜底展示。

### 7.2 数据链路

```text
NLQuery.vue
  -> POST /ai/query {question, conversation_id?}
  -> FastAPI require_permission('ai:query') 校验 JWT
  -> _llm_client_for(uid) 获取用户 LLM 配置（可选）
  -> IntentClassifier：规则/LLM 识别意图与参数
  -> NLQueryEngine：只允许固定工具/模板
      event_lookup -> BackendClient GET /orders/{id}
      stats_aggregation -> BackendClient GET /orders/stats
      trace_replay -> BackendClient GET /orders/{id}/events
  -> 结构化 QueryResult + 中文 answer
```

AI 服务使用机器密钥 `X-API-Key` 调 Java 只读接口，不直连业务数据库。这样 SQL/表结构留在 Java 查询服务，LLM 不能越权生成任意 SQL。LLM 润色超时约 8 秒时，后端返回规则摘要；前端 Axios 10 秒超时则显示可重试提示。

### 7.3 面试演示问题

- “最近 7 天有多少订单？”：展示 stats aggregation。
- “订单 `<某个 UUID>` 当前状态是什么？”：展示 event lookup。
- “查看这笔订单的轨迹”：展示 trace replay。
- 先问“它现在怎样”，缺少订单号时后端返回 `needs_input=true`；下一轮携带 conversation id 和订单号，说明多轮状态不是前端猜测，而是后端会话协议。

## 9. 补偿执行 `/compensations`

### 9.1 页面输入

- 动作下拉：`REFUND(MEDIUM)`、`NOTIFY_DELAY(LOW)`、`MARK_OUT_OF_STOCK(LOW)`、`FREEZE_ORDER(HIGH)`、`BACKOFF_AND_STOP(LOW)`。
- 聚合根 ID、参数 JSON；异常看板跳转时通过 query 自动预填。
- 执行按钮要求 `compensation:execute`；JSON 解析失败在前端直接拦截。

### 9.2 后端分流

```text
POST /compensations
  -> CompensationController（compensation:execute）
  -> Registry 白名单查动作
  -> requiresApproval(aggregateId, params)?
       是 -> CompensationSaga.start -> compensation_approval(PENDING)
       否 -> CompensationService.execute
  -> gateway（支付/库存/通知，默认 Mock，可替换真实适配器）
  -> 成功后追加 CompensationExecutedEvent
```

普通人工入口保持“单动作立即执行”语义，但高风险动作仍会进入审批。`/compensations/saga` 接受多步骤，逐步执行；任何 AI 建议动作不在白名单都会被 400 拒绝。

### 9.3 风险讲法

> 这里不是让 LLM 直接调用退款 API。LLM 只能建议动作；Java 端重新做权限、白名单、金额和审批判断，外部副作用隔离在 gateway，Saga 负责顺序、挂起和恢复。

## 10. 审批队列 `/approvals`

页面调用 `GET /approvals`，只显示 `status=PENDING` 的审批单：审批单 ID、动作、订单 ID、业务参数、发起方、申请时间；点击批准/拒绝：

```text
POST /approvals/{approvalId}/approve
或 POST /approvals/{approvalId}/reject
  -> ApprovalController
  -> ApprovalRepository.decide
       UPDATE ... WHERE approval_id=? AND status='PENDING'
  -> 只有一个并发点击能更新成功
  -> CompensationSaga.onApproved
       批准：执行当前步骤并继续剩余步骤
       拒绝：Saga FAILED
  -> 前端刷新列表
```

审批单保存 Saga 剩余步骤 JSON；服务重启时 `SagaRecoveryRunner` 从 PENDING 审批单恢复内存实例。这解决单机重启丢在途审批的问题，但当前完整 Saga 实例仍主要在单进程内存，多副本生产化应把完整 Saga 状态机落库。

## 11. 个人中心 `/profile`

个人中心由 `Profile.vue` 组合 `admin/LlmSettings.vue`，并非只有管理员可见。

### 11.1 用户自己的 LLM 配置

页面字段：Provider、Model、Base URL、API key、Max tokens、Temperature，以及已配置/未配置状态。

```text
GET /users/me/llm-config
PUT /users/me/llm-config
  -> UserLlmConfigController
  -> AuthPrincipal.uid（只能访问自己的配置）
  -> UserLlmConfigService
  -> user_llm_config
```

- API key 由 Java 侧 AES-256-GCM 加密存 `api_key_enc`，读取接口只返回 `hasApiKey/apiKeyMasked`。
- 保存时 API key 留空表示保留原密钥；前端保存成功后清空输入框。
- AI 服务收到用户 JWT 后只拿 uid，再用机器密钥调用 Java 内部接口取“该用户解密后的配置”；这样不同用户可以使用不同模型，管理员也不能读取别人的明文 key。
- 前端校验 Base URL 必须 `http(s)://`、Model 非空；后端仍应再次校验。

### 11.2 修改密码与退出所有设备

- 修改密码：前端校验新密码至少 8 位且两次一致，调用 `POST /auth/password`；后端验证旧 BCrypt、更新哈希、递增 token version、写审计；前端清会话并回登录。
- 退出所有设备：`POST /auth/logout-all` 递增 token version，使所有旧 JWT 失效；不是仅删除当前浏览器 token。

## 12. 管理员页面

### 12.1 用户管理 `/admin/users`

页面首屏并行调用 `GET /users` 与 `GET /roles`，表格展示 ID、用户名、显示名、角色、启用状态。交互包括：

- 新建用户：用户名、初始密码、显示名、角色多选、启用开关 -> `POST /users`。
- 编辑：显示名、角色、启用状态 -> `PUT /users/{id}`。

### 12.2 角色权限 `/admin/roles`

页面调用：

- `GET /roles`：角色及权限码；
- `GET /roles/permissions`：权限目录；
- `POST /roles`、`PUT /roles/{id}`、`DELETE /roles/{id}`：角色维护。

当前权限目录由 `AuthDataSeeder` 代码定义：`order:read`、`order:create`、`order:write`、`anomaly:view`、`ai:query`、`compensation:execute`、`user:manage`、`role:manage`、`anomaly:evaluate`。

角色默认矩阵：

| 角色 | 主要权限 | 页面结果 |
|---|---|---|
| ADMIN | 全部权限 | 所有菜单、用户/角色/审计、订单写入、AI、补偿 |
| OPERATOR | 订单读/建/写、异常、AI 查询、补偿 | 无用户管理、角色管理、审计 |
| VIEWER | 订单读、异常查看、AI 查询 | 无新建订单、补偿、审批和系统管理 |

前端侧栏按权限隐藏，直接输入 URL 会被路由守卫送到 `/403`；即使绕过前端，Java `@RequirePermission` 和 Python `require_permission` 仍会拒绝。

### 12.3 审计日志 `/admin/audit-logs`

页面按用户名过滤并分页调用 `GET /audit-logs?page&size&username`，展示 ID、用户名、动作、详情、IP、时间。数据来自 `auth_audit_log`，典型动作包括登录成功/失败、登出、改密、用户/角色增删改和重置密码。

当前接口没有返回 total，前端用“本页是否拉满”估算分页总数，这是已知展示上限；面试中不要把它说成精确总数。

## 15. 面试官高频追问与标准回答

### Q1：为什么订单创建后列表不是立即出现？

因为写模型和读模型解耦：Java 事务先提交 `domain_events`，Debezium 再经 Kafka 异步更新 `order_view`。前端创建后轮询详情确认投影版本，后端也提供读己写等待/409，而不是假装强一致。

### Q2：为什么不用应用代码同时写数据库和 Kafka？

数据库提交与 Kafka 发送无法靠两行代码原子化。这里让 Debezium 从 PostgreSQL WAL 派生消息，消除应用双写窗口；下游按至少一次处理重复。

### Q3：前端删按钮算权限吗？

不算。`v-permission` 和菜单过滤只是 UX；Java `AuthFilter`/`PermissionInterceptor`、Python JWT 依赖、WebSocket 握手都再次校验权限。

### Q4：LLM 会不会直接退款？

不会。LLM 只能返回结构化根因和建议；补偿请求进入 Java 白名单，Saga 按风险决定直接执行或落审批单，外部支付/库存/通知由 gateway 适配器执行。

### Q5：WebSocket 断线会丢告警吗？

实时消息可能错过，所以重连后补拉 Java 侧最近告警历史，并以 anomaly_id 去重。历史先落库再广播；消费失败进入 Kafka 重试/DLT。当前是单实例连接集合，多副本需共享广播。

### Q6：AI 服务为什么不直接查 PostgreSQL？

业务读模型和权限集中在 Java 服务；AI 通过机器密钥调用受限 REST，NL 查询只能映射固定意图/模板，避免把数据库结构和任意 SQL 暴露给 LLM。

### Q7：线上页面为空是不是功能坏了？

不能仅凭空表判断。订单、告警、审批是动态数据；先看 `/health`、WebSocket 连接、`/alerts/recent`、Kafka/检测指标和数据库当前数据。2026-08-25 线上异常/审批为空但 WS 已连接，属于当前没有告警/审批数据的状态，不代表链路断开。

### Q8：当前实现的诚实边界是什么？

Saga 完整状态主要在单实例内存、WebSocket 广播单实例、登录限流和规则上下文缓存主要是进程内、事件乱序只有版本守卫没有 gap 暂存、审计分页没有精确 total、时间线尚未做任意版本状态快照。这些都在架构基线中列出升级路径。

这一节按“看到什么、点击后发生什么、数据从哪里来、失败时怎样、面试怎么说”的固定格式拆解，适合面试前逐页背诵。

**看到什么**

**面试表达**

> 我把公开落地页设计成零业务请求的静态入口，避免登录、数据库或 AI 故障影响项目介绍；账号密码只是演示入口，不能把它当成真实用户数据源。

### 18.2 体验指南：把系统变成可复现的演示剧本

**数据分层**

- `steps`：登录、创建订单、观察异常、NL 查询与补偿四步。
- `flow`：创建订单 -> 事件入库 -> CDC -> 检测 -> 告警 -> 查询/补偿闭环。
- `highlights`：每个亮点包含 icon/title/desc/accent，全部静态渲染。
- `faqs`：解释演示数据隔离、告警延迟、三个账号并行登录和 LLM 配置前置条件。

**交互状态**

- 页面滚动只影响 reveal 动画和导航样式；无业务副作用。
- 账号密码显隐和复制是本地状态；CTA 负责跳转。
- “告警为空”时，应把 FAQ 文案和接口现实区分开：指南是能力说明，数据由当前环境决定。

**面试表达**

> 指南不是第二套业务逻辑，而是前端把真实业务链路编排成一个可复现的测试剧本；这样面试官可以按固定顺序验证事件、检测、AI 和补偿。

### 18.3 登录页：认证状态机

| 状态 | 触发 | 页面表现 | 后端结果 |
|---|---|---|---|
| 空表单 | 点击登录 | error=`请输入用户名和密码` | 不发请求 |
| 请求中 | 调用 `/auth/login` | 登录按钮 loading/禁用 | 服务端校验 |
| 成功 | 返回 token/user | 跳 redirect 或 `/orders` | 审计 LOGIN_OK |
| 密码错误 | 401 | 中文错误提示 | LOGIN_FAILED + 失败计数 |
| 账号禁用 | 403 | 无权限提示 | 不签发 token |
| 首次改密 | user.mustChangePassword | 不可关闭对话框 | `/auth/password` 后 token 失效 |

**响应字段如何被用**

- `token` -> `eg_token`，供 Axios 和 WebSocket 使用。
- `user.roles` -> 头像/显示名与角色展示。
- `user.permissions` -> 菜单、路由守卫和按钮指令。
- `user.mustChangePassword` -> 是否弹改密窗口。
- `user.tokenVersion` 不直接显示，由后端在后续请求校验。

**面试表达**

> 登录成功不是“拿到一个字符串”这么简单，它同时初始化前端会话、权限快照、重定向地址和后续 WebSocket 的认证材料；真正的 token 吊销由服务端 token version 控制。

### 18.4 控制台壳：页面无关的基础设施

**首屏数据**

1. 路由守卫决定当前页面是否需要登录/权限。
2. `App.vue` 调 `GET /health`，把 `status` 转成 Live/Offline。
3. `auth.user` 决定头像首字、显示名和下拉菜单。

**菜单计算**

- `order:read` -> 订单中心。
- `anomaly:view` -> 异常看板。
- `ai:query` -> NL 查询、运营周报。
- `compensation:execute` -> 补偿执行、审批队列。
- `user:manage/role:manage` -> 系统管理及其子菜单。

**关键细节**

- `/orders/:id/timeline` 的 active menu 被归一成 `/orders`，所以详情页仍高亮订单中心。
- `/admin/*` 按真实子路由高亮，避免用户管理和角色管理同时高亮。
- 移动端侧栏是固定层 + backdrop；关闭只改本地 `sidebarOpen`，不影响业务会话。

### 18.5 订单列表：读模型、写模型和按需 AI 三条链并行

**列表字段映射**

| UI 字段 | API 字段 | 真实来源 | 前端处理 |
|---|---|---|---|
| 订单 ID | `orderId` | `order_view.aggregate_id` | 超长省略/tooltip |
| 状态 | `status` | 投影折叠出的当前状态 | `statusType()` 映射颜色 |
| 金额 | `totalAmount` | 创建事件中的金额投影 | `toFixed(2)` |
| 版本 | `version` | 读模型事件版本 | 直接展示 |
| 更新时间 | `updatedAt` | 投影更新时间 | `toLocaleString('zh-CN')` |

**筛选/分页状态机**

- 改状态筛选：`currentPage=1`，将 `status` 作为 query 参数重新 GET。
- 翻页：page 从 UI 的 1-based 转服务端的 0-based。
- 刷新：不改筛选和页码，只重新请求。
- 接口异常：清空 `orders`，显示 `friendlyError`，避免把旧数据误认为新鲜数据。

**新建订单的请求体**

```json
{
  "userId": "u-demo",
  "totalAmount": 199
}
```

请求头额外带 `X-Command-Id`。服务端返回 `orderId` 后，前端不是立即刷新，而是轮询详情直到读模型可见；这段轮询是用户体验层的最终一致性适配。

**面试表达**

> 列表读 `order_view`，时间线读 `domain_events`，创建写 `domain_events`；三者不是同一张表的不同 SQL，而是 CQRS 的三个职责边界。

### 18.6 事件时间线：图表只是事件序列的一个投影

**EventDto 字段**

```json
{
  "version": 3,
  "eventType": "PaymentCompletedEvent",
  "createdAt": "2026-08-18T11:37:17Z",
  "payload": {"paymentId": "..."}
}
```

**渲染过程**

1. `events` 传入组件后先复制数组，按 version 升序排序，不修改父组件数据。
2. x 轴取 `eventType`，y 轴取 `version`，所以线图表达的是事件顺序，不是金额趋势。
3. Tooltip 从 `dataIndex` 找回同一条 EventDto，再格式化 payload。
4. 表格展示完整 payload，便于审计和排障。

**回放语义**

- `upToVersion` 为空：读取整条事件链。
- `upToVersion=N`：服务端 SQL/查询层只返回版本不超过 N 的事件。
- 当前没有将 N 版本折叠为“当时状态”的独立卡片；如果面试官追问，可说明下一步是复用 `OrderAggregate` 做 deterministic replay。

### 18.7 异常看板：实时流 + 历史补偿读取

**告警对象字段**

```json
{
  "anomaly_id": "a-1",
  "rule_id": "R004",
  "aggregate_id": "order-1",
  "level": "ERROR",
  "source": "rule",
  "detected_at": "2026-08-25T08:00:00Z",
  "description": "支付重试次数过高",
  "details": {"retryCount": 6}
}
```

**为什么需要两条输入**

- WebSocket 是低延迟实时输入，负责“现在发生什么”。
- `/alerts/recent` 是 `anomaly_alerts` 的有限历史，负责“断线期间发生什么”。
- 两条输入都进入同一个 `pushAlert()`/`seen` 去重逻辑，避免重连时重复显示。

**聚合模式计算**

```text
key = rule_id + '|' + aggregate_id
count += 1
first = min(detected_at)
last  = max(detected_at)
representative = 第一条告警
```

这是 UI 层的视图转换，不改变后端告警记录；因此刷新页面后聚合结果会从最近历史重新计算。

**根因按钮的三个阶段**

1. 打开弹窗，先请求普通分析。
2. `深度分析（Agent）` 追加 trace，不覆盖告警本身。
3. `相似案例` 追加检索结果；`发起补偿审批`使用当前告警的 `aggregate_id`，不是 `anomaly_id`。

**面试表达**

> anomaly_id 标识一次检测结果，aggregate_id 才标识要补偿的订单聚合根；前端专门保存两个字段，是为了防止把“告警对象”误当成“业务对象”执行副作用。

### 18.8 NL 查询：意图决定结果组件

**前端消息模型**

```ts
{
  role: 'assistant',
  answer: string,
  intent: 'event_lookup' | 'stats_aggregation' | 'trace_replay',
  data: unknown,
  conversation_id?: string,
  needs_input?: boolean
}
```

**提交时序**

1. 先把用户问题 push 到 `messages`，立即清空输入框，保证用户感知到已提交。
2. 设置 loading，发送首轮/续聊请求。
3. 成功后保存后端返回的 conversation id。
4. 失败也追加一条 assistant 消息，而不是丢掉用户问题。
5. `nextTick` 后把 thread scroll 到底部。

**为什么不让前端解析自然语言**

前端只负责展示 intent；意图分类、参数抽取、缺参反问和后端 API 选择在 Python `NLQueryEngine`，这样规则可统一升级，也不会把业务查询规则复制到浏览器。

### 18.9 运营周报：一次请求返回多个数据域

**返回对象拆解**

- `period`：前端显示统计起止时间。
- `total_anomalies`：告警总数。
- `by_rule`：按规则统计，驱动异常分布表。
- `order_stats`：Java 订单统计接口返回，驱动状态金额表。
- `symptoms/recommendations`：LLM 生成的自然语言数组。
- `top_orders`：异常集中订单，点击后再次请求故事线。

**为什么生成周报不是简单查表**

它同时聚合异常历史、订单读模型统计和 LLM 文本总结；任何一个域失败都可能影响整体报告，所以后端统一控制超时和错误，前端只显示 loading/error/report 三态。

**用户操作话术**

> 我先选择 7 天生成报告，再点重点订单看故事线。周报给的是运营摘要，事件时间线给的是可审计事实，两者一个偏总结、一个偏证据。

### 18.10 补偿执行：表单校验不等于业务授权

**前端校验层**

- 空聚合根不在前端强制拦截，最终由后端校验；这样后端仍是唯一规则来源。
- 参数 JSON 由 `JSON.parse` 先校验，失败不发请求。
- query 预填只减少重复输入，用户仍可修改动作、订单和参数。

**后端安全层**

1. JWT 权限拦截。
2. 动作白名单查找。
3. `requiresApproval()` 根据动作和金额判断风险。
4. 网关适配器执行外部副作用。
5. 成功事件落库，失败不写“成功补偿事件”。

**面试追问：为什么页面显示 MEDIUM/HIGH？**

这些标签是前端动作目录的提示，不是最终决策；真正是否审批由后端 Registry 实现，防止攻击者改前端选项或绕过 UI。

### 18.11 审批队列：人工在环的状态机

**页面状态**

- `loading=true`：表格显示加载态。
- 成功且为空：`暂无待审批项`。
- 有数据：待审批数量、每行批准/拒绝按钮。
- 某一行决策中：只锁定该行对应动作，不阻塞其他行。

**批准/拒绝的竞态保护**

数据库使用 `WHERE status='PENDING'` 条件更新。两个浏览器同时批准时只有一个 UPDATE 影响 1 行；另一个请求返回失败，Saga 不会执行两次。

**为什么刷新后状态消失**

审批成功后 `Approvals.vue` 重新 GET `/approvals`，接口只返回 PENDING；已批准/拒绝记录仍留在 `compensation_approval`，只是当前工作队列不再展示。

### 18.12 个人中心：用户级配置和安全操作

**LLM 配置表单状态**

- 初始 `GET` 只填 provider/baseUrl/model/参数，API key 输入框始终清空。
- 已有 key 只显示掩码，例如 `sk-...abcd`，不会回传明文。
- 保存时空 key 表示保留旧 key；前端成功后立即清空输入框。
- Base URL、Model 的前端校验只改善体验，Java 服务仍需校验长度、协议和范围。

**改密状态**

1. 新密码少于 8 位：本地直接报错。
2. 两次不一致：本地直接报错。
3. 服务端旧密码错误：返回 400，保持当前页面。
4. 成功：token version 递增，前端清会话并跳登录。

**安全表达**

> 个人中心的“我的”是授权边界，不是 URL 命名习惯；Controller 从 `AuthPrincipal` 取 uid，用户不能通过修改请求体 uid 读取别人的配置。

### 18.13 用户管理：认证数据的 CRUD 闭环

**首屏并行请求**

```text
Promise.all([
  GET /users,
  GET /roles
])
```

角色列表用于把用户已有的角色编码反向映射成多选框的 role id；保存时前端提交 roleIds，后端重新计算用户权限，不信任浏览器提交的 permissions 数组。

**三个危险操作**

- 删除用户：确认框 + 后端删除/约束；前端禁删自己只是额外保护。
- 重置密码：后端更新 BCrypt，并可设置下次改密标记。
- 禁用用户：后续登录被拒绝；若要让已有会话立即失效，应配合递增 token version（改密/退出所有设备路径已经明确这么做）。

**面试表达**

> 用户管理改的是身份数据，角色管理改的是授权关系，审计日志记录是谁改的；三者都不写入订单事件流，因为它们不属于订单聚合。

### 18.14 角色权限：权限码而不是页面角色硬编码

**编辑过程**

1. 读取角色及权限目录。
2. 用户修改权限 checkbox。
3. 提交 `code/name/description/permissions[]`。
4. Java `RoleService` 更新角色-权限关联。
5. 新登录 token 携带最新权限；`/auth/me` 可以刷新前端显示的用户信息，但后端请求鉴权仍以当前 JWT claims 为准，权限变更要让用户重新登录才会完整生效。

**为什么权限码可扩展**

页面只依赖 `order:read` 等稳定字符串，不依赖“是不是 ADMIN”。新增角色只需分配权限码，菜单和路由守卫自动复用；后端 Controller 仍用同一权限码做最终校验。

### 18.15 审计日志：安全证据链

**筛选与分页**

- 输入用户名回车或点查询，先把 page 重置为 1。
- 前端把 UI 页码转成 0-based page，size 默认 50。
- 服务端按 username 精确过滤、按 created_at 倒序。
- 由于接口不返回 total，前端用返回数量估算下一页；这是展示近似，不是数据库精确计数。

**字段解释**

- `username`：操作者，不等同于被操作用户。
- `action`：标准动作码，前端映射中文。
- `detail`：业务细节，避免把密码/API key 写入日志。
- `ip`：请求来源地址。
- `createdAt`：服务端时间，前端只做本地化显示。

### 18.16 403/404：可达性和授权是两个问题

- 受保护 URL 但未登录：先去 `/login`，不是 403。
- 已登录但缺权限：路由守卫去 `/403`；直接调用 API 则是后端 403。
- 路径不存在：`NotFound.vue`；它与“资源不存在”的 API 404 不同。
- 订单不存在：时间线/详情接口报 API 404，由页面 error alert 显示；不是跳站点 404。

面试时可以这样区分：

> 路由 404 是前端没有这张页面，资源 404 是页面存在但后端没有这条数据；403 是身份已识别但权限不足，401 是身份无效或已过期。

## 19. 页面级排障顺序：面试现场遇到空白或失败怎么办

不要先改代码，按数据链路逐层定位：

1. **浏览器路由**：URL 是否为正确的 `/#/...`，是否被守卫重定向登录/403。
2. **会话**：`eg_token` 是否存在，`/auth/me` 是否返回当前用户和权限。
3. **HTTP 请求**：Network 看路径、状态码、Authorization 是否附上、是否超时。
4. **Java 健康**：控制台 `GET /health` 是否正常，数据库依赖是否 UP。
5. **数据来源**：订单看 `order_view`，时间线看 `domain_events`，告警看 `anomaly_alerts`/WS，审批看 `compensation_approval`。
6. **异步链路**：订单看 Debezium -> `domain-events` -> projection；告警看 AI consumer -> `anomaly-alerts` -> Java consumer。
7. **AI 配置**：根因/周报/故事 409 时检查当前用户 LLM 配置，不要误判为模型代码异常。
8. **权限**：先看 JWT permissions，再看 Java `@RequirePermission` 或 Python `require_permission`，不要只看按钮是否存在。

### 页面空白的快速判断

| 现象 | 更可能的原因 | 先查什么 |
|---|---|---|
| 订单表 No Data | 读模型无数据或筛选条件 | `/orders` 响应、`order_view` |
| 创建成功但列表无新单 | CDC/投影延迟 | `GET /orders/{id}`、投影日志 |
| 时间线空 | 订单 ID 不存在或无事件 | `/orders/{id}/events` |
| 异常看板空但 WS 已连接 | 当前没有告警 | `/alerts/recent`、AI consumer |
| 异常看板未连接 | token/握手/代理问题 | WS URL、JWT、`JwtHandshakeInterceptor` |
| 根因返回 409 | 当前用户未配置 LLM | `/users/me/llm-config` |
| 审批为空 | 没有 PENDING 或权限不足 | `/approvals` 状态码、审批表 |
| 管理菜单消失 | 当前用户缺权限 | `/auth/me` permissions |

这套排障顺序本身就是面试中的系统设计答案：先确认入口和身份，再确认同步 REST，最后追异步消息和外部依赖，避免把派生数据问题误修成业务写入问题。
