# 量化口径：哪些数字能写，哪些不能

> **当前投递提示（2026-08-15）**：性能口径以本文件「资源受限单机负载验收」为准：30 写并发、150 个带目标版本及关键字段校验的读己写抽样。历史 50 并发/520 样本数字仅保留为历史运行记录，不作为当前能力声明。

写简历、答面试前先过一遍这页。规则很简单：**这里列为「可用」的才敢说，列为「禁用」的一个字都不要提。**

面试官追问一个编出来的数字，整场信任就没了。而承认「这个我还没测」的代价几乎是零。

## 一、可用（有实测文件支撑）

| 维度 | 指标 | 实测 |

**必须记住的诚实边界**（这些数字是**单次运行**的功能链路实测，不是压测）：

1. 上面所有延迟都是**单套件内的 p50/p95**（有界自节奏 ≤4 req/s），不是并发下的。并发下的 QPS / 延迟见下方「负载压测」小节，两套数字口径不同，别混。
2. CDC 捕获延迟跨运行有方差（另一轮跑出 p50 204ms），上表取最终一版 p50 697ms——它量的是单次 commit→Kafka 落点，量级对，别当稳定值报死。
3. s03 的 precision 口径：只统计本套件 7 笔注入单 + 20 笔对照单的告警。运行日志如实记录了被排除的 25 条外部告警——全是 IsolationForest 按 5% contamination 对同用户批量订单（R001 的 10 笔基线 + R004 的 19 笔批量）判出的异常，与离线 ai-vs-baseline 评测里 IF 高误报的结论一致。**所以这个 0.778 是"注入检出 + 对照零误报"的端到端口径，和下面的离线评测是两套数字，别混。**

### 历史负载压测（bench load，2026-08-12 实测）

来源：[`eventguard-benchmark/out/load6/benchmark-report.md`](../../eventguard-benchmark/out/load6/benchmark-report.md)（`EG_RATE_LIMIT_ENABLED=false` 关限流后 `docker compose --profile bench run --rm bench --suites load`）。

Profile：10s 预热(2 并发) → 35s 爬坡 5→50 → 30s 稳态 50 并发；写路径 = 下单+支付（create+pay），延迟在 pay 完成即采样；读己写由独立线程异步抽样（CDC 最终一致，≤2s 轮询），不阻塞写吞吐。

| 指标 | 实测 |
|---|---:|
| 吞吐（稳态 50 并发） | **92.7 QPS**（30.5s 内 2823 次下单+支付） |
| 写路径错误率 | **0.00%**（无 5xx / 超时 / 客户端异常） |
| 写路径延迟 | p50 **486 ms** / p95 **1102 ms** / p99 **1500 ms** |
| 读己写（异步抽样，520 样本） | **100%** 追平（CDC 投影滞后 ~0.4-0.6s，最终一致） |

**历史记录边界**：

1. **这是 3.6GB 单机的历史档位**（postgres+kafka+debezium+server+AI+prometheus 全在同一台），不是集群。该结果仅用于追溯，不作为当前容量承诺；当前验收以「资源受限单机负载验收」小节为准。
2. 负载数字与功能套件数字**口径不同**：功能套件是有界自节奏 ≤4 req/s 的 p50/p95，负载是 50 并发打满的 QPS/P95/P99。回答时先声明"负载压测"。
3. s09 套件的 `load_p95 <500ms` 断言**未过**（实测 1102ms），仅保留为历史目标记录。
4. 跑负载需临时关限流（`EG_RATE_LIMIT_ENABLED=false`），跑完已恢复；负载产生的事件数据已清理，功能基线已恢复（上面 9/9 全绿即清理后重跑）。

### 资源受限单机负载验收（bench load，2026-08-15 实测）

来源：[`eventguard-benchmark/out/benchmark-report.md`](../../eventguard-benchmark/out/benchmark-report.md)。

Profile：10s 预热（2 并发）→ 35s 爬坡至 30 写并发 → 30s 稳态；读己写由 8 个独立线程抽样，查询携带支付命令返回的 `expectedVersion`，并校验版本、状态和金额。该档位面向 3.6GiB 单机，验收门槛为写入错误率 `<5%`、写 p95 `<2500ms`、至少 150 个读己写样本且成功率 `>=65%`。

| 指标 | 实测 |
|---|---:|
| 吞吐（稳态 30 写并发） | **52.39 业务迭代/s**（1590 次下单+支付） |
| 写路径错误率 | **0.00%** |
| 写路径延迟 | p50 **503ms** / p95 **1262ms** / p99 **1773ms** |
| 读己写（带版本和关键字段断言） | **110/157 = 70.1%** 在 2 秒内追上 |
| Hikari 等待峰值 | **39**（读己写轮询与写入共享主池的压力信号） |

该档位四项验收均通过，但不代表 50 并发容量承诺；读己写未在窗口内追上的请求返回 409，属于最终一致性的明确降级语义，而非写入失败。

### 异常检测效果

来源：[`eventguard-benchmark/ai-vs-baseline.md`](../../eventguard-benchmark/ai-vs-baseline.md)

| 检测器 | Precision | Recall | F1 | FPR |
|---|---:|---:|---:|---:|
| Baseline（固定阈值规则） | 0.879 | 0.896 | **0.887** | 0.088 |
| AI-Enhanced（IsolationForest + 规则） | 0.649 | 0.896 | **0.753** | 0.345 |

混淆矩阵：Baseline TP=1278 FP=176 FN=149 TN=1824；AI-Enhanced TP=1279 FP=691 FN=148 TN=1309。

样本：正常序列 2000 + 异常序列 1427，序列级标注（一条序列含任一异常事件即判异常）。

**必须一起记住的三个事实**，否则会讲错：

1. **两者 Recall 完全相同（0.896）**。AI 的 TP 从 1278 只涨到 1279，多抓了 1 条。所以不能说「AI 提升了召回但误报变多」——AI 的召回增益基本是零。
2. **差异全部来自误报**：FP 从 176 涨到 691，多出 515 个。FPR 从 0.088 涨到 0.345。
3. **原因是 `contamination=0.05`**：IsolationForest 被强制按 5% 比例判异常，和真实分布不匹配。它划出去的那批样本里几乎没有真异常。

### 终局预测

来源：[`eventguard-benchmark/predict-eval.md`](../../eventguard-benchmark/predict-eval.md)

RandomForest，6224 训练样本，独立测试集 6206 条前缀样本（seed=7），总体准确率 **0.7096**。

分类别 F1：CLOSED 0.885 / STUCK 0.708 / REFUNDED 0.665 / CANCELLED 0.573。

被追问时注意：CANCELLED 的精确率只有 0.423，是明显短板——召回 0.887 但精确率低，说明模型倾向于把别的类别误判成 CANCELLED。

### 代码里的确定参数

这些是从代码读出来的，随时可查：

- 快照阈值：每 **100** 个事件一次

- 读己写轮询：**50ms** 间隔 / **2s** 超时
- Kafka 消费失败重试：**3** 次，退避 0.3 / 0.9 / 1.8s，超限进 DLT
- 告警环形缓冲：**100** 条
- 事件归档周期：**90** 天
- 规则引擎 HTTP 桥接超时：**2s**（可配）
- NL 查询 LLM 润色超时：**8s**（可配），前端 axios 等 10s
- 停滞检测阈值：**24h**（可配）；死循环阈值：**5** 次（可配）
- 业务规则条数：**5** 条（金额偏离 3σ / 重复支付 / 状态跳跃 / 高频下单 / 库存超卖）
- 流程级规则：**3** 条（P001 / P002 停滞 / P003 死循环）

## 二、曾经禁用 → 已全部解禁（2026-08-12）

最初量化口径把「负载压测」和「混沌韧性」列为禁用区（没跑出数就不说）。**现在两类都已实测并移入上方「可用」区**：

| 原禁用项 | 解禁依据 | 关键数字（详见「可用」区） |
|---|---|---|
| ❌→✅ QPS / 吞吐量 | s09 关限流后 `--suites load` 实测 | **92.7 QPS**（稳态 50 并发） |
| ❌→✅ 负载下的 P95 / P99 / 错误率 | 同上 | p95 **1102 ms** / p99 **1500 ms**，写路径错误率 **0%** |
| ❌→✅ 混沌注入后的恢复时间 | 宿主机 `chaos_run.sh` + s10 导入 | db-kill **2s** / kafka-pause **2s**，数据零丢失 |

**跑这些的完整命令**（已实测，留档）：

```bash
# 1) 负载压测（先临时关限流）：
#    .env 加 EG_RATE_LIMIT_ENABLED=false → docker compose up -d --no-build eventguard-server
docker compose --profile bench run --rm bench --suites load
#    跑完恢复 .env（删掉限流行）→ docker compose up -d --no-build eventguard-server
# 2) 混沌注入（宿主机执行，需 Docker 权限；AI 容器也在跑时注入）：
bash eventguard-benchmark/chaos_run.sh
# 3) 韧性断言（s10 从挂载根 /out/chaos-results.json 导入，勿加 --out 子目录）：
docker compose --profile bench run --rm bench --suites functional
```

> 注意两个坑（都踩过，已修复留档）：
> - s09 曾 100% 失败是 bench 客户端 bug（`client.post()` 返回 `(resp, ms)` 元组，代码当裸 response 用）——已修元组解包；读己写须用独立线程异步抽样（CDC 投影滞后 ~0.4-0.6s，同步轮询会拉低写吞吐）。
> - 负载测试会往库里灌上万事件，污染 s03 检测基线、打爆 AI 限流（追补时规则引擎全 429）。跑完负载**必须清理事件数据**（TRUNCATE 业务表保留 auth）+ 重置 AI 消费者 offset，再重跑 functional 恢复全绿基线。

## 三、其他不能说的

| 别说 | 因为 |
|---|---|
| 测试覆盖率 X% | 没配 JaCoCo / coverage，没测过 |
| 服务了 N 个用户 / 日均 N 单 | 个人项目，无真实流量 |
| 性能提升了 N% | 没有优化前的基线数据 |
| 「AI 检测准确率 88.7%」 | 0.887 是 **Baseline 规则**的 F1，不是 AI 的。AI 是 0.753，端到端 s03 是 0.778——**三套口径**，张冠李戴会被当场戳穿。面试说 F1 前先说明是哪套：离线评测（0.753）测的是序列级判异常，s03（0.778）测的是 7 类注入逐单检出 |
| 上线运行 / 生产环境 | 有部署方案文档，但没有真实生产流量。说「部署过」可以，说「生产运行」不行 |

最后一条尤其注意：项目**可以**说「已部署可访问」（Cloudflare Tunnel 方案是真的），但不能暗示有真实用户和业务量。
