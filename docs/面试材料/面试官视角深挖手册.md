# EventGuard 面试官视角深挖手册

> 这是一份面向“项目深挖”而不是面向产品使用的材料。回答顺序建议固定为：**业务问题 -> 设计选择 -> 关键实现 -> 故障/边界 -> 验证证据**。凡是没有真实压测或生产数据支撑的内容，明确说“当前项目尚未验证”。

## 0. 先把项目讲清楚

### 一句话

EventGuard 是一个面向电商订单的事件溯源与异常治理平台：订单变化以不可变领域事件保存，通过 Debezium + Kafka 驱动查询投影、异常检测和 Saga 补偿，最终形成“发现异常、解释原因、人工/自动处置、审计回放”的闭环。

### 三分钟版本

传统订单表只留下最终状态，遇到支付重复、库存失败或状态跳变时，很难回答“谁在什么时候做了什么”。EventGuard 把订单聚合的业务事实写入 `domain_events`，`order_view` 只是可重建的查询模型。Java/Spring Boot 接收命令，在 PostgreSQL 本地事务中完成聚合校验、事件追加、命令幂等日志和快照；Debezium 读取 PostgreSQL WAL，把已提交事件发布到 Kafka。

Kafka 的不同消费组分别更新订单投影、执行规则/模型检测、触发 Saga。由于 CDC 和 Kafka 是至少一次链路，消费侧用 `idempotent_consumer` 去重、版本守卫防倒退，毒消息经重试后进入 DLT。写后查询携带命令返回的 `expectedVersion`，投影达到目标版本才返回，否则在 2 秒上限后返回 409，避免把旧读伪装成成功。

异常检测采用规则优先、模型补充。规则覆盖金额偏差、重复支付、状态跳变、高频操作、库存异常；Isolation Forest 的离线结果反而降低 F1，因此没有把模型包装成“必然提升”，而是保留可解释规则并将模型作为补充。自然语言查询不允许 LLM 生成 SQL，只允许意图分类、参数抽取和结果润色，真正访问数据的是固定的只读模板。高风险退款等补偿动作进入审批，低风险动作可自动执行。

当前是单机 Docker Compose 可运行项目，完成固定用例、负载和故障演练；没有真实生产用户，不能宣称高可用、精确一次或生产容量。

### 先画这张架构图

```text
Vue 3 管理台
   | JWT / commandId / expectedVersion
Spring Boot API
   | 命令、聚合、权限、查询、补偿
PostgreSQL: domain_events + command_log + snapshots
   | WAL
Debezium CDC -> Kafka domain-events
   |            |                 |
   v            v                 v
order projection  AI detector       Saga/补偿
order_view       rules/model       approval/gateway
   |
运营查询 / WebSocket 实时告警 / Prometheus
```

## 1. 面试官真正想判断什么

| 面试官关注点 | 项目中的证据 | 不能夸大的地方 |
|---|---|---|
| 是否理解业务边界 | `OrderAggregate`、订单状态机、补偿动作白名单 | 不是通用电商交易平台 |
| 是否理解一致性 | 版本唯一约束、`command_log`、消费去重、读己写 | 整体仍是最终一致 |
| 是否能处理故障 | 重试、DLT、quarantine、Saga recovery、健康检查 | 单机演练不等于 HA |
| 是否能解释数据 | 事件回放、事件契约测试、投影重建 | 未做无限历史规模压测 |
| 是否有工程取舍 | CDC 代替应用双写、规则优先于模型、固定查询模板 | 能力范围因此变窄 |
| 是否有安全意识 | JWT/RBAC、机器密钥、token version、限流、密钥注入 | 默认开发配置不可直接暴露公网 |

## 2. 端到端时序：按这条链路回答

### 2.1 创建订单到列表可见

1. 前端生成或传入 `X-Command-Id`，携带 JWT 调用命令接口。
2. Controller 做 DTO 校验和权限检查，Handler 根据 `commandId` 查日志；已完成则返回首次结果。
3. 事务内获得 command advisory lock，加载聚合和当前版本，执行状态机，向 `domain_events` 追加事件；必要时写 `snapshots`，同时写 `command_log`。
4. PostgreSQL 提交后 WAL 出现变更。Debezium 只捕获已提交行，并向 `domain-events` 发布 Debezium envelope。
5. `OrderViewProjection` 消费事件：先用消费组+事件 ID 原子去重，再按版本更新 `order_view`，成功提交后通知 `ProjectionProgressNotifier`。
6. 普通列表直接读 `order_view`；写后详情带 `expectedVersion` 等待追平，超时返回 409。

### 2.2 为什么不是“写库后直接发 Kafka”

数据库先提交、Kafka 发送失败会丢下游事件；Kafka 先发、数据库回滚会产生幻觉事件。`domain_events` 既是事实源又承担 Outbox 角色，CDC 消除应用双写窗口，但不消除重复投递，因此下游必须幂等。

### 2.3 一个支付失败如何走到补偿

`PaymentFailedEvent` 进入 Saga 消费组 -> `SagaTrigger` 根据事件映射步骤 -> 低风险动作直接调用 gateway，完成后追加 `CompensationExecutedEvent` -> 高风险 `RefundAction` 创建 `compensation_approval`，审批接口以 `WHERE status='PENDING'` 条件更新，防止重复审批 -> 进程重启由 `SagaRecoveryRunner` 从持久化审批单恢复剩余步骤。Saga 实例本身当前仍有内存状态限制，面试时主动交代。

## 3. 模块级深挖

### 3.1 领域与写模型

- **聚合根**：`OrderAggregate` 是订单一致性边界；外部不能直接改状态，只能发送 `Create/Pay/Confirm/Reserve/Ship/Refund/Cancel` 等命令。
- **事件**：`DomainEvent` 带 `eventId`、`aggregateId`、`eventVersion`、`occurredAt`、`eventType`、`payload/metadata`。事件不可更新，修正业务错误应追加新事件。
- **版本**：应用层先查版本得到友好错误，数据库 `UNIQUE(aggregate_id,event_version)` 处理并发窗口；冲突只做有限重试。
- **快照**：每 100 个事件保存一次聚合状态，加载时读取最近快照再回放增量。100 是经验阈值，尚未通过压测求最优。
- **命令幂等**：`command_log` 同事务保存请求指纹和首次结果；相同编号相同参数复用结果，不同参数复用编号直接拒绝。

面试追问“为什么不只靠 Redis 幂等？”：Redis 过期、丢失或与事件事务分离都会留下窗口；这里把最终正确性放在 PostgreSQL 事务与唯一约束，Redis 更适合作为性能优化而非事实记录。

### 3.2 读模型与 CQRS

`domain_events` 适合按聚合和版本追加，却不适合订单列表、状态筛选和统计。`OrderViewProjection` 将事件折叠为 `order_view`；投影失败可从事件重建。去重表和视图更新在同一事务内，避免“标记已处理但视图没更新”。版本守卫只阻止旧事件覆盖新事件，不能自动补齐乱序缺口，生产化要增加 gap 检测和暂存/重建机制。

“读己写是不是强一致？”标准答案：不是。它是带目标版本的有界 read-your-writes；其他请求仍可能读到旧投影，超时返回 409 让调用方重试。

### 3.3 CDC、Kafka 与 DLT

- Debezium 读取 PostgreSQL logical replication/WAL，应用不直接承担消息双写。
- Kafka 消费采用手动提交、有限重试；DB 事务提交后到 offset 提交前崩溃会重复，靠业务幂等消化。
- DLT 保留原始消息作为审计记录。管理员重放时使用独立 `dlt-replay` 消费组、保留分区、增加 `eg.dlt.replay.attempt` 头；超过 3 次进入 `<topic>.DLT.quarantine`，避免毒消息无限循环。
- Kafka 停止时写侧仍可提交，但复制槽推进停止会保留 WAL，长时间可能耗尽磁盘，所以必须监控 lag、slot retained bytes 和磁盘。

追问“为什么不用 Kafka 事务？”：Kafka 事务只能覆盖 Kafka 生产/消费，不能把 PostgreSQL 和第三方支付纳入同一原子提交；这里的主一致性边界是数据库本地事务 + 幂等/补偿。

### 3.4 异常检测与 AI 服务

AI 服务由 FastAPI、Kafka consumer、规则引擎、统计特征和模型检测组成。规则是可解释、低延迟、可审计的第一层：R001 金额偏差、R002 重复支付、R003 状态跳变、R004 高频、R005 库存溢出。Isolation Forest 作为补充，不直接决定资金动作；模型不可用时降级规则/摘要。

离线对照中规则 F1=0.887，叠加 Isolation Forest 后 F1=0.753，误报上升，因此结论是“模型当前配置不适合直接上线”，不是“用了 AI 就更好”。面试官若问原因，回答特征漂移、`contamination` 与真实异常比例失配、合成数据分布有限，并说明后续会按时间切分验证、校准阈值、监控 precision/recall 和漂移。

### 3.5 自然语言查询

请求 -> JWT/权限 -> 意图分类（订单查询/统计/轨迹）-> 参数抽取 -> 固定只读接口 -> 结构化结果 -> LLM/模板润色。模型永远不拿数据库凭据，也不能执行 SQL；8 秒超时后返回确定性摘要。这样牺牲开放式能力，换取注入面小、权限边界清楚、结果可测试。提示词注入仍不能声称完全消除，必须把模型输出当不可信输入。

### 3.6 Saga、网关与审批

Saga 将跨服务流程拆成步骤，每一步有动作类型、参数、重试与补偿语义。支付/库存 gateway 通过接口隔离，默认使用 Mock，真实实现可替换。外部调用前后都要有幂等键和状态记录：成功后才追加完成事件，避免“外部失败但事件写成成功”。高风险退款需要审批，审批更新采用条件更新保证“一次决定”；待审批数据持久化后可恢复，但当前 Saga 实例 Map 仍是单实例上限。

### 3.7 认证、授权与审计

JWT 使用 HS256，共享 `EG_JWT_SECRET`，claims 含用户、角色、权限、`tokenVersion`。`AuthFilter` 区分用户 JWT 与 `EG_MACHINE_API_KEY` 机器主体；`token_version` 递增可让所有旧 token 失效。`@RequirePermission` 做接口级权限，前端按钮权限只是体验层，不能替代后端鉴权。登录失败限流当前为内存计数，单实例有效；多副本升级路径是 Redis/IP+账号维度计数。认证和用户管理写 `auth_audit_log`，审计失败不阻断主流程但会记录日志。

### 3.8 实时告警与可观测性

异常消费后通过 WebSocket 推给管理台；断线重连时前端仍应以历史接口补齐，不把 WebSocket 当唯一事实源。Prometheus 采集 Spring Actuator、AI 和主机指标，Alertmanager 按 `alertname` 分组并扇出飞书、PushPlus、163 邮箱；`for` 时长和 `repeat_interval` 抑制抖动与刷屏。关键指标：HTTP 5xx、Kafka lag、AI lag、投影版本差、DLT 数量、命令冲突/重试、Saga 审批积压。

## 4. 关键故障窗口与回答模板

| 故障窗口 | 可能结果 | 当前处理 | 仍需升级 |
|---|---|---|---|
| DB 提交后应用宕机 | CDC 仍可读到已提交事件 | Debezium 从 WAL 捕获 | 监控复制槽与 WAL |
| CDC 已发 Kafka、offset 未提交 | 重复消息 | 消费去重 | 端到端仍非 exactly-once |
| 投影先写去重后崩溃 | 若非同事务会丢投影 | 当前同事务提交 | 大规模重建工具 |
| 版本 3 先于版本 2 到达 | 版本缺口 | 版本守卫防倒退 | gap 暂存/补齐 |
| Kafka 长时间不可用 | 事件积压，WAL 增长 | 写侧与 Kafka 解耦 | 容量和恢复演练 |
| LLM 超时/返回脏参数 | 查询失败或越权风险 | 固定模板、超时降级、权限前置 | 更强 schema 校验和审计 |
| Saga 进程重启 | 内存实例丢失 | 审批单持久化 + recovery | Saga 状态全量持久化 |
| 多副本同时审批 | 重复执行风险 | DB 条件更新 | 外部 gateway 幂等键 |

回答故障题时不要只说“加重试”：先区分可重试错误、业务拒绝、毒消息和外部副作用，再说明幂等键、事务边界、退避、DLT 和人工介入点。

## 5. 简历逐条拆解与追问

### “事件溯源 + 并发幂等”

面试官会问：事件和命令日志是否同事务？并发两个版本怎么办？同一 `commandId` 改参数怎么办？

回答要点：本地事务、advisory lock、请求指纹、唯一约束、有限重试；同参数重放复用首次结果，不同参数拒绝；数据库约束是最后防线。

### “异步读模型与读己写”

面试官会问：为什么不同步更新？通知丢了怎么办？返回 409 的契约是什么？

回答要点：写侧隔离、去重与视图更新同事务、通知主路径+50ms轮询兜底、2秒超时；整体最终一致，不把测试样本说成强一致。

### “Debezium + Kafka”

面试官会问：WAL、复制槽、重复、顺序、分区键、停 Kafka 会怎样？

回答要点：已提交事实经 WAL 捕获；按聚合维度保证顺序的前提是稳定 key/分区策略；重复由下游幂等；停 Kafka 不阻断本地写但会积压和占磁盘。

### “规则 + 模型检测”

面试官会问：模型指标、阈值、误报、线上反馈闭环？

回答要点：给出 F1 下降的真实负结果；规则优先是可解释性与安全取舍；后续要做时间切分、校准、漂移监控和人工标注回流。

### “智能查询与补偿闭环”

面试官会问：为什么不用 Text2SQL？如何防止 LLM 直接退款？审批如何防重？

回答要点：模型只做分类/抽取/润色，固定只读模板访问；补偿动作白名单；高风险审批持久化，条件更新和 gateway 幂等键共同防重。

### “监控与验证”

面试官会问：指标怎么证明？测试数量是不是覆盖率？

回答要点：说明固定用例、资源受限单机、并发数、P95、样本口径；338 是测试通过数，不是覆盖率；任何“生产可用”结论都要有环境和基线。

## 6. 技术栈八股，必须绑定项目

### Java / Spring

- `@Transactional` 的代理边界是什么？自调用不会经过代理；本项目让事务边界落在 command handler/repository 入口，异常必须向外抛出才能回滚。
- Spring Kafka 手动 ack 有什么代价？吞吐和位点控制更细，但业务提交与 offset 仍非原子，必须幂等。
- JDBC 为什么不用 ORM？事件 payload 是 JSONB、SQL 需要唯一约束/条件更新/批量投影，Spring JDBC 可明确控制 SQL 和事务；代价是映射代码更多。
- 线程池如何估算？IO 型任务按等待时间和 CPU 比例压测，不拿经验值直接宣称容量；外部 gateway 应设置连接、读取和整体超时。

### PostgreSQL

- MVCC 下为何仍需唯一约束？两个 READ COMMITTED 事务都可能读到旧版本；唯一索引在写入阶段做最终串行化。
- JSONB 的取舍？事件 schema 演进灵活、可保留原始 payload；常用筛选字段应抽列或建表达式索引，否则查询和类型约束变弱。
- WAL/逻辑复制槽风险？消费者停滞会阻止 WAL 回收；需监控 retained bytes、slot active、磁盘水位并设置告警。
- 事件表如何分区/归档？先按时间或聚合规模验证查询模式；归档必须保证重建投影仍能拿到完整历史，不能为了降存储破坏审计。

### Kafka

- 分区数、key、顺序如何取舍？同一订单用 `aggregateId` 作为 key 可保序，热点订单会集中到单分区；扩容分区会改变分布，不能把全局顺序当默认能力。
- at-least-once 与 exactly-once？本项目是至少一次 + 业务幂等；Kafka EOS 不覆盖 PostgreSQL 和第三方副作用。
- DLT 与重试队列区别？短暂故障适合退避重试，无法解析/业务毒消息进 DLT；重放必须有次数上限和隔离区。

### 安全

- JWT 与 session 怎么选？JWT 便于 API/AI/WS 跨服务验证，但撤销困难，所以加入 token version；生产密钥必须注入，不能使用默认 secret。
- CORS、CSRF、XSS 的边界？Bearer token 放 Authorization 头降低 CSRF 风险；CORS 只允许显式来源；前端展示事件内容仍需转义，不能把后端权限检查交给前端。
- 机器回调为何不用用户 JWT？网关回调是服务到服务身份，使用机器密钥并限制路径/权限；密钥轮换和重放防护仍需补齐。

### AI / 机器学习

- 为什么 F1 下降仍保留模型？模型提供发现未知模式的可能，但当前离线证据不支持提升；先灰度、只告警不自动补偿，采集人工反馈后再调参。
- 如何避免数据泄漏？按时间切分训练/验证，特征只能使用事件发生时可获得的信息；不能把未来订单状态作为当前特征。
- 模型服务不可用怎么办？规则检测继续运行，查询退回模板摘要；明确超时、熔断、降级指标，不能无限同步等待。

## 7. 设计取舍清单（Trade-off）

| 选择 | 得到 | 付出 | 什么时候换方案 |
|---|---|---|---|
| 事件溯源而非 CRUD | 可回放、审计、统一事实 | 存储增长、schema 演进、最终一致 | 只关心当前状态时改 CRUD+审计 |
| CDC 而非应用双写 | 消除提交/发送窗口 | 复制槽运维、重复投递 | 低复杂度小系统可用事务 Outbox |
| 异步投影 | 写侧隔离、读侧可扩展 | 旧读、乱序处理 | 强一致核心查询可同步读事实源 |
| 规则优先 + 模型补充 | 可解释、可降级 | 开放发现能力有限 | 标注数据足够且收益稳定再扩大模型职责 |
| 固定查询模板而非 Text2SQL | 安全、可审计、可测试 | 查询范围受限 | 只读副本+SQL AST 校验后再扩展 |
| 内存 Saga + 持久审批 | 实现简单、演示直观 | 多副本恢复有限 | 生产需状态机持久化/工作流引擎 |
| HS256 JWT | 部署简单、跨 Java/Python | 共享密钥、撤销复杂 | 多团队/跨域信任改 RS256/JWKS |

## 12. 领域模型和状态机：面试官会逐个状态拷打

### 12.1 订单状态的业务语义

项目中的状态不是“随便改一个字符串”，而是聚合在事件回放后得到的业务状态。面试时应能说清每个状态的进入条件、允许的下一步以及失败后的语义：

| 状态/事件语义 | 允许的后续 | 容易被问的边界 |
|---|---|---|
| 创建后待支付 | 支付请求、取消 | 创建命令重放不能产生第二个订单 |
| 支付请求 | 支付成功、支付失败、支付重试 | “请求”不是“已支付”，不能提前扣减库存 |
| 支付完成 | 库存预留、退款请求 | 支付回调可能重复，回调状态不能倒退 |
| 库存预留成功 | 确认、发货 | 库存服务超时不能直接判定库存不足 |
| 库存预留失败 | 补偿、人工介入 | 订单可能仍是已支付，不能伪造成未支付 |
| 退款请求 | 退款完成、退款失败 | 请求事件表示意图，完成事件才表示外部结果 |
| 已发货/已完成 | 关闭、售后流程 | 已发货后取消通常是业务拒绝而非技术异常 |

### 12.2 为什么“请求事件”和“结果事件”要拆开

支付、退款、库存都存在外部系统延迟。`PaymentRequestedEvent` 表示本系统已经发起动作，`PaymentCompletedEvent`/`PaymentFailedEvent` 才表示网关确定结果。拆分后可以：

1. 区分“请求没发出去”“请求已发出但未回调”“回调失败”三种故障。
2. 让超时任务和人工重试有明确的状态依据。
3. 避免数据库事务回滚时已经发生的外部副作用被误记为成功。

反问“为什么不在一个事务里同步调用支付？”：外部系统不参与 PostgreSQL 事务，网络超时也不等于支付失败；同步调用会把外部不确定性带入核心写事务。

### 12.3 状态机追问题

- 如果收到 `PaymentCompletedEvent` 两次，聚合怎么处理？应根据事件 ID/命令幂等和当前状态拒绝重复推进，并让检测规则记录异常证据。
- 如果先收到支付成功再收到支付失败，谁覆盖谁？不能简单按到达顺序覆盖；必须依据事件版本/业务回调版本和外部交易号判断，冲突进入人工或异常队列。
- 为什么不允许控制器直接改 `order_view.status`？那会绕过聚合不变量，事件历史和当前视图漂移。
- 取消订单是否一定要生成 `OrderCancelledEvent`？只有状态机允许取消且业务前置条件满足时才生成；否则返回业务错误，不产生“失败也算事件”的假事实。
- 业务修复历史错误怎么办？不更新旧事件，新增纠正事件，并记录操作者、原因和关联原事件。

## 13. 数据表、索引和事件契约

### 13.1 核心数据的职责分层

| 数据 | 角色 | 能否直接修改 | 损坏后的恢复方式 |
|---|---|---|---|
| `domain_events` | 订单事实源 | 只追加 | 备份恢复、WAL/归档、事件重放 |
| `snapshots` | 聚合加载优化 | 可按版本新增 | 删除后从事件重建 |
| `command_log` | 命令幂等和首次响应 | 业务上不可覆盖结果 | 从备份恢复；不能随意清空 |
| `order_view` | 列表/详情查询投影 | 可重建 | 删除后消费历史事件重建 |
| `idempotent_consumer` | 消费事实 | 可清理过期记录 | 重新消费时仍需保留业务唯一性 |
| `compensation_approval` | 高风险动作审批 | 只允许条件状态迁移 | 持久化恢复待审批 Saga |
| `auth_audit_log` | 安全审计 | 追加写 | 从备份恢复，审计失败不阻断主流程 |

### 13.2 索引设计如何回答

- 事件追加最关键的是 `(aggregate_id, event_version)` 唯一约束，它既保证版本不重复，也服务聚合增量加载。
- 聚合回放查询按 `aggregate_id` 和 `event_version > snapshot_version`，应保持稳定排序，不能依赖数据库“碰巧返回顺序”。
- 列表查询集中在 `order_view`，状态、用户、时间范围是候选索引字段；是否建联合索引要由真实查询组合和 `EXPLAIN` 决定。
- DLT、审计和事件表都是持续增长表；索引越多写放大越大，归档前要核对事件重建和审计查询需求。

面试官要求现场写 SQL 时，优先写出“按聚合取快照之后事件”的查询，并说明为什么必须 `ORDER BY event_version`；要求查最新版本时说明 `MAX(event_version)` 在并发下只用于读取，不足以保证写入正确性。

### 13.3 跨 Java 与 Python 的事件契约

Debezium 消息外层是 envelope，真正行数据在 `payload`；PostgreSQL `JSONB` 在 CDC 中可能以字符串出现，AI 侧必须先解串。稳定字段包括 `event_id`、`aggregate_id`、`event_type`，业务字段位于解串后的事件 payload 中。

契约演进的回答模板：

1. 新增字段优先采用可选字段并提供默认值。
2. 不能直接重命名旧字段，至少保留兼容读取窗口。
3. 事件类型是显式白名单，未知类型不能静默丢弃，应进入重试/DLT。
4. Java 序列化测试和 AI `flatten_debezium_event` 契约测试必须同时修改。
5. 对跨版本消费者做 replay 测试，确认历史事件仍可解码。

## 14. 接口层和权限层：从 HTTP 一直问到数据库

### 14.1 一次命令请求的校验顺序

推荐回答顺序：网关/反向代理 -> CORS 与限流 -> JWT/机器密钥认证 -> Controller DTO 校验 -> `@RequirePermission` -> commandId 幂等 -> 聚合业务校验 -> 数据库事务。顺序的理由是尽早拒绝不可信请求，并把业务校验放在事实写入前。

### 14.2 401、403、409、429、5xx 怎么区分

| 状态码 | 项目语义 | 面试官想听什么 |
|---|---|---|
| 401 | 没有凭据、JWT 无效/过期 | 认证失败，不代表用户没有权限 |
| 403 | 凭据有效但权限不足 | 后端权限是最终边界 |
| 409 | 版本冲突、投影未追平、幂等编号参数冲突 | 可恢复的业务/一致性冲突，不要伪装成 500 |
| 429 | 命中登录或通用限流 | 返回 Retry-After/前端友好提示，避免无限重试 |
| 5xx | 依赖故障或未处理异常 | 要有 trace、日志和指标，不能把业务拒绝都打成 500 |

### 14.3 “前端隐藏按钮是否安全”

不安全。Vue 只根据权限决定展示，攻击者仍可直接调用接口。后端 `PermissionInterceptor`/`@RequirePermission` 对每个敏感接口重新判断；机器回调单独使用机器主体，避免把用户 token 暴露给外部网关。

### 14.4 JWT 追问清单

- HS256 的密钥长度和轮换怎么做？当前要求生产注入强随机 `EG_JWT_SECRET`；轮换需要双密钥验证窗口或升级 RS256/JWKS。
- JWT 已签发后如何“退出所有设备”？递增数据库 `token_version`，过滤器比对 claim 中的 `tv`。
- token 放 URL 有什么风险？WebSocket 握手当前需要查询参数，必须限制日志、代理和 referrer 泄漏；普通 HTTP 使用 Authorization 头。
- 权限变化后旧 token 是否立即生效？仅 token version 变更/重新登录可即时失效；若角色直接改库，需决定是否递增版本。
- 密码如何存？只保存 BCrypt 等单向哈希，绝不保存明文；默认演示账号只能作为本地启动便利，公网部署必须改密。

## 15. Kafka 消费的“时间线题”

### 15.1 数据库提交成功，进程在 ack 前崩溃

恢复后 Kafka 重新投递同一条消息。正确行为是：去重表命中后不再次修改投影，但仍要让消费者能够提交位点；不能因为重复就把消息重新抛回 DLT。

### 15.2 数据库提交失败，进程却提交了 ack

这是错误实现，会造成消息被跳过。当前设计要求业务处理异常向外抛出，Kafka error handler 才能重试或进入 DLT；数据库事务与消费位点的提交顺序必须在代码和测试中明确。

### 15.3 版本乱序如何进一步生产化

当前版本守卫能防止 2 覆盖 3，但不能让 2 的字段“补写”到 3 的状态。生产化方案可按成熟度递进：

1. 生产者以 `aggregateId` 作为 Kafka key，先保证同聚合尽量同分区有序。
2. 投影表保存 `last_version`，发现 `incoming_version > last_version + 1` 时记录 gap 指标并暂存消息。
3. 定时 gap healer 从事件库补读缺失版本，按顺序重放。
4. 长时间无法补齐的聚合进入人工/重建队列。

### 15.4 DLT 运维题

- 为什么不能每次从 DLT offset 0 全量重放？会重复消耗带宽，也会让已处理消息再次触发副作用。
- 为什么需要 quarantine？某条消息结构永久错误时，无上限重试会形成循环和告警风暴。
- 重放是否需要权限？必须是管理员/机器权限，且记录操作者、topic、数量、隔离数量和批次。
- 重放成功能否从 DLT 删除？Kafka 没有事务删除已读历史；推进 DLT 位点即可，原消息保留作审计。

## 16. 性能、容量和 SLO：不要只背一个 QPS

### 16.1 当前数据如何正确表达

验证记录中存在不同测试态和不同并发度，回答时必须带上下文：资源受限单机、关闭限流或 DLT 重放、写并发数、预热/稳态时间、样本数、P95 和 409 语义。不能拿一次 30 并发的结果外推生产容量，也不能把读己写 409 当成写入失败。

### 16.2 2 vCPU 全栈合部的瓶颈推理

PostgreSQL 的 WAL/逻辑复制、投影回写、Debezium、Java 和 AI 共用 CPU。并发从 50 降到 30 时吞吐接近而 P95 明显下降，说明进入 CPU 饱和排队区；解决顺序应是拆分 AI/数据库 CPU 预算、提高机器规格、限制后台重放，再做连接池和 SQL 微优化，而不是盲目加线程。

### 16.3 从吞吐反推容量的面试回答

如果业务要求每秒 100 个订单，不能直接说“当前 40 QPS 不够”。需要拆成：每单产生多少事件、CDC/Kafka 消息大小、投影写放大、AI 消费成本、峰值持续多久、可接受 lag 和恢复窗口。再用压测得到单节点安全吞吐（例如 P95 不超过 SLO 的拐点），按峰值/安全吞吐计算实例数，并为重放、重平衡和故障恢复预留余量。

### 16.4 关键指标和告警阈值的设计逻辑

| 指标 | 解释 | 不应只看什么 |
|---|---|---|
| command latency P95/P99 | 用户写请求体验 | 平均值会掩盖排队 |
| optimistic conflict/retry | 热点聚合和客户端重试 | 只看成功率会漏掉重试成本 |
| projection lag / version gap | 读模型新鲜度 | Kafka 总 lag 不等于业务延迟 |
| DLT count/rate | 毒消息或代码回归 | 只看当前数量会漏掉增长速度 |
| AI detection latency | 异常发现时效 | 只看 HTTP latency，AI 是异步链路 |
| approval pending age | 人工处置积压 | 只看数量不看最老任务 |

## 17. 测试矩阵：面试官问“你怎么证明它对”

### 17.1 单元测试

- 聚合状态机：每个合法转移、非法转移、边界金额、重复动作。
- 事件序列：回放后状态与直接执行一致；未知事件类型明确失败。
- 幂等：同 commandId 顺序重复、并发重复、参数指纹冲突。
- 投影：重复消息、低版本消息、空 payload、未知 eventType。
- 安全：JWT roundtrip、篡改、过期、token version、401/403。
- 规则：每条 R001-R005 的命中与不命中样例，避免只测“有异常”。

### 17.2 集成测试

- Testcontainers PostgreSQL 验证唯一约束、事务回滚、advisory lock。
- Kafka 容器验证 DLT 路由、分区保留和重放次数上限。
- Java/Python 事件契约测试验证 envelope、JSONB 字符串和字段命名。
- 网关回调验证重复回调不重复产生完成事件。
- Saga 审批验证并发 approve/reject 只有一个成功，重启后 PENDING 可恢复。

### 17.3 故障演练

至少准备以下脚本化场景：

1. PostgreSQL 重启：已提交事件是否仍能被 CDC 捕获。
2. Kafka 暂停：写入是否可用，恢复后 lag 是否追平，WAL 是否增长。
3. 投影消费者杀进程：重启后是否重复但结果正确。
4. 注入坏 JSON/未知事件：是否进入 DLT 而非阻塞分区。
5. AI 超时：查询是否在 8 秒内降级，规则告警是否继续。
6. WebSocket 断线：重连后最近告警补拉且不重复。
7. Saga 进程重启：待审批动作是否继续，不重复调用 gateway。

### 17.4 测试结果的表达方式

“338 项通过”只能说明固定测试集通过；要回答覆盖率，必须真的生成 JaCoCo/coverage 报告。要回答容量，必须给出机器规格、并发、稳态窗口、错误定义、P95/P99、数据量和是否开启后台任务。

## 18. 部署和排障：面试官会让你现场定位

### 18.1 页面能打开但订单列表为空

排查顺序：

1. 浏览器 Network 看 JWT 是否过期、接口是否 401/403/409。
2. 查 `order_view` 是否有数据，确认命令写入的是同一个数据库。
3. 查 Kafka consumer lag 和 `domain-events` 是否有新消息。
4. 查 Debezium connector 状态、复制槽是否 active、WAL 是否持续增长。
5. 查投影日志中的反序列化、版本缺口、唯一冲突。
6. 用事件库按订单回放，对比投影是否需要重建。

### 18.2 页面能登录但 WebSocket 没有实时告警

检查握手 URL token、`anomaly:view` 权限、反向代理 Upgrade 头、服务端连接日志；确认异常是否真的进入 `anomaly-alerts` topic。不能只重连前端，因为告警可能已经消费成功，应该依赖 `GET /alerts/recent` 补拉历史。

### 18.3 DLT 数量持续上涨

先按异常类型分类：schema 不兼容、外部依赖超时、数据库约束冲突、业务拒绝。查看原消息和异常堆栈，修复消费者后只重放可恢复类别；永久坏消息隔离，不能通过无限重试掩盖代码问题。

### 18.4 命令 P95 突然升高

把请求耗时拆成 DB 连接等待、聚合回放、事件插入、外部同步调用和读己写等待。观察 CPU、连接池 active/pending、Kafka lag、投影版本差和 DLT 重放时间点；若吞吐不升而延迟升，多半是资源饱和或排队，不是简单“Kafka 慢”。

### 18.5 密钥或配置排障

确认 `.env` 是否被 Compose 注入、容器内环境变量是否生效、模板渲染后的 Alertmanager 配置是否更新、JWT secret 是否仍为开发默认值。任何日志都不能打印 JWT、机器密钥、LLM API key 或支付凭据；排障时只能打印 hash/长度/是否为空。

## 19. AI 拓展能力的面试说法

项目后续还加入了多轮自然语言查询、告警去重/风暴抑制、LLM JSON 校验重试、LLM 缓存与 trace、订单终局预测、ReAct 分析、周报/故事线和相似案例检索。面试时要把它们说成“受控的辅助能力”，不是自主代理：

- 多轮查询有 pending 槽、TTL 和 LRU 上限，避免会话无限增长。
- 告警去重按事件/流程门控，带 TTL、LRU 和每分钟风暴上限；去重不能丢失历史告警，所以要有落盘或历史接口。
- LLM 结构化输出失败会重试并做 Pydantic/schema/证据校验；失败则回退模板。
- 缓存 key 必须包含 provider、model、temperature 和 prompt 版本，不能把不同权限用户的结果混用。
- 预测模型只展示风险角标，不自动发新告警、不自动执行资金补偿；否则离线误报会直接造成业务事故。
- ReAct 工具只开放 `query_order/query_events/query_stats` 等只读工具；写操作仍由人工在环触发 Saga，并经过白名单与审批。
- 相似案例检索是可解释的加权相似度，不应包装成完整向量数据库或 RAG 平台。

## 20. 系统设计变体题

### 20.1 如果订单量增长 100 倍

先拆分部署：PostgreSQL 与 AI 不再和 Java 共用 CPU；Kafka 增加分区但维持同订单 key；投影按消费组水平扩展；事件表按时间/租户分区并设计归档；查询走读副本或专用 OLAP；快照阈值通过压测调优。核心写路径仍保持单聚合串行化，不能为了吞吐取消版本不变量。

### 20.2 如果要求强一致订单详情

不要让所有读都等待投影。可以对写后关键详情直接从事实事件回放，或在同一数据库事务维护一个极简当前状态表；列表、统计仍异步投影。明确强一致范围，否则系统成本会被所有查询放大。

### 20.3 如果要求跨机房高可用

需要数据库复制/故障切换、Kafka 多 broker 多副本、Debezium connector 状态持久化、外部 gateway 的跨区域幂等键、密钥和配置中心、全链路 trace，以及 RPO/RTO 演练。单机 Compose 的重启验证只能证明恢复路径存在，不能证明跨机房切换。

### 20.4 如果要支持多租户

所有事件、命令日志、投影、审计和审批记录增加 `tenant_id`，权限 claim 绑定租户；数据库查询必须强制带租户条件，可用 PostgreSQL Row Level Security 作为额外防线。Kafka key 和 topic 是否按租户隔离要基于噪音、合规和容量决定。

### 20.5 如果要支持事件 schema 大规模演进

建立事件版本号和兼容矩阵，消费者支持旧版本读取；生产事件不能依赖 Java 类名直接反序列化；引入 schema registry 前先明确兼容规则、回放窗口和失败处理。迁移期间同时发布新旧字段，等所有消费者升级后再下线旧字段。

## 21. 反模式题：哪些回答会被扣分

- “Kafka 保证 exactly-once，所以不会重复。”错：外部 DB/网关不在 Kafka 事务内。
- “加 Redis 锁就解决并发。”错：锁失效、过期和事务分离仍可能写出错误；数据库约束才是底线。
- “投影异步所以最终一致不用管。”错：必须定义最大延迟、409 契约、lag 指标和重建路径。
- “AI 提升了准确率。”若没有对照和指标口径就是夸大；本项目真实结果是 Isolation Forest 叠加后 F1 下降。
- “前端没有入口所以用户不能调用。”错：安全边界在后端鉴权，不在按钮隐藏。
- “测试全绿就是生产可用。”错：还缺备份恢复、滚动发布、容量、权限攻击、依赖故障和数据保留演练。
- “Saga 就是分布式事务。”错：Saga 是可补偿的最终一致流程，无法回滚已发生的外部副作用。

## 22. 30/60/90 分钟面试准备方案

### 30 分钟速过

只背架构图、三分钟介绍、事件事实源、幂等、读己写、DLT、AI 边界和五句复盘卡。目标是被打断后仍能把主线讲完。

### 60 分钟深挖

再看状态机、命令事务、投影乱序、Saga 审批、JWT token version、性能瓶颈和测试矩阵。每个主题准备一个“故障发生 -> 当前表现 -> 修复 -> 未完成”的四句答案。

### 90 分钟模拟答辩

按自测题随机抽题，要求每题都落到类名、表名、topic 或指标；不会的地方明确说“当前未实现/未验证”，然后给升级路径。最后打开代码导航速查表，现场能在 30 秒内定位实现。
