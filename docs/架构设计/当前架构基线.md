## 1. 当前定位

EventGuard 是一个单仓库、多进程部署的电商订单事件溯源与异常治理平台。系统的主线不是“AI 直接改订单”，而是：

```text
订单命令
  -> 聚合校验与事件追加
  -> PostgreSQL 事实事件
  -> Debezium CDC / Kafka 事件传播
  -> 订单查询投影、异常检测、Saga 补偿分别消费
  -> 查询、告警、审批和审计形成运营闭环
```

当前实现已包含：

- Java 17 + Spring Boot 3.3 后端；
- PostgreSQL 事件库、命令日志、快照、投影、审批和审计数据；
- Debezium PostgreSQL logical replication -> Kafka `domain-events`；
- `order-view-projection`、`saga-trigger`、异常告警等独立消费组；
- Python FastAPI AI 服务，消费事件执行规则/模型检测并提供受限智能查询；
- Vue 3 管理台、JWT/RBAC、WebSocket 实时告警、补偿审批；
- Docker Compose、Prometheus、Alertmanager、Grafana、Loki 和备份/归档/混沌脚本。

当前明确不是：

- 不是多副本高可用集群；
- 不是端到端 exactly-once；
- 不是让 LLM 直接生成 SQL 或执行资金动作；
- 不是已承载真实生产用户的商业系统。

### 2.1 服务边界

| 服务/组件 | 主要职责 | 不应承担的职责 |
|---|---|---|
| `eventguard-server` | 订单事实写入、查询投影、认证授权、补偿编排、告警 API | 不把 AI 当作写入事实源 |
| `eventguard-ai` | 消费事件做检测、模型/LLM 辅助查询和分析 | 不直接连接业务写库，不直接执行退款 |
| PostgreSQL | 本地事务、事实事件和状态类持久化 | 不承担跨系统分布式事务 |
| Debezium | 捕获已提交 WAL 变更并发布 Kafka | 不保证下游业务 exactly-once |
| Kafka | 解耦传播、消费组隔离、重试/DLT | 不作为订单事实源 |
| Vue UI | 查询、展示、人工审批和操作入口 | 不作为权限边界 |
| Prometheus/Grafana/Loki | 指标、告警、日志可观测性 | 不替代业务审计 |

## 3. 数据分层和事实来源

### 3.1 数据职责

| 数据对象 | 事实/派生 | 写入方式 | 重建方式 |
|---|---|---|---|
| `domain_events` | 唯一业务事实 | 事务内 append-only | 备份/WAL/归档恢复 |
| `snapshots` | 聚合派生优化 | 达到阈值时新增 | 删除后从事件回放 |
| `command_log` | 命令幂等事实 | 与事件同事务 | 需与事件一起恢复 |
| `order_view` | 查询派生模型 | Kafka 投影事务 | 从事件全量/增量重放 |
| `idempotent_consumer` | 消费处理事实 | 与具体投影同事务 | 清理后需评估重放窗口 |
| `anomaly_alert_history` | 检测结果历史 | AI/Java 告警消费 | 原事件重新检测 |
| `compensation_approval` | 人工决策事实 | 条件状态更新 | PENDING 启动恢复 |
| `auth_audit_log` | 安全审计事实 | 追加记录 | 从备份恢复 |

事件库是订单状态的唯一事实来源。Kafka 可能积压或重复，`order_view` 可以删除重建，快照只是优化，任何冲突都以事件序列为准。

### 3.2 事件契约

Java 写入 `domain_events` 后，Debezium 消息外层为 envelope，行数据在 `payload`。稳定字段是 `event_id`、`aggregate_id`、`event_type`、`event_version`；事件业务字段位于 JSONB `payload` 中。Python 侧需要兼容 JSONB 字符串和已解析 Map 两种形态。

事件反序列化集中在 `EventDeserializer`，未知 `event_type` 必须抛出异常进入重试/DLT，不能静默跳过。Java 侧事件契约测试和 AI 侧 `test_event_contract.py` 共同防止 envelope、字段名和 JSONB 形态漂移。

## 4. 写路径：命令到事实事件

```text
HTTP POST /orders/... 
  -> AuthFilter / PermissionInterceptor / RateLimitFilter
  -> OrderCommandController DTO 校验
  -> OrderCommandHandler
  -> commandId 幂等查询 + advisory lock
  -> AggregateRepository.load
  -> OrderAggregate 状态机
  -> EventStoreJdbcImpl.append
  -> SnapshotStore（达到阈值时）
  -> CommandLogRepository.saveResult
  -> PostgreSQL commit
  -> 返回 eventVersion / expectedVersion
```

### 4.1 并发控制的两层防线

1. 应用层加载聚合并检查当前版本，尽早返回 `OptimisticConcurrencyException`。
2. 事件表 `(aggregate_id, event_version)` 唯一约束兜住检查和插入之间的竞争窗口。
3. 同一个 `commandId` 的并发请求通过 PostgreSQL transaction advisory lock 串行化。
4. 发生可重试冲突时重新加载聚合；业务状态非法则不重试。

前置检查改善错误语义，数据库约束保证正确性，不能用其中一层替代另一层。

### 4.2 命令幂等

`command_log` 保存 commandId、聚合、命令类型、请求指纹和首次结果。相同 commandId + 相同指纹直接复用首次结果；同编号不同参数、不同订单或不同命令类型返回冲突。命令日志和事件同一事务提交，避免“事件成功但重试看不到幂等记录”或“幂等记录成功但事件回滚”。

## 5. CDC 与 Kafka

应用只写 PostgreSQL，不在同一业务流程中直接发送 Kafka。Debezium 从 logical replication slot 读取已提交 WAL，发布到 `domain-events`。这一选择消除了应用层数据库/Kafka 双写窗口，但 CDC 仍可能重复发布，因此所有消费端按至少一次投递设计。

### 5.1 当前消费组

| 消费组 | 输入 | 结果 | 失败处理 |
|---|---|---|---|
| `order-view-projection` | `domain-events` | 更新 `order_view`、投影进度 | JDBC 事务、重试、DLT |
| `saga-trigger` | `domain-events` | 触发补偿步骤 | 事件去重、重试、DLT |
| AI consumer | `domain-events` | 规则/模型检测、发布告警 | AI 重试/指标 |
| anomaly alert consumer | `anomaly-alerts` | 历史记录、WebSocket | 消费去重 |
| `dlt-replay` | `*.DLT` | 有限重放回主 topic | 超过上限进 quarantine |

### 5.2 投影一致性

`OrderViewProjection` 在一个 JDBC 事务中完成：消费去重占用、按版本守卫更新视图、更新进度。数据库提交后才通知 `ProjectionProgressNotifier`；通知丢失时 `OrderQueryService` 用 50ms 轮询兜底，最多等待约 2 秒，仍未达到 `expectedVersion` 返回 409。

版本守卫只能防止旧消息覆盖新消息，不能解决版本缺口。生产化需要记录 gap、暂存后续事件或从事件库补齐重放。

## 6. 查询和时间旅行

普通列表、详情、统计读取 `order_view`。订单事件时间线直接读取事件库。详情查询支持 `expectedVersion`，用于写后读；也支持 `upToVersion` 形式的历史截断，当前主要提供事件范围/投影能力，完整的任意版本状态重建仍是后续增强项。

查询服务不能反向调用命令端修改订单。读模型落后时应返回明确的同步中语义，而不是返回旧值并标记成功。

## 7. 异常检测和 AI

### 7.1 Java 规则层

Java 侧 `RuleEngine` 使用 `RuleContextLoader` 读取事件上下文和历史基线，当前规则包括金额偏差、重复支付、状态跳变、高频操作、库存溢出。规则输出告警，不直接执行高风险补偿。上下文缓存为进程内 TTL，多副本各自维护，属于当前已知上限。

### 7.2 Python AI 服务

Python 服务消费 CDC 事件并提供 FastAPI 接口，能力包括：

- 规则/统计/Isolation Forest 检测；
- 异常查询与固定意图自然语言查询；
- LLM 根因分析和结构化输出校验；
- 多轮会话、告警去重/风暴抑制、LLM 缓存与 trace；
- 终局预测、周报、订单故事线、相似案例检索；
- ReAct 只读分析工具。

模型只做分类、抽取、排序、解释或只读工具调用。预测结果不自动发新告警，ReAct 不直接拥有写工具；补偿仍需 Java 白名单、权限和审批。

规则基线 F1=0.887，叠加 Isolation Forest 后 F1=0.753，因此当前架构采用规则优先、模型补充和可降级策略，不宣称模型带来准确率提升。

## 8. 补偿、网关和审批

`SagaTrigger` 消费失败类领域事件，将事件映射成补偿步骤；`CompensationActionRegistry` 只注册白名单动作。支付、库存和通知通过 gateway 接口隔离，默认 Mock，真实适配器可替换。

外部动作成功后才追加完成事件，避免“网关失败但事件写成功”。高风险动作创建 `compensation_approval`，审批通过/拒绝使用 `WHERE status='PENDING'` 条件更新，重复点击只有一个请求成功。Saga 实例当前保存在单实例内存 Map，但 PENDING 审批单持久化剩余步骤并由 `SagaRecoveryRunner` 在启动时恢复；多副本仍需落库完整 Saga 状态机。

## 9. 认证、授权与安全

- 用户通过 JWT 认证，HS256 与 Java/Python 共享 `EG_JWT_SECRET`；生产禁止默认密钥。
- `AuthFilter` 同时识别用户 JWT 和 `EG_MACHINE_API_KEY` 机器主体。
- `@RequirePermission`/`PermissionInterceptor` 做后端接口鉴权，前端按钮隐藏仅是体验优化。
- JWT claims 含 `tokenVersion`，登出所有设备/改密递增数据库版本，使旧 token 失效。
- 登录防爆破和通用 per-IP 限流当前以内存为主，单实例有效；多副本升级为 Redis 分布式计数。
- LLM 配置按用户/内部机器权限隔离，API key 加密存储或脱敏返回，日志不得打印密钥。
- WebSocket 握手需要有效 JWT 和 `anomaly:view`，多实例广播升级路径是 Redis Pub/Sub。

## 10. 可观测、运维和恢复

### 10.1 指标

命令延迟/吞吐/冲突、投影处理和版本差、Kafka lag、AI 检测吞吐和延迟、告警数、Saga 状态、审批积压、限流拒绝、HTTP 5xx 都应可查询。Prometheus 负责采集和规则，Alertmanager 负责分组、静默、恢复通知和多渠道扇出，Loki 聚合容器日志。

### 10.2 备份、归档与重建

`domain_events` 是最高优先级备份对象；恢复后先校验事件数量、版本连续性和核心表。`retain-events.sh` 归档旧事件前必须确认快照和投影重建策略，不能直接删除唯一历史。投影损坏时可以停投影、清空派生表、从事件/归档按顺序重放，再恢复消费位点。

### 10.3 DLT 重放

管理员接口 `/admin/dlt/{topic}/replay` 和定时任务负责有限重放。重放使用独立消费组、保留分区和 `eg.dlt.replay.attempt` 头；超过最大次数转入 quarantine。DLT 原消息保留作为审计，不把“读过”误认为已删除。

## 11. 当前已知边界

| 边界 | 当前表现 | 升级路径 |
|---|---|---|
| Saga 状态 | 实例 Map 单实例，审批单可恢复 | Saga 状态全量落库/工作流引擎 |
| 投影通知 | 进程内通知，轮询兜底 | Redis Pub/Sub 或共享进度服务 |
| 登录计数 | 内存单实例 | Redis/IP+账号维度 |
| 规则上下文缓存 | 进程内 TTL | 共享缓存或按租户重算 |
| 事件乱序 | 版本守卫防倒退 | gap 暂存和重建 |
| WebSocket | 单实例连接集合 | Redis Pub/Sub + 网关粘性/广播 |
| AI/DB 资源 | 单机共置有 CPU 竞争 | 拆分服务或提高 CPU 预算 |
| 认证密钥 | HS256 共享密钥 | RS256/JWKS/密钥轮换 |
| 生产容量 | 已有单机压测 | 按目标 SLO 做多节点容量测试 |

## 12. 代码结构与阅读导航

本节把当前实现映射到仓库目录，作为开发者与面试官的代码阅读入口。模块按业务边界划分，跨服务只通过 HTTP、Kafka 或数据库 CDC 约定协作。

### 12.1 顶层模块

| 目录 | 职责 | 主要入口 |
|---|---|---|
| `eventguard-server/` | 订单领域、事件存储、读模型、鉴权、Saga 与网关适配。 | `EventGuardApplication` |
| `eventguard-ai/` | 异常检测、智能查询、根因分析、预测与报告。 | `app/main.py` |
| `eventguard-ui/` | Vue 管理台和运营工作流。 | `src/main.ts` |
| `eventguard-benchmark/` | 全栈功能、负载与报告生成。 | `run.py` |
| `eventguard-chaos/` | PostgreSQL、Kafka、AI 延迟故障演练。 | `*.sh` |
| `debezium/` | PostgreSQL WAL 到 Kafka 的 CDC 配置。 | `conf/application.properties` |
| `postgres-init/` | 初始模式与逻辑复制配置。 | `00-schema.sql`、`01-logical.sql` |
| `prometheus/` | 抓取、告警、日志与看板配置。 | `prometheus.yml` |
| `scripts/` | 备份、归档和开发辅助脚本。 | `backup-db.sh`、`retain-events.sh` |

### 12.2 后端分层

```text
HTTP / WebSocket
  ├── auth            身份、权限、审计、令牌吊销
  ├── command         命令、聚合、事务、版本与幂等
  ├── event           领域事件、事件仓库、快照
  ├── query           order_view、Kafka 投影、读己写
  ├── gateway         支付、库存、通知的端口与适配器
  ├── compensation    Saga、审批、补偿动作
  ├── anomaly         Java 规则上下文、告警消费与 WebSocket
  └── common          配置、指标、异常、共享安全与基础设施
```

依赖方向保持从 HTTP/应用层指向领域与基础设施；`common` 只放跨领域技术能力，不承载订单业务规则。`query` 不能反向调用 `command` 改写订单，投影只消费已提交事件。

### 12.3 跨服务代码链路

```text
UI -> Server command -> PostgreSQL domain_events
                         -> Debezium -> Kafka domain-events
                                            -> Server projection -> order_view
                                            -> AI detection -> anomaly-alerts -> UI WebSocket
UI -> AI query/report -> Server read APIs
```

### 12.4 推荐阅读顺序

1. 本文第 1-5 节：建立当前拓扑和数据流。
2. `command/aggregate/OrderAggregate`、`EventStoreJdbcImpl`、`OrderCommandHandler`：理解写侧不变量。
3. `OrderViewProjection`、`ProjectionProgressNotifier`、`OrderQueryService`：理解最终一致和读己写。
4. `KafkaConsumerConfig`、Debezium 配置、`EventDeserializer`、contracts：理解跨服务契约。
5. `anomaly/`、`eventguard-ai/app/`：理解检测和 AI 降级。
6. `compensation/saga/`、gateway、审批控制器：理解副作用和人工在环。
7. `auth/security/`、监控配置、验证报告：理解安全、可观测和证据边界。

构建产物、运行报告、数据库备份、环境变量与本地 IDE 配置均不应提交，具体规则见仓库根目录 `.gitignore`。
